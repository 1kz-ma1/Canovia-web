# V58.9 Recall Candidate Outcome Trace

Status: implemented / validated  
Branch: `feature/v58-9-recall-candidate-outcome-trace`

## 1. Goal

Connect AI-generated Recall Candidate provenance to actual Recall outcomes while
keeping learner difficulty separate from Candidate quality.

```text
StudyRecallCandidate
→ Human Review / promote
→ StudyRecallItem
→ Again / Hard / Good / Easy
→ traceable Review Evidence
→ provider-free outcome projection
```

V58.9 is an observation layer.

It does not automatically rescore Candidate quality.

## 2. Why Recall difficulty is not Candidate quality

An `Again` response does not prove that an AI-generated Candidate is poor.

Observed difficulty may come from:

- genuinely difficult source content;
- insufficient prior study;
- wording quality;
- ambiguous source material;
- review timing;
- learner-specific memory state.

Therefore V58.9 deliberately avoids a causal quality score.

Original Candidate confidence and later Recall outcomes remain separate facts.

## 3. Candidate lineage in Recall Evidence

When a reviewed Recall Item has one or more promoted Candidate origins, the
existing `study_recall_reviewed` Task Evidence now records bounded ordered
lineage arrays:

- `study_recall_candidate_ids`
- `study_recall_source_ids`
- `candidate_confidences`

The arrays use the same Candidate order and are capped at 12 entries.

This handles the valid case where multiple reviewed Candidates were edited and
promoted into the same existing Recall Item.

Manual Recall cards record empty arrays.

Existing review idempotency remains unchanged, so one Recall review still
produces one Evidence row.

## 4. Intelligence normalization

`TaskEvidenceAdapter` exposes only bounded known lineage facts:

- positive Candidate IDs;
- positive Source IDs;
- confidence values clamped to 0-100.

It does not pass through:

- Candidate prompt;
- Candidate answer;
- source excerpt;
- raw AI payload.

The current normalized-facts boundary therefore remains intact.

## 5. Historical data support

No migration or backfill is required.

Existing promoted Candidates already store:

`promoted_item_id`

Existing Recall Reviews already store:

`study_recall_item_id`

Therefore historical Candidate → Item → Review relationships can be projected
from current relational data even though older Task Evidence rows do not contain
the new direct lineage arrays.

## 6. Outcome projection

`StudyRecallCandidateOutcomeService` is provider-free and mutation-free.

For each promoted Candidate it projects the outcome of its linked Recall Item:

- original Candidate confidence;
- source identity;
- review count;
- Again / Hard / Good / Easy counts;
- latest rating;
- lapse count;
- current mastery state;
- self-rated recall success percent;
- outcome state.

Outcome states:

```text
unobserved
developing
needs_reinforcement
retained
```

Rules:

- no reviews → `unobserved`
- current Item satisfies existing Recall mastery → `retained`
- at least 2 reviews and Again is at least half of reviews →
  `needs_reinforcement`
- otherwise → `developing`

These states describe learning/card outcomes, not Candidate quality.

## 7. Shared Item / multiple Candidate safety

Multiple Candidates may validly point to one Recall Item after Human Review
editing/deduplication.

V58.9 keeps every Candidate lineage but computes Task-level Recall metrics from
unique Item outcomes.

Therefore:

```text
2 Candidate lineages
→ 1 Recall Item
→ 1 Review
→ promoted_candidate_count = 2
→ promoted_item_count = 1
→ review_count = 1
```

Review activity is never doubled because of Candidate lineage multiplicity.

## 8. Aggregate projection

Task-level projection includes:

- promoted Candidate count;
- promoted unique Item count;
- observed Candidate count;
- observed unique Item count;
- retained unique Item count;
- reinforcement-needed unique Item count;
- total unique Recall review count;
- self-rated successful Recall count;
- self-rated Recall success percent;
- average original Candidate confidence.

Successful self-rated Recall is:

`Hard + Good + Easy`

Again is excluded.

This metric remains explicitly self-rated and is not promoted to objective
Practice accuracy.

## 9. Descriptive confidence bands

Original AI Candidate confidence is grouped only for descriptive observation:

- high: 85-100
- medium: 60-84
- low: 0-59

Each band projects:

- Candidate count;
- unique Item count;
- observed Candidate count;
- retained Candidate count;
- unique Review count within the band;
- Again count.

Bands do not change extraction ranking or Candidate confidence.

## 10. Recall UI

When the Task has promoted AI Candidate lineage, Recall shows a collapsed:

`AI候補の実Recall結果`

section.

It includes:

- AI Candidate count;
- resulting unique Recall Item count;
- retained unique Item count;
- Recall review count;
- self-rated Recall success;
- average original AI confidence;
- reinforcement-needed count;
- recent Candidate outcome rows.

The UI explicitly explains that observed difficulty includes content/learner
difficulty and does not automatically mean the Candidate is poor.

Manual-only Recall Decks do not render the section.

Opening the section performs no provider call.

## 11. Boundaries

V58.9 does not:

- call AI/provider;
- change Candidate extraction;
- change V58.8 batch ingest;
- change Candidate Human Review;
- change Candidate confidence;
- create an automatic Candidate quality score;
- rewrite cards;
- change Recall scheduler;
- change V58.6 Task progression;
- add a migration;
- change entitlement or billing.

## 13. Result

Canovia can now retain the complete observational path:

```text
source
→ AI Candidate + original confidence
→ Human Review
→ promoted Recall Item
→ real Recall reviews
→ normalized Evidence lineage
→ deterministic outcome projection
```

This completes the V41.12 "Candidate品質を実Recall成績へ接続" follow-up at the
safe observation boundary.

A future calibration or extraction-policy change must use accumulated outcome
data with an explicit causal/reliability design instead of treating memory
difficulty as direct Candidate quality.
