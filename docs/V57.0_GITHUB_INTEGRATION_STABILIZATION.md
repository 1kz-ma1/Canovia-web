# V57.0 GitHub Integration Stabilization

## Goal

Make GitHub integration failures diagnosable instead of surfacing as raw 500 / 403 responses.

V57.0 is an infrastructure stabilization phase before Development State First.

It does not redesign Development Workspace yet.

## Problems addressed

Observed production behavior:

- `/admin/github` previously returned 500 because the diagnostics path queried an incorrect inferred table name.
- GitHub write/evidence routes can return raw 403 when entitlement is unavailable, including Super Admin Free/Premium Preview.
- GitHub App server configuration, repository installation, user entitlement, and queue-worker readiness are currently separate failure domains but can look identical to users.
- Render currently has no separately observed queue worker service, so automatic webhook Return Sync cannot be assumed healthy.

## Principles

### 1. Diagnose before mutate

GitHub UI must distinguish:

- Canovia code/schema problem
- Canovia operator / Render configuration problem
- current account capability / preview-mode restriction
- Repository editor permission problem
- GitHub App installation / permission problem
- Queue worker / webhook processing problem

### 2. Web UI write denial is fail-closed but not opaque

Backend authorization still denies unavailable capabilities.

However, user-originated web actions should redirect back to the current GitHub surface with an actionable explanation instead of emitting a generic 403 page.

### 3. No secret disclosure

Diagnostics may expose booleans such as:

- App ID configured
- Private Key configured
- Install URL configured
- Webhook Secret configured

It never displays:

- private key
- webhook secret
- JWT
- installation token
- PAT

### 4. Manual connection and automatic Return Sync are separate readiness levels

```text
Interactive GitHub App connection/write
requires:
- DeveloperGithubWrite entitlement
- App ID + Private Key
- valid Install URL
- Repository installation + required write permissions

Automatic Return Sync
additionally requires:
- Webhook Secret
- async Queue driver
- queue schema
- running worker observed through processed deliveries
```

## New readiness projection

Add `GitHubIntegrationReadinessService`.

It provides:

- actor capability status for DeveloperGithubEvidence
- actor capability status for DeveloperGithubWrite
- safe runtime configuration status
- actionable denial message
- readiness labels for Workflow UI

For Super Admin Preview:

- Free/Premium preview restrictions are identified explicitly.
- To test the real GitHub App connection, the operator is told to return to Super Admin mode.

## Diagnostics hardening

`GitHubIntegrationDiagnosticsService` must:

- use the model-declared webhook delivery table name
- check required tables before querying
- avoid throwing just because one diagnostics table is missing
- expose schema readiness
- expose install URL readiness separately from App credential readiness
- emit operator steps with owner category:
  - CANOVIA
  - RENDER
  - GITHUB APP
  - REPOSITORY
- keep worker state as observed/unverified/attention instead of assuming process liveness

## Web action behavior

The following web actions should return an explanatory status redirect when the relevant capability is unavailable:

GitHub Workflow:

- Repository refresh
- GitHub App connect
- GitHub App callback completion
- connection check
- review-only Repository change

Execution GitHub Handoff:

- prepare
- confirm
- Return Sync
- Evidence decision apply

Plan edit / artifact identity checks remain authoritative and may still use 403/404 where appropriate.

## GitHub Workflow UI

Add an Integration Readiness surface near the top of GitHub Workflow.

It shows separately:

- Repository read capability
- Review-only write capability
- GitHub App server setup
- Automatic Return Sync readiness

If blocked, show who owns the next action:

- YOUR PLAN ACCESS
- CANOVIA OPERATOR
- GITHUB / REPOSITORY ADMIN
- PLAN / ENTITLEMENT
- RENDER WORKER

The existing workflow lanes remain unchanged in V57.0.

## Admin diagnostics

The operator checklist becomes data-driven and must clearly identify:

- App credentials
- Install URL
- Webhook Secret
- async Queue
- DB schema
- Repository installation
- Worker observation

## Validation

At minimum:

1. diagnostics page does not 500 when webhook-delivery table is unavailable.
2. diagnostics uses `github_webhook_deliveries`.
3. App credential and Install URL readiness are separate.
4. Free/Premium Super Admin preview denial returns actionable redirect, not 403.
5. normal no-entitlement denial returns actionable redirect.
6. read/write capability statuses render in GitHub Workflow.
7. App not configured is labeled Canovia operator action.
8. Install URL missing is labeled Canovia operator action.
9. disconnected Repository is labeled GitHub/Repository action.
10. connected Repository remains write-ready when entitlement/config permit.
11. Execution GitHub Handoff capability denial redirects instead of 403.
12. Plan edit denial remains forbidden.
13. existing V46.5 App Connection regressions pass.
14. existing V46.10 Webhook Return Sync regressions pass.
15. existing Development Workspace regressions pass.

## Non-goals

V57.0 does not:

- create a Render background worker automatically
- change pricing / entitlement policy
- bypass GitHub Organization approval
- bypass Repository installation permission
- redesign Development Workspace stages
- make GitHub mandatory for Development plans


## Implementation / Validation

Implemented:

- `GitHubIntegrationReadinessService`
  - separates DeveloperGithubEvidence / DeveloperGithubWrite
  - distinguishes App credential / Install URL / Webhook / async Queue readiness
  - identifies Admin Free/Premium Preview as the cause of capability denial
  - projects Repository-level next owner
- GitHub Workflow
  - raw capability 403 responses replaced by actionable redirects
  - true Plan/editor authorization remains fail-closed
  - Integration Readiness surface added
  - Repository cards show next owner / blocker
- Execution GitHub Handoff
  - shared readiness projection
  - capability denial returns to current Development context
  - validation failures return to the current context with form errors
- Admin GitHub diagnostics
  - schema-safe table checks
  - canonical `github_webhook_deliveries` table lookup
  - diagnostic query failures are reported instead of causing the diagnostics page to 500
  - operator checklist identifies CANOVIA / RENDER / GITHUB APP / REPOSITORY ownership
  - worker liveness is treated as observed/unverified rather than assumed
- source-text integrity
  - GitHub file bodies preserve leading/trailing whitespace and final newline
  - only the two GitHub file-body routes are excluded from Laravel TrimStrings
  - ordinary form fields continue to use normal request normalization

Production investigation that motivated V57.0:

- historical `/admin/github` 500 traced to the old inferred `git_hub_webhook_deliveries` table name
- current model explicitly uses `github_webhook_deliveries`
- GitHub Workflow itself was observed returning 200 in production
- repository registration / refresh paths were observed returning normal redirect → 200 flows
- no separate Render Queue Worker service was observed, so automatic Return Sync still requires operator/runtime completion
