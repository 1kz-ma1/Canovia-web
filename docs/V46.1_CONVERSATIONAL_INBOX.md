# V46.1 Conversational Inbox

## Purpose

Inboxを「分類済みデータを入力するフォーム」ではなく、Canoviaへ曖昧な意図・資料・作業結果をそのまま渡せるConversational Intakeへ再定義する。

初見ユーザーへTitle / Category / Plan / Taskの事前整理を要求しない。

```text
User
  -> Inbox Composer
  -> InboxItem (canonical capture)
  -> Interpretation / clarification
  -> Human-reviewed action
```

Inboxは保存箱を廃止しない。Conversation-first UIは既存InboxItemの上に置く入口であり、未整理状態そのものを有効な状態として維持する。

## Primary UX

初期画面の主入力は1つのcomposerとする。

- text / memo / intentを同じtextareaへ入力
- URLはtextareaへ貼り付ければ最初のHTTP(S) URLをsource_urlとして抽出
- image / screenshot / PDFはcomposerのattachmentとして追加
- titleは既存inferTitleで自動生成
- Plan / Taskはcapture時に必須にしない
- advanced title / Plan fieldsをprimary capture surfaceへ表示しない

capture直後は一時的なConversation previewを表示する。

- YOU: 今渡した内容
- CANOVIA: 「受け取った」「まだ分類不要」を明示
- Automatic AI entitlementがありNative AIが利用可能な場合、capture直後にrouting suggestionまで自動生成する
- AI障害時もcapture自体は成功させ、未整理Inboxとして残す
- authenticated userは既存CompanionへContext付きで会話を継続できる
- 保存済みInbox Itemへ戻れる

Conversation preview自体は新しい会話DBを作らない。複数ターン相談は既存Canovia Companionを再利用し、InboxとCompanionの責務を重複させない。

## Interpretation boundary

既存Inbox Intelligenceはcandidate生成だけを行う。

```text
InboxItem
  -> InboxIntelligenceService
  -> routing_suggestion
  -> review
  -> InboxRoutingService
  -> canonical mutation
```

AIはPlan / Task IDを選ばない。routing_suggestionだけではcanonical dataを変更しない。

判断できないものはkeep_inboxへ残してよい。低confidenceを無理にTask / Planへ変換しない。

## Action boundary

Conversational Inboxの責務は「何をしたいかを受け取り、次に進める状態へする」ところまでとする。

現行の確定先は既存InboxRoutingService / Companion Mutation Candidateを使用する。

- Task作成・Task更新: Companion Candidate
- Plan更新: Companion Candidate
- Future Memo / memory: Companion /既存memory path
- Evidence / Recall / Career / Plan Resource: InboxRoutingService
- 未整理: InboxItem

V47 Execution Orchestrationとの直接dispatchはOrchestration側のrequest contractがcanonical化されてから接続する。Inbox側から独自のexecution tableや暫定payloadを先行作成しない。

将来の接続は以下の境界を守る。

```text
Inbox / Companion
  -> explicit Execution Request candidate
  -> human confirmation
  -> Execution Orchestration Layer
  -> assignee / AI / dependency / contract execution
```

Inboxは担当分配やdependency解決を行わない。Orchestration Layerはcapture UXやuser intent clarificationを持たない。

## Compatibility

既存POST `inbox.store`を維持する。

新しいInbox composerのみ `intake_mode=chat` を送る。
Space Stationや既存clientはintake_mode未指定のまま従来captureとして動作する。

Chat modeでのみInboxItem.metadataへ以下を保存する。

```json
{
  "intake_mode": "chat",
  "capture_surface": "inbox"
}
```

absolute UI stateやconversation preview stateはDBへ保存しない。

## Validation

- text / URL / image / PDFのいずれか1つ以上
- attachment最大10MB
- URL抽出はHTTP(S)のみ
- inferred URL以外の本文はそのまま保持
- explicit source_urlを送る既存client validationは維持
- private storage / ownership authorizationは変更しない

## Non-goals

- Inbox独自のchat thread model
- AIによる自動Plan / Task確定
- capture時の自動canonical mutation
- Execution Orchestrationの暫定contract実装
- 既存Space Station capture semanticsの変更


## Follow-up: V47.1

V46.1で未確定としていたExecution Orchestrationとのrequest contractはV47.1でcanonical化した。
以後のInbox / Companion -> Execution Orchestration handoffは `docs/V47.1_EXECUTION_REQUEST_HANDOFF.md` を正とする。

V46.1の「Execution Orchestrationの暫定contractを実装しない」というNon-goalは、V46.1時点で独自の仮contractを先行させないという意味であり、V47.1の正式contract追加を禁止するものではない。
