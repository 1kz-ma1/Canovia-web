## 1. Purpose

Long-term, Canovia may become not only a product but a repeatable system for:

```text
Product Discovery
+
Value Design
+
Specification
+
Implementation
+
Review
+
Telemetry
+
Improvement
```

The goal is not autonomous company management.

The goal is to increase the amount of high-quality product work a founder / small team can operate with strong Context continuity.

## 4. Products born on the Platform

Principle:

> A product created by Canovia should not be built first and integrated with Canovia later if the needed platform contracts already exist.

Future first-party products should prefer starting on:

- Identity
- Context
- Consent
- Activity
- Capability
- Telemetry
- Entitlement
- Intelligence

This requires those contracts to mature first.

---

## 5. Canovia as first customer

First-party apps should not receive unrestricted private shortcuts by default.

Where practical, use the same future contracts intended for partners:

- Identity Contract
- Context Contract
- Consent Contract
- Activity Contract
- Capability Contract

First-party products become reference implementations.

---

## 6. Incubation model

Do not jump from Opportunity directly to standalone app.

Candidate flow:

```text
Idea / Opportunity
↓
Canovia Internal Prototype
↓
Premium / Pro Feature
↓
Real User Validation
↓
Standalone Signal
↓
Official App Candidate
↓
Spin-out
↓
reconnect as Execution Provider
```

The precise commercial tier used for validation is a future product decision.

---

## 7. Standalone signals

Potential evidence for spin-out:

- high usage frequency
- dedicated UI required
- strong retention
- search / acquisition demand
- independent monetization
- value exists even without Canovia Core
- keeping it in Core would create product bloat

No single signal is sufficient automatically.

---

## 8. First-party / Partner decision

Use the Platform/Ecosystem criteria.

### Prefer Partner when

- high-quality provider exists
- external execution is sufficient
- data contract can meet Canovia needs
- Canovia does not need deep domain-specific ownership

### Consider First-party when

- unique Canovia Context creates strong advantage
- external provider cannot expose required data
- dedicated high-frequency UX is necessary
- standalone demand exists
- product can validate platform contracts
- strategic moat is meaningful

Human decision required.

## 13. Builder / Reviewer / Governor

A future creation system may separate roles:

### Builder

- specification implementation
- bounded code changes
- tests

### Reviewer

- independent correctness review
- spec consistency
- evidence interpretation

### Governor

- policy-based approval boundary
- Auto / Human Review / Reject

No single agent should silently own the full consequential decision chain.

## 19. Strategy is not Product Requirement

Past discussion may include a multi-year goal of growing Canovia into an independent business option.

This belongs to Strategic Context, not runtime requirements.

The useful direction is:

> build enough repeatability, revenue, validation, and operational independence that independence becomes an option.

No date automatically creates engineering requirements.

---

## 20. Promotion criteria for a new product

Before spin-out, require explicit evidence around:

- user problem
- usage frequency
- retention
- provider alternatives
- Canovia synergy
- standalone value
- acquisition path
- monetization hypothesis
- support / maintenance cost
- data/privacy boundary
- product owner approval

An AI score must not auto-create a company/product.

---

## 21. Current Architecture Gaps

Missing before a Product Creation System can be claimed:

- Product Intelligence / Product Memory
- stable Platform contracts
- explicit Opportunity model
- Incubation records
- value-hypothesis contract
- product candidate comparison
- cross-product identity/context
- partner/provider governance
- mature implementation orchestration
- human approval policy
- release/measurement lineage

These are architecture gaps, not implementation defects.

---

## 22. Recommended promotion sequence

1. use Canovia development process as internal dogfooding
2. mature current Living Specification / Development orchestration
3. establish Product Intelligence basics
4. preserve Hypothesis / Decision Memory
5. create manual Opportunity Board
6. validate one internal prototype via explicit Incubation record
7. define standalone signal based on real data
8. spin out only after evidence
9. reconnect first-party spin-out through shared Platform contracts
10. productize proven internal system as Developer Pro only after repeatability
