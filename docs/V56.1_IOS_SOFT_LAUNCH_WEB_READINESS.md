# V56.1 iOS Soft Launch Web Readiness

## Goal

V56.1 closes Web-side App Store blockers for the first Canovia iOS Soft Launch.

This phase does not redesign Canovia or add new product features.

Scope:

1. public Privacy Policy surface
2. public Support surface
3. in-app account deletion
4. deletion of owned Canovia content and uploaded files
5. App Store metadata URLs that remain stable on the Web origin

The iOS shell remains:

```text
SwiftUI
→ WKWebView
→ Canovia Web / Laravel
```

Authentication and business state remain Web-owned.

## Apple review constraints

For Soft Launch readiness, Canovia must satisfy the current App Store requirements that:

- apps supporting account creation also provide account deletion in-app
- a Privacy Policy URL is provided in App Store Connect and is accessible in-app
- a Support URL leads to a real support/contact surface

V56.1 implements the product-side surfaces. App Store Connect metadata entry remains a release operation.

## Public routes

New public routes:

```text
GET /privacy
GET /support
```

Both pages must work without authentication.

### Privacy

The Privacy page explains, at minimum:

- account data
- Plan / Task / user-entered content
- uploaded images / files
- usage / diagnostics data
- AI processing when AI features are used
- external integration metadata when connected by the user
- retention / deletion
- contact path

The page does not claim that Canovia collects no data.

### Support

The Support page provides:

- current beta / soft-launch context
- a direct feedback form using the existing Feedback endpoint
- configured support email when available
- links to Privacy and account controls

The support email comes from:

```text
CANOVIA_SUPPORT_EMAIL
```

Soft Launch release checklist must treat a missing support email as a release blocker.

## Account deletion

Authenticated route:

```text
DELETE /account
```

The Account page exposes the destructive action directly.

Deletion requires:

- current password
- re-entry of the account email
- explicit destructive submit

The feature deletes the account rather than merely deactivating it.

## Data deletion boundary

Deleting the User row alone is insufficient because many Canovia records intentionally use `nullOnDelete()` to preserve collaborative / guest-compatible history.

V56.1 therefore:

1. identifies Plans owned by the user
2. gathers owned/private upload paths before database deletion
3. deletes owned Plans first so Plan-scoped Task / Study / Career / Evidence data cascades
4. deletes user-authored records that may exist outside owned Plans or on shared Plans
5. deletes the User
6. removes gathered private files from Storage
7. invalidates the authenticated session

### Owned Plans

All Plans with:

```text
plans.user_id = deleting user
```

are deleted.

This intentionally deletes the user's Plan-scoped:

- Tasks
- Work Sessions / Logs
- Study Practice
- Study Recall
- Study Scope Capture
- Career data
- Task Evidence
- Intelligence state attached to those Plans
- Plan resources / artifacts
- execution records that cascade from Plan/Task

### Standalone / shared-context user records

User-owned rows that can survive Plan deletion through nullable FKs are explicitly removed where applicable, including:

- Inbox
- Feedback
- Native AI runs
- Goal Context / discovery messages
- Study Practice attempts / sessions authored by the user
- Study Recall reviews / sources authored by the user
- Task Evidence authored by the user
- Guided Executions
- Practice Question Demand
- Intelligence snapshots / traces / reasoning / projections
- Execution Activities
- roadmap support / PWA handoff / session state

Records with database-level cascade from `users` can continue using the cascade.

## Uploaded files

Before DB deletion, V56.1 gathers private Storage paths for:

- Inbox files
- Study Recall source files
- Career Capture screenshots

including paths attached to owned Plans.

After the database transaction succeeds, these files are removed from private Storage.

If a Storage path is missing, deletion continues.

## Collaborative Plans

Deleting one user must not delete a Plan owned by another user.

The user's membership / user-authored records are removed, while the other owner's Plan survives.

## Authentication / security

- account deletion requires an authenticated session
- current password must match
- confirmation email must match the current account email exactly, case-insensitive after trim
- CSRF protection remains standard Laravel Web protection
- no deletion endpoint exists on the unauthenticated API surface

## UX

Account page adds:

- Privacy
- Support
- Delete account

Deletion copy must clearly state:

- owned Plans and associated history are deleted
- this operation cannot be undone
- collaboration content owned by others is not deleted as an entire Plan

No dark pattern or multi-screen retention flow is added.

## Non-goals

V56.1 does not implement:

- App Store submission automation
- App Icon binary asset
- subscription purchase
- Sign in with Apple
- social login
- data export
- delayed/manual deletion queue
- legal advice or region-specific legal drafting
- iOS-native account settings UI

## Validation

Required tests:

1. Privacy / Support are public.
2. Account page links to Privacy / Support / deletion.
3. Wrong password cannot delete the account.
4. Wrong confirmation email cannot delete the account.
5. Valid deletion removes the User.
6. User-owned Plans are deleted.
7. Another user's Plan survives.
8. user-owned standalone rows are deleted.
9. private uploaded files are deleted.
10. session is logged out after deletion.

## iOS relationship

The iOS shell uses these Web routes directly.

App Store Connect targets:

```text
Privacy Policy URL: <Canovia canonical origin>/privacy
Support URL:        <Canovia canonical origin>/support
```

The exact production origin remains deployment configuration and is not hard-coded by this spec.
