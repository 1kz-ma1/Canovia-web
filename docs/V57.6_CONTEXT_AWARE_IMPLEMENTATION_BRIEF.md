# V57.6 Context-aware Implementation Brief

## Goal

V57.6 converts the bounded V57.4 Development Execution Context into a concrete
implementation / review / validation brief for the current Developer Action.

Canonical flow:

```text
Development Adaptive Action
+ target Task
+ V57.4 task-scoped GitHub context
→ deterministic Implementation Brief
→ human / coding-tool handoff
→ existing execution / GitHub / gate flows
```

The brief answers:

- what exactly is the current Task?
- which Repository / Branch / PR is in scope?
- what GitHub state is already known?
- what should be done next?
- what proves the Action is done?
- what must not be inferred or mutated automatically?

## Authority boundary

V57.6 is a presentation / handoff projection.

It does not become a second decision engine.

The existing Development Adaptive Action remains authoritative for:

- next Action
- intent
- target Task
- Release Gate
- success signals

V57.4 remains authoritative for bounded task-scoped GitHub context.

V57.6 only transforms those two inputs into an actionable brief.

## No remote read / no AI on GET

Developer Home GET still performs no GitHub or AI call for the brief.

The brief reads only:

- current ActionProposal
- selected Task
- persisted V57.4 execution context
- persisted GitHub Evidence already projected into that context

It does not:

- fetch source code
- fetch diff / patch
- fetch PR body
- fetch Issue body
- fetch Review body
- call an LLM
- write to GitHub
- change Task state
- persist a new brief row

## Brief modes

The Action kind is mapped deterministically to one of these brief modes:

- implementation
- CI triage
- review
- merge
- deploy
- verification
- spec sync
- evidence connection
- release
- generic continuation

Each mode produces a short task-scoped checklist.

Examples:

```text
development_fix_ci
→ CI TRIAGE BRIEF
→ identify failing CI on current PR/head SHA
→ fix inside Task scope
→ rerun CI
→ confirm CI success Evidence
```

```text
development_review_fix
→ REVIEW BRIEF
→ inspect latest review on GitHub
→ apply only Task-scoped changes
→ update the current PR
→ re-observe Review state
```

Canovia intentionally does not store Review body text in order to generate this
brief. The user opens GitHub when provider text is needed.

## Known State

The brief may expose bounded facts already present in V57.4:

- Repository
- Branch
- short Commit SHA
- PR number / state / draft
- CI state
- Review state / reviewer
- Issue number / state
- Deploy environment / status / production flag

Unknown facts remain unknown.

## Done When

The brief reuses the Action / Handoff success signals.

It does not invent a new completion definition.

If no explicit signal exists, fallback guidance is only:

> update the target Task Evidence and let Development Intelligence recalculate
> the next Action.

## Copy-ready handoff

Developer Home exposes a copy-ready text brief.

It is intended for:

- the developer themself
- an IDE assistant
- an external coding agent
- a review assistant

The handoff contains only bounded context:

- Action / objective
- Task
- Repository / Branch / PR identifiers
- known GitHub state
- deterministic steps
- done-when signals
- guardrails

It excludes provider bodies and source material.

Copying a brief does not authorize or trigger a coding agent.

## Guardrails

Every brief preserves these boundaries:

- unknown GitHub facts are not guessed
- Task progress / status / remaining time are not changed by the brief
- GitHub writes stay behind existing entitlement / installation / human
  confirmation boundaries
- source code / diff / PR body / Issue body are not persisted in the brief

## Developer Home UI

The V57.4 Action Context remains visible first.

V57.6 adds directly below it:

```text
IMPLEMENTATION / CI / REVIEW ... BRIEF
→ objective
→ HOW TO PROCEED
→ KNOWN STATE
→ DONE WHEN
→ copy-ready handoff
→ guardrails
```

This keeps the daily flow:

```text
Next Action
→ understand target context
→ know exactly how to proceed
→ execute
→ collect Evidence
→ recalculate
```
