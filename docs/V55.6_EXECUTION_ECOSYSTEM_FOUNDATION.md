# V55.6 Execution Ecosystem Foundation

## Goal

V55.6 introduces the minimum internal domain foundation for the future Canovia Execution Ecosystem.

The product direction is:

```text
Goal / Plan / Current Action
→ decide what should be executed
→ select the best execution provider
→ execute in Canovia or an external application
→ receive factual activity
→ project it into Task Evidence
→ reuse existing Intelligence / Replan
```

V55.6 does **not** expose a Marketplace, Developer Portal, external OAuth platform, public Activity API, or provider picker UI.

The existing user experience remains unchanged.

## Architecture

The canonical layering after V55.6 is:

```text
Workspace / Intelligence
        ↓
Current Action / Task
        ↓
Execution Mode
        ↓
Execution Capability
        ↓
Execution Resolver
        ↓
Execution Provider
        ↓
Operation Surface
        ↓
ExecutionActivity
        ↓
TaskEvidence
        ↓
Existing Intelligence / Replan
```

### Existing responsibilities remain authoritative

Workspace Mode:

```text
domain state / Readiness / Gap / Decision / Current Action
```

Execution Mode:

```text
study / development / career / general
→ execution family for the selected Task
```

Execution Capability:

```text
what operation the Task requires
```

Execution Provider:

```text
which implementation performs that operation
```

V55.6 does not replace `ExecutionModeService`.


## Execution Provider Catalog

V55.6 uses a code-defined provider registry behind the `ExecutionProviderCatalog` interface.

Initial providers:

```text
canovia.study.practice
  kind: native
  capability: study.practice

canovia.study.recall
  kind: native
  capability: study.recall

canovia.study.resource
  kind: native
  capability: study.resource

canovia.development
  kind: native
  capability: coding.repository

github
  kind: external
  capability: coding.repository

canovia.general
  kind: native
  capability: general.task
```

The catalog is intentionally not database-backed yet.

Future published external providers can be composed behind the same interface without changing resolver consumers.

## Plan Execution Preference

Table:

```text
plan_execution_preferences
```

Fields:

- plan_id
- capability
- provider_key
- user_selected
- timestamps

Constraint:

```text
unique(plan_id, capability)
```

V55.6 only establishes Plan-level preference.

Future precedence may extend to:

```text
Task override
→ Plan preference
→ User default
→ Resolver default
```

but those additional scopes are not implemented now.

## Execution Resolver

`ExecutionResolver` is deterministic.

Current order:

```text
1. Valid Plan preference
   → selected provider

2. Enabled Native provider
   → Native default

3. No Native provider
   → preserve current execution fallback
```

External providers are **never selected merely because they exist in the catalog**.

For `coding.repository`, both Canovia Native and GitHub are registered, but the default remains:

```text
canovia.development
```

GitHub is used only after an explicit saved preference exists.

No recommendation ranking, sponsored signal, monetization signal, or AI scoring enters the resolver.

## ExecutionActivity

A new provider-neutral Activity intake model is introduced.

Table:

```text
execution_activities
```

Core fields:

- user_id / actor_token
- provider_key
- capability
- external_key
- type
- title
- status
- started_at / completed_at
- duration_seconds
- metrics
- metadata
- nullable plan_id / task_id
- nullable task_evidence_id
- linked_at

Supported statuses:

- started
- completed
- interrupted
- failed
- cancelled

### Activity can exist before Task linkage

This is intentional.

External providers should not need to understand Canovia Plan / Task structure.

```text
Provider
→ normalized ExecutionActivity
→ Canovia linking
→ TaskEvidence
```

### Idempotency

When `external_key` exists:

```text
provider_key + external_key
```

is unique.

Repeated provider delivery updates the same Activity instead of creating duplicates.

Provider integrations must therefore use a stable provider-scoped external identifier.

## ExecutionActivity != TaskEvidence

This separation is a V55.6 architectural rule.

`ExecutionActivity` answers:

> What did an execution provider report?

`TaskEvidence` answers:

> What factual observation is now attached to this Canovia Task?

Current `TaskEvidence` requires a Plan and Task, so it cannot be the raw external intake model.

The flow is:

```text
ExecutionActivity
→ explicit Task link
→ ExecutionActivityProjector
→ TaskEvidence
→ TaskEvidenceAdapter
→ normalized Intelligence Evidence
```

## Activity → Evidence projection

`ExecutionActivityProjector` is introduced as an interface.

The V55.6 implementation projects linked Activities through the existing `TaskEvidenceService`.

Generic Evidence type:

```text
execution_activity_observed
```

Evidence metadata contains only normalized Activity facts:

- execution_activity_id
- provider_key
- capability
- activity_type
- activity_status
- title
- duration_seconds
- metrics

The Activity `metadata` payload is **not copied** into TaskEvidence.

Therefore provider trace/private payload data does not cross automatically into Intelligence.

Source mapping:

```text
Native Provider
→ EvidenceSource::Native

External Provider
→ EvidenceSource::External
```

Projection external key:

```text
execution-activity:{activity_id}
```

Repeated linkage is idempotent.

## Progress / Intelligence safety

V55.6 never changes Task progress or Task status from ExecutionActivity.

```text
Activity received
≠ progress updated

Activity completed
≠ Task completed
```

The generic `execution_activity_observed` type currently has no additional allowlisted domain facts in `TaskEvidenceAdapter`.

Therefore the foundation does not alter Study / Development / Career readiness calculations.

Future domain integrations must add explicit normalized Evidence semantics before Activity metrics can affect Intelligence.

## Existing architecture reused

V55.6 reuses rather than duplicates:

- `ExecutionModeService`
- `StudyActivityPolicyService`
- `ExecutionActionPolicyService`
- `TaskEvidenceService`
- `TaskEvidenceAdapter`
- existing Study Intelligence

The existing `ExecutionAdapter` contract is retained unchanged as the older external-environment-to-Evidence seam.

## UI boundary

No visible UI is added in V55.6.

Do not change:

- Plan creation redirect
- Study Workspace onboarding
- Development Workspace onboarding
- Career Workspace onboarding
- `/navigate` provider UI
- Current Action CTA
- current specialized destination routes
- Timer fallback

Execution Setup will be validated in a later version only where a real provider choice exists.

The intended UX remains:

```text
Planning / setup
→ choose only when meaningful

Normal execution
→ one Start action
→ stored/default provider resolves automatically
```

## Database impact

New tables:

- `plan_execution_preferences`
- `execution_activities`

No existing column is modified.

No existing Plan / Task requires backfill.

Deleting a Plan removes its execution preferences.

Activity Plan / Task / Evidence links use nullable foreign keys so provider activity facts can remain independently attributable to the actor if a linked planning object is removed.

## Runtime / cost boundary

V55.6 adds:

- no AI traffic
- no external provider request
- no GitHub request
- no new GET-page provider query
- no visible UI
- no automatic progress mutation

The new resolver/activity services only run when explicitly invoked.
