# V57.8 Opt-in Coding Agent Handoff

## Goal

V57.8 connects the V57.6 Development Implementation Brief to the existing
Execution Orchestration boundary without introducing a second agent runtime.

Canonical flow:

```text
Development Adaptive Action
+ Task-scoped Execution Context
+ V57.6 Implementation Brief
→ explicit user confirmation
→ canonical Execution Request
→ existing Execution Orchestration
→ external Coding Agent prompt
→ user copies / sends it
→ implementation result
→ existing GitHub / Provider return path
→ Evidence
→ Development Intelligence
```

The central rule is:

> Canovia prepares an execution context. It does not silently start an agent.

## Reuse over duplication

V57.8 deliberately reuses:

- `ExecutionRequestHandoffService`
- `ExecutionOrchestrationContextService`
- `ExecutionPacketService`
- existing session-scoped Execution Request state
- existing external-AI prompt handoff
- existing Execution GitHub Handoff / GitHub Return Evidence
- existing ProviderConnection / Activity intake foundation for future real
  connected providers

It does not create:

- a second execution packet model
- a second provider registry
- a Development-only provider connection table
- a Coding-Agent-specific activity model
- a new GitHub return pipeline

## Why no fake Codex provider

The current ProviderConnection architecture is ready for real external
providers, but Canovia does not yet have a provider-specific Codex / Claude /
Gemini coding-agent connection contract.

V57.8 therefore does **not** register a pretend provider whose only behavior is
copying text.

The current concrete handoff is:

```text
confirmed Implementation Brief
→ existing external Execution Orchestration prompt
→ user-selected coding tool
```

When a real provider integration exists, the existing
`ProviderConnection + execution_context + signed Activity return` boundary can
be used without changing the Development Brief contract.

## Human confirmation

Developer Home exposes a dedicated:

```text
Coding Agentへ引き継ぐ
```

surface.

Submission requires a checked confirmation stating that the user understands:

- current Task scope
- completion criteria
- only Context preparation happens now
- agent execution has not started
- GitHub write has not started
- merge has not happened
- deploy has not happened

The POST route is the approval boundary.

## Canonical Execution Request

The confirmed Development Brief is converted through
`ExecutionRequestHandoffService`.

New source type:

```text
development_implementation_brief
```

The request records bounded source metadata:

- brief version
- brief mode
- Development Action kind
- title
- SHA-256 brief hash

The confirmed instruction is the V57.6 copy-ready brief.

The brief already excludes:

- source code
- diff / patch
- PR body
- Issue body
- Review body

## External actor

The handoff uses the existing Execution actor:

```text
external
```

and dispatch label:

```text
Coding Agent
```

No Native AI request is needed to prepare the handoff.

## Existing Execution Context

After confirmation, V57.8 builds the normal
`ExecutionOrchestrationContextService` snapshot.

Therefore the Coding Agent prompt inherits existing boundaries:

- Plan
- selected Task
- Dependency state
- blockers
- available inputs
- protected scope
- confirmed constraints
- known unknowns
- recent bounded Evidence
- confirmed Execution Request

The Development Brief does not replace these canonical constraints.

## Session state

V57.8 stores only the normal session-scoped Execution Orchestration state:

- context fingerprint
- external actor
- optional available minutes
- confirmed Execution Request
- generated external handoff prompt
- small handoff marker / brief hash

It does not create a DB handoff record.

The handoff becomes stale under the existing context fingerprint rule if
canonical Plan / Task context changes.

## V57.7 Provider Triage relationship

Provider-linked Review bodies / inline comments / CI annotations from V57.7
remain transient.

When the user leaves the Triage page for Coding Agent Handoff:

```text
V57.7 transient provider detail
X automatic session persistence
X automatic handoff persistence

V57.6 bounded Implementation Brief
→ rebuilt server-side
→ Execution Request
```

The Triage page still offers its explicit copy action if the user personally
wants to share provider text with a coding tool.

This preserves the V57.7 response-only provider-text boundary.

## Execution Orchestration UX

The existing CONFIRMED EXECUTION REQUEST panel now recognizes the source:

```text
Developer Homeで確認したImplementation Briefを引き継いでいます
```

The normal EXTERNAL AI HANDOFF surface remains authoritative for:

- prompt copy
- external tool use
- returned Execution Packet JSON import

V57.8 does not add a parallel handoff screen.

## Result return

V57.8 does not invent a new result protocol.

If implementation produces GitHub changes:

```text
Branch / Commit / Pull Request
→ existing GitHub App observation
→ GitHub Return Evidence
→ TaskEvidence
→ Development Intelligence
```

If a future authenticated external Coding Agent uses ProviderConnection:

```text
ProviderConnection
→ execution_context
→ signed ExecutionActivity
→ TaskEvidence
```

Both are existing Canovia boundaries.

## Safety

V57.8 does not automatically:

- invoke a Coding Agent
- send content to a third party
- create a GitHub branch
- create a Commit
- create a Pull Request
- merge
- deploy
- change Task progress
- change Task status
- change remaining minutes
- mark a Release Gate complete

GitHub write continues to use the existing explicit write authority.

## Compatibility

V57.8 preserves:

- V46.x GitHub write / return authority
- V47.x Execution Orchestration / Distribution
- V55.6 Execution Ecosystem
- V55.9 ProviderConnection / authenticated Activity intake
- V57.1–V57.5 Developer state / GitHub foundation
- V57.6 Context-aware Implementation Brief
- V57.7 transient Provider-linked Triage

## Next

The next real automation step should require one concrete provider integration,
not another generic abstraction.

Candidate:

```text
real coding provider
→ provider-specific connection / launch
→ existing ProviderConnection
→ confirmed Development Execution Request
→ execution_context
→ provider Activity / GitHub PR return
→ Evidence
```

Until then, the copy-based external Coding Agent handoff is the truthful
product boundary.
