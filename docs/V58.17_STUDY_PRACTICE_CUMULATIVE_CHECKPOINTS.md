# V58.17 Study Practice 50 / 100 Cumulative Checkpoints

Status: implemented / validated  
Branch: `feature/v58-17-practice-cumulative-checkpoints`

## 1. Goal

Expose cumulative 50 / 100 question checkpoints across the current Study Practice Task while preserving the existing 10-question Session contract.

```text
assessed Practice Attempts on current Task
→ normalized graded question events
→ 50-question checkpoint
→ 100-question checkpoint
→ Practice UI
```

V58.17 is analysis only. It does not change Practice routing authority.

## 2. Scope

Checkpoint counting is limited to:
- current Plan
- current Task
- current actor
- assessed Study Practice Attempts

All current Practice providers are supported when assessment feedback is structurally valid.

## 3. Authoritative graded event

A question counts only when `assessment.question_feedback` contains:
- non-empty `question_id`
- `correctness` in `correct / partial / incorrect`

The same `question_id` is counted at most once inside one Attempt.

Top-level Attempt score, strengths, weaknesses, draft answers, and prepared Sessions do not create question count.

## 4. Provider-neutral volume

Question Bank, Hybrid, Native AI, and external-AI assessed questions may all contribute to cumulative volume.

AI-generated questions without a durable Question Bank id are counted as graded question events, but V58.17 does not invent uniqueness for them.

## 5. Question Bank repeat diagnostics

When a linked StudyPracticeSession provides a numeric Bank `question_id` for the feedback `question_ref`, V58.17 also records:
- Bank question exposure count
- unique Bank question count
- repeated Bank exposure count

Repeated Bank questions still count as solved question volume, while unique Bank count stays stable.

## 6. Checkpoint snapshots

Milestones are fixed at 50 and 100 graded questions.

When reached, each checkpoint is calculated over the first N valid question events in chronological order and returns:
- correct count
- partial count
- incorrect count
- observed correct rate
- reached_at
- reaching Attempt id

Observed correct rate is `correct / total`; partial is not counted as correct.

Because the snapshot always uses the first N events, later Practice does not alter the historical 50-question result.

## 7. Current progress

The projection also returns:
- assessed_question_count
- current correct / partial / incorrect
- current observed correctness
- next_checkpoint = 50 / 100 / null
- questions_to_next_checkpoint
- complete when >=100

## 8. History bound

Read at most the oldest 500 Attempts for the current Task / actor.

This preserves the first 50 / 100 checkpoint history while preventing an unbounded read.

If more than 500 Attempts exist, `history_truncated=true` is surfaced. V58.17 does not claim an exact post-500 Attempt lifetime question total.

## 9. Practice UI

A `CUMULATIVE CHECKPOINT` block is rendered near Practice Strategy.

Before 50:
```text
32 / 50問
次のCheckpointまであと18問
```

After 50:
- the frozen 50-question result remains visible
- progress continues toward 100

After 100:
- both 50 and 100 snapshots are visible
- `100問達成` is shown

Question Bank provenance, when available, is displayed as unique count plus repeated exposure count.

## 10. Authority boundary

V58.17 does not modify:
- StudyPracticeStrategyService
- StudyWeaknessPrioritizationService
- StudyExamConvergencePolicyService
- StudyPracticeRoutingPolicyService
- Task progress / completion
- Study Intelligence mastery
- Study Method Recommendation

V58.17 itself does not change routing. V58.18 now reads the `>=100` checkpoint as one eligibility gate for a separate bounded Plan-wide weakness handoff policy.

## 11. Clock determinism fix

Validation exposed that `StudyExamDateService::daysUntil()` used `new DateTimeImmutable()` directly and therefore ignored Laravel/Carbon's application test clock.

V58.17 changes only the clock source to `now()` before converting to DateTimeImmutable.

Production semantics remain current application time; tests can now freeze time deterministically.

## 12. Provider / storage boundary

DB-only, deterministic, read-only.

No provider call. No migration.

## V58.18 checkpoint consumer update

Reaching 100 graded questions still does not automatically start weakness reinforcement or complete the Task.

V58.18 uses the 100-question checkpoint only as one prerequisite. Plan-wide AP parent-topic evidence must independently satisfy >=3 exposures, >=2 unique Bank questions, and <60% observed correctness, and the current Task must still be broad General Practice.

See `docs/V58.18_PLAN_WIDE_WEAKNESS_HANDOFF.md`.
