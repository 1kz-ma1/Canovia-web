# V46.0 GitHub Workflow Hub

## Goal

GitHubのBranch / Pull Request / Issue / Review / Actionsといった構造を、
そのままCanoviaのUIへ持ち込まない。

ユーザーが知りたいのはGitHubのobject hierarchyではなく、

- 今やる
- レビュー待ち
- 修正必要
- マージ待ち
- 完了

のどこにあるか、次に何をするか。

V46.0では既存PlanArtifactをsource of truthとして、
GitHub Artifactをこの5レーンへ再投影する。

## Important boundary

V46.0はGitHub API / OAuth / Webhookを導入しない。

そのためCanoviaが自動断定しないもの:

- PR open / closed
- merged
- review requested
- approved / changes requested
- CI success / failure
- branch freshness
- merge conflict
- GitHub assignee

URLから判定してよいのはURL自体に明示された構造だけ:

- Repository
- Pull Request number
- Issue number
- Commit
- Actions run number
- Branch path

この構造判定はremote status判定ではない。

## User-facing workflow

PlanArtifact.metadataに:

`github_workflow_state`

を持てる。

allowed values:

| State | UI |
| --- | --- |
| now | 今やる |
| review | レビュー待ち |
| changes | 修正必要 |
| merge | マージ待ち |
| done | 完了 |

これはGitHub remote stateではなく、
Canovia上でユーザーが明示した「今どう扱うか」。

既存GitHub Artifactでstateがないものは
自動分類せず「未整理」に置く。

PR URLだからreviewへ自動移動しない。

## GitHub Workflow Hub

route:

`/github-workflow`

全閲覧可能PlanのGitHub Artifactを集約する。

表示:

- Total
- 今やる
- レビュー待ち
- 修正必要
- マージ待ち
- 完了
- 未整理

Plan filterを持つ。

### Card

GitHubの複雑なmetadataを全部表示しない。

Cardで優先するもの:

- Repository
- object kind
- PR / Issue等のreference
- Artifact title
- Plan
- linked Task
- assigned user
- Canovia workflow state

Action:

- GitHubで開く
- Artifact詳細
- Canovia workflow state変更

## Quick Capture

HubからGitHub URLを貼るだけでPlanArtifactを作成できる。

input:

- Plan
- GitHub URL
- initial Canovia state
- optional title

title未指定時はURL structureから生成する。

例:

```text
https://github.com/1kz-ma1/Canovia/pull/456
→ 1kz-ma1/Canovia · PR #456
```

Quick Captureでremote APIは呼ばない。

Task / assignee / notesは既存Artifact詳細から追加できる。

## Parser

`GitHubWorkflowService::parseUrl()`

recognizes:

- `/{owner}/{repo}`
- `/{owner}/{repo}/pull/{number}`
- `/{owner}/{repo}/issues/{number}`
- `/{owner}/{repo}/commit/{sha}`
- `/{owner}/{repo}/actions/runs/{id}`
- `/{owner}/{repo}/tree/{branch...}`

github.com以外はQuick Captureで拒否する。

Repository名やPR番号をparseしても
GitHubへnetwork requestはしない。

## Persistence

新DB table / migrationは追加しない。

既存:

`plan_artifacts.metadata`

を利用する。

GitHub providerから別providerへArtifactを変更した場合は、
staleな`github_workflow_state`を削除する。

通常Artifact更新でproviderがGitHubのままなら
workflow stateは保持する。

## Evidence boundary

GitHub Workflow lane変更はTask Evidenceではない。

例:

`review -> changes`

はユーザーの整理操作であって、
GitHubから取得した「changes requested」という証拠ではない。

そのためlane変更時にTaskEvidenceを作らない。

GitHub URLを新規Artifactとして登録し、
Taskへ明示linkした場合は既存Artifact登録Evidence contractを利用できる。

将来authoritative GitHub connectorから取得したeventは
EvidenceSource::GitHubとして別境界で記録する。

## Permission

既存PlanOwnershipServiceを利用する。

owner / editor:
- item閲覧
- workflow state変更
- quick capture

viewer:
- item閲覧
- state変更不可

他ユーザーのprivate Plan ArtifactはHubへ出さない。

## Navigation

Desktop:
- Header secondary actionにGitHub

Mobile:
- 新しいBottom Tabは追加しない
- Roadmap section配下として扱う
- Roadmapの選択PlanからPlan-filtered GitHub Hubへ移動

Artifact page:
- GitHub Workflow shortcutを追加
- Artifact cardにanchorを付与
- GitHub workflow state badgeを表示

これによりモバイルNavigationを増やさずGitHub管理へ到達できる。

## Monetization boundary

Manual GitHub Workflow Hubは既存ProjectArtifact能力の延長として扱う。

将来の:

- GitHub OAuth
- automatic PR / commit Evidence
- Webhook
- CI status ingestion
- automated workflow state suggestion / synchronization

は既存`developer_github_evidence` capabilityへ接続可能。

「努力するための管理UI」は閉じず、
外部取得・自動同期による摩擦削減を高コスト能力として分離できる。

## Non-goals

V46.0では行わない:

- GitHub OAuth
- Personal Access Token入力
- live API polling
- Webhook
- PR作成
- branch作成 / 削除
- merge操作
- review submission
- CI rerun
- automatic workflow state changes
- automatic progress update

## Next

V46.1以降でauthoritative GitHub connectionを入れる場合も、
UIはこのWorkflow Hubを継続利用する。

Connector dataは生のGitHub objectを増やすためではなく、

```text
GitHub authoritative facts
       ↓
Canovia normalization
       ↓
今やる / レビュー / 修正 / マージ / 完了
```

へ変換するために使う。
