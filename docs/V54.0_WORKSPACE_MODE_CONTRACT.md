# V54.0 Workspace Mode Contract

## Goal

V54 begins the UI shift from one general-purpose surface toward specialized Workspaces without splitting Canovia into separate products.

The Workspace Mode layer sits above the shared Canovia Intelligence core:

```text
Canovia Core
State / Evidence / Readiness / Decision / Action
                    ↓
          Intelligence Presentation
                    ↓
             Workspace Mode
        ↙             ↓             ↘
    Overview         Study      Development
```

V54.0 defines the Mode contract only.

It deliberately does **not** render the fixed dropdown yet and does **not** persist a user's manual Mode selection yet.

Those belong to V54.1 and V54.2.

## Mode is not Plan category

Canovia already has broader Plan category profiles:

- study
- development
- career
- creative
- general

Workspace Modes are intentionally narrower.

Current public Modes:

- overview
- study
- development

Current mapping:

```text
study       → Study Workspace
development → Development Workspace
career      → Overview
creative    → Overview
general     → Overview
```

Career / Creative / General remain valid Canovia Plans. They are not reclassified or removed.

A future dedicated Workspace can be introduced by registering another Mode rather than rewriting every global navigation surface.

## WorkspaceMode

`App\Enums\WorkspaceMode`

V54.0 values:

- `overview`
- `study`
- `development`

These keys are stable UI/context identifiers.

They are not billing products and are not Intelligence domains by themselves.

## WorkspaceModeDefinitionData

Each public Mode owns a definition:

- key
- user-facing label
- semantic icon key
- description
- accent tone
- home strategy
- supported Plan profile keys
- navigation semantic keys
- empty-state title
- empty-state description
- empty-state action key

The definition intentionally stores semantic keys rather than hard-coded Blade fragments.

Example:

```text
Study
├ supported profile: study
├ navigation
│  ├ current_action
│  ├ readiness
│  ├ study_scope
│  ├ practice
│  ├ recall
│  └ history
└ empty action: capture_study_scope
```

Development:

```text
Development
├ supported profile: development
├ navigation
│  ├ current_action
│  ├ release_readiness
│  ├ github
│  ├ evidence
│  └ history
└ empty action: connect_github
```

V54.1+ can map these semantic keys to actual routes/components without changing the Mode registry contract.

## WorkspaceModeRegistry

`App\Services\WorkspaceModeRegistry`

The registry is the single public catalog of Workspace Modes.

Public order in V54.0:

1. Overview
2. Study
3. Development

The fixed Mode dropdown must consume this registry rather than hard-code its options in Blade.

This is the key future-expansion rule:

> Adding a public Workspace Mode should begin in the registry, not in every header template.

The registry can answer:

- all public Mode definitions
- default Mode
- definition for a Mode
- dedicated Mode for a Plan profile
- whether a profile currently has a dedicated Mode
- stable public Mode keys

## WorkspaceModeContextData

Resolved UI context contains:

- current Mode
- resolution source
- related Plan ID when available
- Plan profile key when available
- route name

Resolution source values:

- explicit
- route_hint
- plan_profile
- default

V54.0 defines `explicit` as the highest-precedence input for the resolver, but does not persist it.

V54.2 will implement user preference persistence.

## WorkspaceModeResolver

`App\Services\WorkspaceModeResolver`

Current precedence:

```text
explicit Mode passed by caller
        ↓
strong domain route hint
        ↓
current Plan profile
        ↓
Overview fallback
```

This prepares the later final precedence:

```text
persisted user choice
> explicit current navigation choice
> unambiguous current Plan/deep-link context
> Overview
```

without implementing persistence prematurely.

## Strong route hints

Some routes identify the Workspace even when no Plan route parameter is available.

Study examples:

- Study Scope
- Study Adaptive Action
- Study Activity
- Study Practice
- Study Recall

Development examples:

- GitHub Workflow
- Development Readiness confirmation
- GitHub-specific Execution Orchestration routes

A generic Plan/Task/WorkSession route instead resolves through the related Plan's category profile.

## Plan / Task / WorkSession context

The resolver can obtain Plan context from:

- route-bound Plan
- route-bound Task → Plan
- route-bound WorkSession → Plan / Task → Plan

This allows later fixed headers to show the correct automatic Workspace context across detail and execution screens.

## Overview semantics

Overview is not a third specialist product.

It is the fallback and cross-Mode command surface.

Its V54 role is intentionally thin:

- overall Current Action
- Mode summaries
- Inbox
- timeline / important cross-Mode changes

Detailed Study or Development workflows belong inside their dedicated Workspaces.

## Study semantics

Study Mode is a specialized view of the shared Intelligence core.

User-facing language should emphasize:

- exam
- scope
- practice
- recall
- mastery
- retention
- readiness

rather than exposing Task mechanics as the primary model.

Primary empty-state action:

`capture_study_scope`

## Development semantics

Development Mode is a specialized view of the shared Intelligence core.

User-facing language should emphasize:

- release
- implementation
- CI
- review
- merge
- deploy
- verification
- specification sync
- GitHub Evidence

Primary empty-state action:

`connect_github`

## What V54.0 does not do

V54.0 does not:

- render a Mode dropdown
- create a new top header
- persist a selected Mode
- add a User DB preference column
- auto-switch the browser after opening a Plan
- create Study / Development Workspace Home pages
- change V53 Intelligence calculations
- change Task progress
- change Plan category
- introduce new AI requests
- create Premium / Free differences
