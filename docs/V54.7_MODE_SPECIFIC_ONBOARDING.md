# V54.7 Mode-specific Onboarding

## Goal

V54.7 adds first-use guidance for specialized Workspace Modes without creating another persistent onboarding system.

The global First-run Gate remains responsible for introducing Canovia itself.

Mode-specific onboarding is responsible only for answering:

```text
What must exist before this Workspace becomes useful?
What is the next setup action?
When should setup guidance disappear?
```

The guidance is derived from real domain state and automatically disappears when the Mode has enough Evidence to operate.

## Principles

- no new onboarding-completed column
- no dismiss / skip state
- no localStorage duplication
- no modal
- no forced tour
- no AI call
- no GitHub provider call on Workspace GET
- Mode setup must remain semantically truthful
- future public Modes should be able to register onboarding steps in the Workspace Mode registry

## Registry contract

`WorkspaceModeDefinitionData` gains:

- `suggestedPlanCategory`
- `onboardingSteps`

The Mode remains distinct from Plan category.

`suggestedPlanCategory` is only a creation default used when the user explicitly starts a Plan from a specialized Workspace.

Each onboarding step contains:

```text
key
title
description
action_key
action_label
```

Overview has no onboarding steps.

### Study

1. `create_plan`
2. `capture_study_scope`
3. `record_study_evidence`

### Development

1. `create_plan`
2. `connect_github_evidence`

## Derived completion

Mode onboarding is self-completing from durable product state.

### Study

`create_plan` complete when a selected Study Plan exists.

`capture_study_scope` complete when confirmed Study Scope exists.

`record_study_evidence` complete when at least one of these exists for the selected Plan:

- `study_practice_assessed`
- `study_recall_reviewed`

After the first learning Evidence exists, the setup card disappears and normal Exam Readiness / Gap / Current Action becomes the primary surface.

### Development

`create_plan` complete when a selected Development Plan exists.

`connect_github_evidence` complete when Development Intelligence has an observed focus / Release candidate state from Development Evidence.

After Release Evidence exists, the setup card disappears and normal Release Readiness / Quality Gates / Current Action becomes primary.

## Shared onboarding presentation

A shared Mode onboarding card renders:

- Mode identity
- completed steps / total
- ordered step rail
- current step
- current step explanation
- one primary setup CTA
- note that the guide disappears automatically when real state is established

No secondary setup checklist is persisted.

## Mode-aware Plan creation

Starting Plan creation from a specialized Workspace uses:

```text
/plans/create/manual?workspace_mode=study
/plans/create/manual?workspace_mode=development
```

The specialized Workspace uses the existing manual Plan form because `/plans/create` is the conversational Goal Discovery entry and the user has already selected a concrete domain.

The manual create screen:

- validates the requested public Mode through `WorkspaceModeRegistry`
- prefills the Mode's suggested Plan category
- shows the originating Workspace context
- includes the requested Mode in the create form

After creation, if the resulting Plan profile still matches the requested specialized Mode:

Study:

```text
create Plan
→ /workspace/study?plan_id=...
→ next onboarding step: Study Scope
```

Development:

```text
create Plan
→ /workspace/development?plan_id=...
→ next onboarding step: GitHub Evidence
```

If the user changes the category so the resulting Plan no longer matches the requested Mode, Canovia does not force a semantically false Workspace redirect. The existing generic post-create flow is used instead.

## Overview first-use choice

When there is no Study Plan and no Development Plan, Overview shows a compact "choose a Workspace" first-use surface.

The options come from the public Workspace Mode registry, excluding Overview.

Each option uses:

- registry label
- registry description
- Mode entry URL
- Mode accent semantics

This is a choice surface, not a new onboarding gate.

## Performance

Study adds one selected-Plan `exists()` query for learning Evidence.

Development reuses the already evaluated `focus_task_state`.

Registry onboarding definitions are static.

No all-Plan Evidence scan is introduced.

## Non-goals

V54.7 does not:

- redesign the global Welcome screen
- mark Mode onboarding complete in the database
- create a tutorial overlay
- auto-create Tasks
- auto-import Study Scope
- auto-connect GitHub
- infer a Mode from an ambiguous Plan create request
- make Workspace Mode equal Plan category
- alter Intelligence scoring
- alter billing
