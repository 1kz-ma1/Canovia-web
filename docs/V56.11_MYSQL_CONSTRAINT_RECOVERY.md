# V56.11 MySQL Constraint Recovery

## Goal

Complete production deployment recovery after MySQL exposed a schema-definition issue that SQLite CI did not enforce.

## Production evidence

After V56.10 successfully reconciled the orphaned V53.2 / V53.3 tables, Render reached:

`2026_10_04_000500_create_intelligence_action_projections_table`

MySQL then rejected Laravel's generated foreign-key name:

`intelligence_action_projections_intelligence_decision_trace_id_foreign`

with MySQL error 1059 because the identifier exceeds the 64-character limit.

The same generated-name risk exists for the Decision Trace foreign key on
`intelligence_reasoning_runs`.

Historical failed CREATE TABLE attempts can also leave a physical table with its columns present while later foreign-key and index commands were never applied.

## Fix

Fresh creation paths now use explicit short names for the long Decision Trace foreign keys:

- `irr_decision_trace_fk`
- `iap_decision_trace_fk`

A follow-up reconciliation migration restores the complete intended schema contract for:

- `intelligence_reasoning_runs`
- `intelligence_action_projections`

It introspects existing foreign keys and indexes and adds only missing ones.

The repair covers:

- user / Plan foreign keys
- Decision Trace foreign keys
- Native AI / projected Task foreign keys
- single-column lookup indexes
- composite scope/history indexes
- Action Projection unique `action_reference` index

## Safety

V56.11 does not:

- drop either production table
- delete or rewrite rows
- duplicate an existing foreign key or index
- weaken uniqueness
- bypass Laravel migrations

The repair migration is idempotent and its `down()` intentionally does not remove historical schema requirements.

## Validation

Validation must cover:

- fresh migration chain
- V56.11 reconciliation idempotency
- explicit MySQL-safe identifier names
- V56.10 migration reconciliation
- V56.9 startup retry
- V56.8 migration recovery
- V53.2 / V56.7 / V56.6 regressions
