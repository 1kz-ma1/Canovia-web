# V58.30 Plan Completion Fingerprint / Revision

## Goal

V58.29で追加した `plan_completed` Refresh Triggerを、
単純なPlan ID memoryから**material completion revision**へ進化させる。

目的:

```text
same Plan
complete
→ reopen
→ re-complete without material change
= same completion

same Plan
complete
→ material Plan/Task change
→ re-complete
= new completion revision
```

これはAI推論ではなく、deterministic structural fingerprintで判定する。

- `docs/CANOVIA_PERSONALIZATION_SPEC.md`

- `docs/V58.29_PLAN_LIFECYCLE_PERSONALIZATION.md`

## Completion Fingerprint

New service:

- `PlanCompletionFingerprintService`

Fingerprint schema version:

```text
1
```

Hash:

```text
SHA-256(canonical structural payload)
```

### Included Plan fields

- Plan id
- title
- description
- category
- priority
- priority_mode
- start_date
- deadline
- study_learning_type_override

### Included non-cancelled Task fields

- Task id
- title
- description
- estimated_minutes
- priority
- activation_cost
- sort_order
- continuation_of_task_id
- dependency_task_ids

Tasks and dependencies are deterministically ordered.

### Deliberately excluded runtime fields

- status
- progress_percent
- remaining_minutes
- progress_reason
- next_action_note
- updated_at

Why:

A simple reopen / re-complete must not become a new material completion merely because runtime progress state changed.

## Material change examples

Fingerprint should change for examples such as:

- Task added
- Task removed / cancelled
- Task title or description changed
- estimated effort changed
- priority / activation cost changed
- dependency graph changed
- Plan title / description / category changed
- Plan dates changed

Fingerprint does not claim that every material change is equally important.

It only establishes:

> current completed Plan structure differs from the previously completed structure.

## Completion snapshot

Observed Context:

```text
observed_context.plan_lifecycle.completion_snapshots.<plan_id> = {
  schema_version,
  fingerprint,
  revision,
  task_count,
  completed_at,
  change
}
```

`change`:

- `first_completion`
- `material_revision`
- `legacy_baseline`

Snapshot memory is bounded to 20 Plan entries.

This is Living Profile dedupe / revision memory, not a canonical audit ledger.

## First completion

```text
no previous fingerprint
+ no V58.29 legacy completion memory
→ revision = 1
→ change = first_completion
→ plan_completed refresh
```

## Same fingerprint

```text
previous fingerprint == current fingerprint
→ no new revision
→ no new plan_completed refresh
```

Example:

```text
complete
→ reopen to 80%
→ complete again
without changing material Plan/Task structure
```

remains revision 1.

## Material revision

```text
previous fingerprint != current fingerprint
→ revision += 1
→ change = material_revision
→ plan_completed refresh
```

Example:

```text
revision 1 complete
→ reopen
→ add / edit meaningful Task structure
→ complete
→ revision 2
```

## V58.29 compatibility

V58.29 persisted:

```text
recent_completed_plan_ids
```

without a structural fingerprint.

V58.30 must not reinterpret that old memory as a new completion.

Compatibility behavior:

```text
Plan ID remembered by V58.29
+ no completion fingerprint yet
+ Plan reaches completion after upgrade
→ store current fingerprint as revision 1
→ change = legacy_baseline
→ DO NOT emit plan_completed
```

After that baseline:

```text
material fingerprint change
→ revision 2
→ emit plan_completed
```

This intentionally prefers a missed historical distinction over a false new completion event.

## Cancellation correction

V58.29 evaluated Plan completion only when the updated Task itself became done / 100%.

But this case is also valid:

```text
Task A = done
Task B = todo
↓
Task B becomes cancelled
↓
all remaining non-cancelled Tasks are complete
↓
Plan is complete
```

V58.30 therefore evaluates Plan completion when status/progress changes and the current Task becomes either:

- complete
- cancelled

All-cancelled Plan remains non-complete because at least one non-cancelled Task is required.

Cancelled Tasks are excluded from the structural completion fingerprint.

## Trigger Task semantics

Observed Context separates:

```text
last_completion_trigger_task_id
```

from:

```text
last_completed_task_id
```

If a cancellation establishes Plan completion:

- trigger task = cancelled Task
- completed task = null

This avoids calling a cancelled Task "completed".

## Refresh telemetry

Existing event:

- `context_refresh_triggered`

For Plan completion V58.30 includes:

```text
trigger = plan_completed
completion_revision = N
completion_change = first_completion | material_revision
```

`legacy_baseline` does not emit a completion refresh event.

Full fingerprint is not copied to Behavior Event metadata.

## Living Profile boundary

A completion revision only triggers existing deterministic Living Profile re-evaluation.

V58.30 does not add:

- Plan-direction inference
- experience-level inference
- new recommendation engine
- automatic replanning
- automatic Guidance change

## Ownership / trust

V58.29 boundaries remain:

- HTTP request only
- authenticated actor
- Plan owner only
- existing Personalization Context required
- guest does not create profile
- collaborator does not mutate owner Context

## Release boundary

Minimum:

```text
L1 Early Access Core
```

No new route or migration.

Manual review:

- `plan_completion_fingerprint`

Check:

- runtime progress/status change does not change fingerprint
- material Task edit changes fingerprint
- first completion = revision 1
- reopen/re-complete same structure = no revision
- material change + re-complete = revision 2
- new Task + re-complete = revision 2
- V58.29 memory becomes silent legacy baseline
- post-baseline material change emits revision 2
- cancellation can establish completion
- cancelled trigger Task is not labelled completed
- existing V58.29 lifecycle behavior remains intact
