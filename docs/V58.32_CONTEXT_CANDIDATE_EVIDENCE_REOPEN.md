# V58.32 Context Candidate Evidence Revision / Reopen

## Goal

V58.27で導入した high-impact Context Update Candidate のdismiss contractを、
「同じ事実では再通知しない」から一段進める。

Target:

```text
Candidate shown
→ User dismisses
→ same / similar evidence
→ stay dismissed

Candidate shown
→ User dismisses
→ materially stronger evidence appears
→ reopen candidate
→ ask again once
```

最重要原則:

> Dismissal is respected until evidence becomes materially stronger.

Fingerprintが変わっただけでは再openしない。
Dismiss時より `signal_strength` が厳密に上がった場合だけ再open可能とする。

## Scope

V58.32でgeneric evidence revision fieldsをCandidate contractへ追加する。

最初の適用対象:

- `development_advanced_support`

他Candidateへ自動適用しない。

## Candidate evidence fields

Candidate may contain:

```text
signal_strength
evidence_fingerprint
evidence_revision
dismissed_signal_strength
dismissed_evidence_fingerprint
dismissed_evidence_revision
last_dismissed_at
reopened_at
reopen_reason
```

Initial candidate:

```text
evidence_revision = 1
```

Reopen:

```text
evidence_revision += 1
reopen_reason = stronger_evidence
status = pending
resolved_at = null
```

## Development signal source

New service:

- `DevelopmentPersonalizationSignalService`

It uses bounded existing Canovia facts:

- connected GitHub repository roots
- `DevelopmentActivityObservation` from the last 30 days

Important:

`DevelopmentActivityObservation` describes repository activity.

It does **not** prove:

- the user authored a Pull Request
- the user authored a Commit
- the user's experience level increased

Therefore V58.32 uses this signal only for:

> whether repository-aware advanced Development support may now be more useful.

It must not reclassify the user's experience.

## Observed Context

Safe aggregate facts are written to:

```text
observed_context.development_behavior
```

Fields:

```text
connected_repository_count
recent_activity_count
recent_pr_or_commit_count
observed_at
```

Do not copy into Personalization Context:

- repository URL
- repository name
- PR title
- Issue title
- Commit message
- source code
- diff / patch

## Signal strength

V58.32 deterministic MVP levels:

### Strength 1

```text
GitHub integration connected
```

### Strength 2

Either:

```text
connected repositories >= 2
```

or:

```text
recent Development observations >= 3
AND
recent PR/Commit observations >= 1
```

### Strength 3

Either:

```text
recent PR/Commit observations >= 3
```

or:

```text
connected repositories >= 2
AND
recent Development observations >= 5
AND
recent PR/Commit observations >= 2
```

These thresholds are deterministic MVP heuristics, not experience-level definitions.

## Evidence fingerprint

Fingerprint is SHA-256 over coarse bounded counters only.

Concept:

```text
schema
connected_repository_bucket
recent_activity_bucket
recent_pr_or_commit_bucket
```

No repository identifiers or provider content are included.

The fingerprint answers:

> Has the relevant evidence shape changed?

It does not by itself authorize a reopen.

## Reopen rule

For a dismissed candidate:

```text
current signal_strength > dismissed signal_strength
AND
current fingerprint != dismissed fingerprint
→ reopen
```

Both are required.

Therefore:

```text
same strength + different fingerprint
→ remain dismissed
```

This prevents minor activity fluctuations from creating nagging prompts.

## Pending candidate update

If a Candidate is still pending and stronger evidence arrives:

- keep status = pending
- update evidence snapshot silently
- update signal strength
- update confidence
- increment evidence revision if fingerprint changed
- do not create a second prompt event

Why:

Dismissal must snapshot the actual current evidence strength, not stale evidence from first presentation.

## Confirmed candidate

A confirmed candidate is not reopened.

V58.32 may backfill missing evidence metadata for legacy confirmed candidates, but does not create a new decision request.

## Legacy compatibility

V58.27–V58.31 candidates may not contain:

- signal_strength
- evidence_fingerprint
- evidence_revision

Compatibility rule:

```text
legacy dismissed candidate
→ baseline dismissed strength = 1
```

Then:

```text
same strength 1
→ stay dismissed

new strength >= 2
→ may reopen
```

This avoids forcing all historical dismissals back to pending after deployment.

## UI

When a candidate reopens because of stronger evidence, Living Profile shows:

> より強い観測事実が増えたため再確認しています。前回と同じ事実だけで繰り返し表示しているわけではありません。

It must also continue to state:

- this is not an experience-level reclassification
- Initial Diagnosis is not rewritten

Dismiss copy explains:

- same observed facts will not repeat the prompt
- a materially changed usage situation may cause a future re-check

## Telemetry

Existing event remains:

- `context_update_candidate_created`

For this Candidate it includes safe metadata:

```text
candidate_key
domain
risk
confirmation_required
signal_strength
evidence_revision
reopened
reason
```

`reason`:

- `initial_evidence`
- `stronger_evidence`

Resolution telemetry also includes:

- signal_strength
- evidence_revision

No full evidence fingerprint is copied to Behavior Event metadata.

## Trust boundary

V58.32 does not automatically modify:

- self-reported experience
- Guidance Level
- Plan
- Task
- Entitlement
- Release Level

Reopen means:

> Ask again because circumstances changed materially.

It does not mean:

> Canovia has decided the user changed.

## Release boundary

Minimum:

```text
L1 Early Access Core
```

No migration / new public route.

Manual review:

- `context_candidate_evidence_reopen`

Check:

- initial candidate has evidence revision 1
- dismiss snapshots signal strength / fingerprint
- same evidence → stays dismissed
- same strength + changed fingerprint → stays dismissed
- stronger signal → candidate reopens
- evidence revision increments
- reopen explanation visible
- pending evidence refresh does not duplicate prompt event
- legacy dismissed candidate remains dismissed at strength 1
- legacy dismissed candidate may reopen at stronger signal
- self-reported experience preserved
- Guidance preserved
- mobile / desktop

## Non-goals

Not implemented:

- generic AI evidence scoring
- semantic repository complexity scoring
- user-authorship inference
- automatic experience reclassification
- automatic Plan-direction changes
- reopening every Candidate type
- arbitrary Candidate evidence execution
