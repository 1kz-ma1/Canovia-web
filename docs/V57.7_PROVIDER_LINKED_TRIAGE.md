# V57.7 Provider-linked CI / Review Triage

## Goal

V57.7 lets a developer explicitly pull bounded GitHub provider detail when the
current Development Action cannot be resolved from state summaries alone.

Canonical flow:

```text
Development Adaptive Action
+ V57.4 Execution Context
+ V57.6 Implementation Brief
→ explicit user request
→ GitHub App provider read
→ transient CI / Review detail
→ deterministic Task-scoped triage
→ human / coding-tool handoff
```

V57.7 is intentionally **not** part of normal Developer Home GET.

Provider text is fetched only after a user presses a triage action.

## Why explicit fetch

Normal Canovia Development Intelligence stores bounded facts such as:

- CI = failure
- Review = CHANGES_REQUESTED
- PR number / head SHA
- reviewer identity

Those facts are sufficient to choose the next Action, but they are not always
enough to perform the work.

Examples:

```text
CI = failure
→ which job?
→ which failing step?
→ which check annotation?

Review = CHANGES_REQUESTED
→ what did the reviewer ask for?
→ which file / line has an inline comment?
```

V57.7 crosses that provider-text boundary only after explicit user intent.

## Route and authorization

New explicit POST route:

```text
POST /plans/{plan}/tasks/{task}/development-provider-triage
```

Requirements:

- actor may edit the Plan
- Task belongs to the Plan
- Plan is Development
- actor has `DeveloperGithubEvidence`
- Task has a bounded Execution Context with Repository + Pull Request Evidence

This route is throttled.

Viewer-only collaborators cannot use it because the returned provider text may
belong to a Private Repository.

## Provider source

GitHub is read through the already-installed GitHub App.

Authority flow:

```text
Repository full name
→ exact GitHub App installation
→ short-lived installation token
→ Pull Request
→ bounded provider detail
```

The installation token is never persisted or returned to the browser.

## CI triage detail

When CI triage is requested, Canovia may read the current PR head SHA and,
where the installation has permission:

- GitHub Actions runs
- failed workflow jobs
- failed job step names
- Check Runs
- Check annotations
- Commit statuses

Boundaries:

- up to 12 workflow runs
- up to 5 failed runs expanded
- up to 20 failed jobs
- up to 10 failed steps per job
- up to 30 check runs
- up to 8 failed checks expanded
- up to 30 annotations per expanded check
- provider text fields are length-bounded

V57.7 does not download Actions log archives.

Check annotations are preferred because they provide bounded failure messages
and file / line references without ingesting arbitrary full logs.

## Review triage detail

When Review triage is requested, Canovia may read:

- Pull Request reviews
- Review state
- reviewer
- bounded Review body
- inline review comments
- comment file path / line
- bounded comment body
- canonical GitHub URLs

Boundaries:

- up to 20 Review records
- up to 30 inline comments
- provider body text is truncated before presentation

V57.7 does not fetch:

- PR source code
- diff / patch
- diff hunk
- arbitrary Repository file content

## Persistence boundary

Provider-linked detail is **transient**.

The triage response uses:

```http
Cache-Control: no-store, private
Pragma: no-cache
```

Review bodies, inline comments, CI annotations and provider descriptions are
not written to:

- `task_evidence`
- `plan_artifacts`
- Development State snapshots
- Decision traces
- Action projections
- a new triage table

The durable Intelligence layer remains bounded to the existing factual
Evidence model.

## Triage projection

`DevelopmentProviderTriageService` converts the transient provider response
into:

- current Task / Repository / PR target
- CI failure detail
- Review detail
- deterministic next steps
- warnings / missing-permission notes
- copy-ready triage handoff
- guardrails

No AI is called.

Unknown or unavailable provider facts remain unknown.

## Developer Home entry

V57.6 Implementation Brief gains an explicit provider-detail action when it is
useful:

```text
CI failure / CI triage
→ CI失敗の詳細を取得

Review changes requested / review Action
→ Review指摘の詳細を取得
```

Developer Home GET itself still performs no provider fetch.

## Copy handoff

The transient triage page can be copied for use in an IDE assistant or coding
agent.

Unlike the V57.6 durable bounded brief, the copied V57.7 handoff may include
the provider text the user explicitly requested in the current response.

Copying remains a user action.

Canovia does not:

- invoke an external coding agent automatically
- write source changes automatically
- create a GitHub branch automatically
- create or merge a Pull Request automatically

Existing GitHub write authorization remains authoritative.

## Safety

V57.7 never changes:

- Task progress
- Task status
- remaining minutes
- Task association
- Development Evidence
- Release Gate state

After the developer fixes the problem, the normal GitHub Evidence pipeline
must re-observe the new provider state.

Then Development Intelligence recalculates the next Action.
