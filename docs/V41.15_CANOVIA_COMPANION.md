# V41.15 Canovia Companion

更新日: 2026-09-27

## 1. Purpose

V41.14でCanoviaは、

```text
Goal
→ Current State
→ Provisional Plan
→ Execution
→ Reflection / Evidence
→ Tool Demand
```

まで未知Goalを扱えるようになった。

V41.15では、この既存Contextを毎回ユーザーが画面間で読み解かなくてもよいよう、
**Canoviaの状態を読める常時伴走Conversation**を追加する。

Companionは汎用AI Chatではない。

```text
Goal Context
Plan / Task
Inbox
Evidence
Current Screen
Recent Conversation
        ↓
Canovia Companion
        ↓
Response
        ↓
Mutation Candidate
        ↓
Human confirmation
        ↓
Existing Canovia mutation service
```

FreeのGoal達成経路を閉じず、
文脈整理・転記・判断摩擦をCanoviaが引き受けるPremium価値とする。

## 2. Economy boundary

`FeatureKey::CanoviaCompanion`

- Free: false
- Premium Core: included
- All Access: Premium Core経由でincluded

Native conversationを実行するには、
- `CanoviaCompanion`
- `AutomaticAiExecution`

の両方が必要。

これらは別Capabilityとする。

理由:
- CompanionのProduct access
- ProviderをCanovia側で実行するAI access

は将来別々に構成できる必要があるため。

AI Capacityも引き続き別責務。

## 3. Step 1 — Foundation + Native Conversation

Implemented.

### 3.1 Persistence

`companion_threads`

- user_id
- plan_id nullable
- task_id nullable
- status
- title
- context_scope
- last_message_at

`companion_messages`

- companion_thread_id
- user_id nullable
- native_ai_run_id nullable
- request_id unique nullable
- role: user / assistant
- content
- metadata

`companion_mutation_candidates`

- companion_thread_id
- companion_message_id
- user_id
- plan_id nullable
- task_id nullable
- candidate_key
- type
- status
- title / summary
- payload
- reviewed_at / applied_at

Step 1では `applied` への遷移処理を実装しない。

### 3.2 Context scope

Conversation作成時に以下から選ぶ。

- global
- Plan
- Task

Task scopeは親PlanもCanovia側で確定する。

### 3.3 Prompt context

毎回全DBを送らない。

最大:
- selected Plan
- selected Task
- Goal Context
- confirmed facts 10件
- known unknowns 8件
- Recent Evidence 6件
- own Inbox pending count
- current screen
- recent conversation 12 messages

Global scopeでは直近Plan概要だけを使う。

### 3.4 Mutation Candidate types

Step 1 allowlist:

- `create_task`
- `update_task`
- `update_plan`
- `record_goal_fact`
- `create_future_memo`
- `create_inbox_item`

AIは対象IDを決定しない。

Candidate payload内の以下は破棄する。

- id
- user_id
- plan_id
- task_id
- owner_token

Targetはselected Canovia contextからdeterministicに設定する。

必要なscopeがないCandidateは保存しない。

例:
- global conversationから `update_task` → reject candidate
- task conversationから `update_task` → selected Taskへcandidate
- global conversationから `create_future_memo` → candidate可

### 3.5 No direct mutation

Step 1では:

- AI responseはCanovia stateを変更しない
- Candidate creationもCanovia stateを変更しない
- apply endpointを作らない
- UIは「未反映」を明記
- Humanはcandidateを見送れる

AI response内でも「変更しました」と表現させない。

### 3.6 Idempotency

User message:
- UUID request_id

同じThread / User / request_idでAssistant responseが既にあれば再利用し、
Native AIを再実行しない。

Native AI失敗時:
- User messageは保持
- 同じrequest_idでretry可能
- duplicate User messageを作らない

### 3.7 UI

Main navigationは変更しない。

```text
Home | Inbox | Roadmap | Timeline
```

Companionはpersistent utilityとして、
公開時に各画面右下のlauncherから開く。

`/companion`
- Premium explanation
- Context selection
- conversation list

`/companion/threads/{id}`
- context summary
- messages
- Mutation Candidate preview
- send composer

## 4. Step 2 — Human-confirmed Mutation Apply

Next.

Candidate typeごとに専用Validator / Applierを作る。

原則:

```text
Candidate
→ server-side normalize
→ ownership check
→ domain validation
→ human confirm
→ existing Service / Model boundary
→ audit result
```

AI payloadをそのままModel::update()へ渡さない。

予定:

### create_task
selected Planへ作成。
既存Task creation contractを再利用。

### update_task
selected Taskだけ更新。
許可field allowlistを持つ。

### update_plan
selected Planだけ更新。
Plan Updateの既存validation / auditを再利用。

### record_goal_fact
GoalContextService経由。
candidate → Human confirm → confirmed Fact。

### create_future_memo
Future Memo既存contract経由。

### create_inbox_item
Inbox capture contract経由。

各applyは:
- request idempotency
- before/after audit
- applied candidate immutable linkage

を持つ。

## 7. Safety / Product principles

1. CompanionはCanoviaの事実を読む。事実を捏造しない。
2. AI suggestionとconfirmed stateを分離する。
3. AIはIDを選ばない。
4. AIは直接mutationしない。
5. Human confirmationをmutation境界に置く。
6. Time spentをProgress evidenceにしない。
7. FreeのGoal達成経路を残す。
8. Premiumは整理・判断・転記摩擦を引き受ける。
9. Conversation lengthやengagement最大化を目的にしない。
10. Contextは必要な範囲だけAIへ渡す。
