# V41.15 Canovia Companion

更新日: 2026-09-27

## 1. Purpose

V41.14でCanoviaは、

```text
Goal
→ Current State
→ Provisional Plan
→ Execution
→ Reflection / Evidence
→ Tool Demand
```

まで未知Goalを扱えるようになった。

V41.15では、この既存Contextを毎回ユーザーが画面間で読み解かなくてもよいよう、
**Canoviaの状態を読める常時伴走Conversation**を追加する。

Companionは汎用AI Chatではない。

```text
Goal Context
Plan / Task
Inbox
Evidence
Current Screen
Recent Conversation
        ↓
Canovia Companion
        ↓
Response
        ↓
Mutation Candidate
        ↓
Human confirmation
        ↓
Existing Canovia mutation service
```

FreeのGoal達成経路を閉じず、
文脈整理・転記・判断摩擦をCanoviaが引き受けるPremium価値とする。

---

## 2. Economy boundary

`FeatureKey::CanoviaCompanion`

- Free: false
- Premium Core: included
- All Access: Premium Core経由でincluded

Native conversationを実行するには、
- `CanoviaCompanion`
- `AutomaticAiExecution`

の両方が必要。

これらは別Capabilityとする。

理由:
- CompanionのProduct access
- ProviderをCanovia側で実行するAI access

は将来別々に構成できる必要があるため。

AI Capacityも引き続き別責務。

## 3. Step 1 — Foundation + Native Conversation

Implemented.

### 3.1 Persistence

`companion_threads`

- user_id
- plan_id nullable
- task_id nullable
- status
- title
- context_scope
- last_message_at

`companion_messages`

- companion_thread_id
- user_id nullable
- native_ai_run_id nullable
- request_id unique nullable
- role: user / assistant
- content
- metadata

`companion_mutation_candidates`

- companion_thread_id
- companion_message_id
- user_id
- plan_id nullable
- task_id nullable
- candidate_key
- type
- status
- title / summary
- payload
- reviewed_at / applied_at

Step 1では `applied` への遷移処理を実装しない。

### 3.2 Context scope

Conversation作成時に以下から選ぶ。

- global
- Plan
- Task

Task scopeは親PlanもCanovia側で確定する。

### 3.3 Prompt context

毎回全DBを送らない。

最大:
- selected Plan
- selected Task
- Goal Context
- confirmed facts 10件
- known unknowns 8件
- Recent Evidence 6件
- own Inbox pending count
- current screen
- recent conversation 12 messages

Global scopeでは直近Plan概要だけを使う。

### 3.4 Mutation Candidate types

Step 1 allowlist:

- `create_task`
- `update_task`
- `update_plan`
- `record_goal_fact`
- `create_future_memo`
- `create_inbox_item`

AIは対象IDを決定しない。

Candidate payload内の以下は破棄する。

- id
- user_id
- plan_id
- task_id
- owner_token

Targetはselected Canovia contextからdeterministicに設定する。

必要なscopeがないCandidateは保存しない。

例:
- global conversationから `update_task` → reject candidate
- task conversationから `update_task` → selected Taskへcandidate
- global conversationから `create_future_memo` → candidate可

### 3.5 No direct mutation

Step 1では:

- AI responseはCanovia stateを変更しない
- Candidate creationもCanovia stateを変更しない
- apply endpointを作らない
- UIは「未反映」を明記
- Humanはcandidateを見送れる

AI response内でも「変更しました」と表現させない。

### 3.6 Idempotency

User message:
- UUID request_id

同じThread / User / request_idでAssistant responseが既にあれば再利用し、
Native AIを再実行しない。

Native AI失敗時:
- User messageは保持
- 同じrequest_idでretry可能
- duplicate User messageを作らない

### 3.7 UI

Main navigationは変更しない。

```text
Home | Inbox | Roadmap | Timeline
```

Companionはpersistent utilityとして、
公開時に各画面右下のlauncherから開く。

`/companion`
- Premium explanation
- Context selection
- conversation list

`/companion/threads/{id}`
- context summary
- messages
- Mutation Candidate preview
- send composer

## 4. Step 2 — Human-confirmed Mutation Apply

Implemented.

Candidate typeごとにserver-side allowlist / Validator / Applierを実装する。

原則:

```text
Candidate
→ server-side normalize
→ ownership check
→ domain validation
→ human confirm
→ existing Service / Model boundary
→ audit result
```

AI payloadをそのままModel::update()へ渡さない。

### create_task
selected Planへ新規Taskを作る。

Companionからは以下だけを受け付ける。
- title
- description
- estimated_minutes
- priority
- activation_cost
- next_action_note

新規Taskは常に:
- progress_percent = 0
- status = todo
- remaining_minutes = estimated_minutes

で開始する。

### update_task
selected Taskだけ更新する。

許可:
- title
- description
- estimated_minutes
- remaining_minutes
- priority
- activation_cost
- next_action_note
- status = todo / doing のみ

禁止:
- progress_percent
- done
- cancelled

Companionが実行結果をTask Progressへ変換する経路は作らない。

### update_plan
selected Planだけ更新する。

許可:
- title
- description
- category
- priority
- priority_mode
- start_date
- deadline

禁止:
- public / private変更
- collaboration変更
- visual setting変更

Plan title変更時は既存GoalContext title syncを通す。

### record_goal_fact
GoalContextService経由でconfirmed Factへする。

許可type:
- current_state
- signal
- constraint
- driver

AI由来であることをsource / metadataへ残しつつ、
Human confirm後なのでstate=confirmed / confidence=1とする。

current_state Factを確認した場合はcurrent_state_summaryも同期する。

### create_future_memo
既存FutureMemoService経由で作成する。

### create_inbox_item
text Inbox Itemとして保存する。
Plan scopeのConversationなら、そのPlanへ紐づける。

### Apply audit / idempotency
Candidateへ以下を保存する。
- apply_request_id
- applied_target_type
- applied_target_id
- normalized_payload
- blocked_fields
- before
- after
- applied_by_user_id
- applied_at

applyはtransaction + row lockで処理する。
同一Candidateへの再送で二重mutationしない。

Validation error時はtransactionをrollbackし、
Candidateはpendingのまま残す。

### Human review UI
Candidate cardで:
- 実際に反映される項目
- 反映しない項目
- Target
- pending / applied / dismissed

を区別して表示する。

Humanが「この内容を反映する」を押すまで変更しない。

Native AI providerが一時停止していても、
すでに作られたCandidateのHuman applyは別責務として実行可能。

## 5. Step 3 — Contextual Companion Entry

Implemented.

Current ScreenからCompanionへ入るとき、Canovia側でContextを決定する。

```text
Task screen
→ Companion
→ same Task thread

Guided Execution / Reflection
→ Companion
→ same Task thread + latest Evidence

Plan / Roadmap
→ Companion
→ selected Plan thread

Inbox item
→ Companion
→ that Inbox item context
```

### 5.1 Entry boundary

persistent launcherは `POST /companion/entry` を使い、現在画面から:

- entry_type
- Plan / Taskのroute binding
- source route
- source path

を渡す。

対象IDをAIに選ばせない。
server-sideでownershipを再確認してからThreadを開く。

Free / provider unavailableなどNative conversationを開始できない場合は、
Contextual Entryから既存の `/companion` 説明画面へ戻す。
既存のFree Goal達成経路は変更しない。

### 5.2 Stable conversation reuse

同じContextから開くたび新しいConversationを量産しない。

stable entry key:

- global → `global`
- Plan → `plan:{id}`
- Task / Guided Execution → `task:{id}`
- Inbox item → `inbox:{id}`

Task screenとGuided Executionは同じTask conversationを共有する。
Guided Executionから再度開いた場合は、Threadを増やさずentry metadataを最新画面へ更新する。

Step 1で作成済みのlegacy global / Plan / Task Threadも、
同じscopeなら再利用できる。

Inbox itemは同じPlanに紐づいていてもgeneric Plan threadとは分離する。
「どの入力について相談しているか」を失わないため。

### 5.3 Context scope metadata

DB migrationは追加しない。
既存 `companion_threads.context_scope` JSONへ:

- scope
- entry_type
- entry_key
- source_path
- source_route
- inbox_item_id nullable

を保存する。

Conversation画面へ遷移した後も、
`current_screen` は `/companion/threads/{id}` ではなく元のCanovia画面を保持する。

### 5.4 Context details

Guided Execution entry:
- selected Task
- parent Plan / Goal Context
- TaskのRecent Evidence
- 最新Evidenceをentry contextとして明示

Inbox item entry:
- selected Inbox item title
- content（Context上限内）
- source type / URL
- linked PlanがあればPlan / Goal Context

を渡す。

Inbox一覧では各Itemに「Companionで整理」を置き、
global launcherだけでは特定できないinput contextを明示的に接続する。

### 5.5 Manual fallback

`/companion` のContext selectorは削除しない。

- 別Planについて相談したい
- Canovia全体を横断して相談したい
- 明示的に新しい対象を選びたい

場合のmanual entryとして残す。

通常導線ではユーザーへ毎回Context選択を要求しない。

## 6. Step 4 — Companion Continuity

Later.

Conversationを単なる履歴ではなく、
Canovia stateへ接続した継続対話にする。

候補:
- pending Mutation Candidate reminder

## 7. Safety / Product principles

1. CompanionはCanoviaの事実を読む。事実を捏造しない。
2. AI suggestionとconfirmed stateを分離する。
3. AIはIDを選ばない。
4. AIは直接mutationしない。
5. Human confirmationをmutation境界に置く。
6. Time spentをProgress evidenceにしない。
7. FreeのGoal達成経路を残す。
8. Premiumは整理・判断・転記摩擦を引き受ける。
9. Conversation lengthやengagement最大化を目的にしない。
10. Contextは必要な範囲だけAIへ渡す。
