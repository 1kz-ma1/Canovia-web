# V41.22 — Instant Navigation Phase 3: Shared Core Context

## Goal

V41.20でCore画面をSoft Navigation化し、
V41.21でFull Shell再生成をFragment Layoutへ置き換えた。

Phase 3では、Core画面をbackground warm-upするときに
Home / Roadmap / Timeline / Calendarが同じPlan・Task・WorkLogを
別requestで何度も取得する構造をやめる。

## Scope

Shared Core Context対象:

- Home
- Roadmap
- Timeline
- Calendar

Inboxは以下の固有データが中心なので、Phase 3では独立Prefetchを維持する。

- Inbox Items
- Study Recall Candidates
- Career Captures
- pending plan updates
- AI entitlement / provider status

## Before

V41.21まではidle prefetchが各画面を1件ずつ取得していた。

```text
Home
  -> GET /roadmap
     -> Plans / Tasks / WorkLogs
  -> GET /timeline
     -> Plans / WorkLogs
  -> GET /calendar
     -> Plans / Tasks / WorkLogs / Availability
  -> GET /inbox
     -> Plans / Inbox-specific data
```

画面切替自体は速くても、裏ではPlan graphを繰り返しDBから組み立てていた。

## After

V41.22:

```text
Core Shell
  -> GET /instant/core-bundle
      -> CoreContextService
          -> owned Plans: once
          -> Tasks: load once when first needed
          -> Task dependencies/resources: load once
          -> WorkLogs: load once
          -> Availability: load once
          -> Home-only relations: load only if Home requested
      -> Roadmap fragment
      -> Timeline fragment
      -> Calendar fragment
      -> Home fragment when requested

  -> GET /inbox
      -> Inbox-specific path
```

Bundle responseは複数のV41.21 Fragment HTMLを1つのJSON responseで返す。

## CoreContextService

request-scoped serviceとして追加。

保持するもの:

- owned/viewable Plan collection
- loaded relation feature set
- actor token

Relationは必要になった時だけloadMissingする。

Feature:

- tasks
- task_dependencies
- task_artifacts
- work_logs
- availability
- plan_resources
- plan_artifacts
- career
- memberships

重要なのは「全画面用supersetを常に取得しない」こと。

Roadmap / Timeline / CalendarだけのBundleではCareerやPlan Artifactを読まない。
HomeがBundle対象に入った時だけHome用relationを追加する。

## Page Data Builders

Controller内に散らばっていたPage Data組み立てを以下へ分離した。

- HomePageDataService
- RoadmapPageDataService
- CalendarPageDataService
- TimelinePageDataService

通常のHard / Fragment requestも同じBuilderを利用する。

これによりBundle専用にController logicを複製せず、
通常画面とBundleで同じbusiness logicを共有する。

## Core Fragment Bundle

Endpoint:

`GET /instant/core-bundle`

Internal boundary:

`X-Canovia-Instant-Navigation: prefetch`

がないrequestは404。

DB-backed rate limiterは付けない。
現在のdefault Cache Storeがdatabaseのため、
throttle middlewareを付けるとPrefetch削減のためのendpoint自身が
DB roundtripを追加するため。

Response:

```json
{
  "version": 1,
  "fragments": {
    "/roadmap": "<html>...</html>",
    "/timeline": "<html>...</html>",
    "/calendar": "<html>...</html>"
  }
}
```

Cache-Controlはprivate, no-store。

## Client Bundle Prefetch

V41.20のmemory cache / history / fail-openは維持。

idle warm-up時:

1. Home / Roadmap / Timeline / Calendarの未cache URLを抽出
2. 1回のcore-bundle requestへまとめる
3. 各Fragmentを既存payload parserへ通す
4. memory cacheへ格納
5. Inboxだけ独立Prefetch

Pointer / focus / touch intentで既に個別Prefetchが始まっているURLは
Bundle対象から除外し、重複requestを防ぐ。

Bundle処理中にユーザーが対象画面を押した場合は、
そのBundle promiseをそのままnavigationが待つ。

Bundleが失敗、または特定Fragmentが欠落した場合は
既存のdirect fragment GETへfail-openする。

## Shared relation reuse

同一Bundle request内では同じEloquent Plan modelをPage Builders間で共有する。

例:

Roadmapが先に:

- Plans
- Tasks
- Task dependencies/resources
- WorkLogs

をロードした後、

Timelineは同じWorkLogs relationをそのまま利用し、
Calendarは同じPlans / Tasks / WorkLogsを利用しつつ
Availabilityだけ追加ロードする。

## Ownership memoization

PlanOwnershipServiceのrole lookupをrequest内memoize。

Keyは:

- User ID + Plan ID
- Guest owner token hash + Plan ID

共同PlanのcanView / canEdit / role確認を同じBundle中に繰り返しても、
同じmembership queryを再実行しない。

## Request isolation

CoreContextServiceはscoped bindingだが、
Feature Testなど同じApplication processで複数Requestが走る状況も考慮し、
Request objectが変わったら:

- Plans
- loaded relation set
- actor token

を明示的にresetする。

ユーザー間・request間でEloquent modelを共有しない。

## Observability

performance対象へ:

`/instant/core-bundle`

を追加。

既存metricsに:

- core_bundle
- response_bytes
- query_count
- db_ms
- table summary
- session_query_ms

を使い、本番でBundle導入前後を比較できる。

## Validation

Focused regressionでは以下を固定する。

- Bundle endpointはinternal prefetch header必須
- Roadmap / Timeline / Calendarを1 responseで返す
- direct Fragment routeは維持
- Bundleのowned Plan query数は3画面別request合計より少ない
- BundleのWorkLog relation query数は3画面別request合計より少ない
- Bundle内WorkLog relation取得は1 query
- InboxはBundle対象外
- performance pathにcore-bundleを含む
- V41.17〜V41.21 regressions維持
- Instant Start維持

## Architectural result

V41.20:
ユーザーをserver待ちから切り離した。

V41.21:
Shell生成をserver hot pathから外した。

V41.22:
複数画面のbackground preparationを1つのCore Contextへ集約した。

```text
Plan / Task / WorkLog / Availability
               ↓
        Shared Core Context
          ↙     ↓      ↘
      Home   Roadmap  Calendar
                 ↓
              Timeline
```
