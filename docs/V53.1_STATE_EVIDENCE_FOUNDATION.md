# V53.1 State / Evidence Foundation

## Goal

V53.1 turns the V53.0 Intelligence contract into a usable State/Evidence pipeline without creating a second raw evidence system.

The first validation domain is Study.

```text
existing TaskEvidence
      ↓
TaskEvidenceAdapter
      ↓
EvidenceObservation
      ↓
StudyStateBuilder
      ↓
StateSnapshot
      ↓
StateSnapshotStore
      ↓
intelligence_state_snapshots
```

V53.1 still does not calculate Readiness or choose a Next Action. Those remain V53.2 responsibilities.

## Evidence boundary

Existing `TaskEvidence` remains the durable source for Task-linked observations.

V53.1 introduces `TaskEvidenceAdapter` to translate that existing record into the provider-neutral `EvidenceObservation` contract.

The adapter deliberately does not copy arbitrary `metadata`.

Only fields with known decision meaning cross the boundary.

Examples currently normalized:

- Study practice score / strengths / weaknesses / next-step label
- Study recall rating / interval
- Focus session duration / interruption
- GitHub PR CI state
- GitHub PR merge state
- GitHub review state
- Artifact provider/type/version/action
- Guided execution outcome rating

Unknown TaskEvidence types still retain their origin identity, source, type, occurrence time and confidence, but arbitrary metadata is not copied.

## Raw data exclusion

Intelligence records are not a mirror of provider or user raw payloads.

Do not copy the following into Intelligence State by default:

- Study question bodies
- Study answer bodies
- provider request / response payloads
- full prompts
- cookies / session / CSRF values
- private URLs
- arbitrary free-text metadata
- third-party raw webhook payloads

Raw source data remains in the source subsystem when it is needed for its own feature.

The Intelligence layer receives normalized decision facts only.

## Fingerprints

V53.1 introduces canonical fingerprints so later Decision/Outcome records can point to stable inputs.

### Canonical JSON

`CanonicalJson` recursively sorts associative keys while preserving list order.

This prevents semantically equivalent associative payloads from producing different hashes because of key ordering.

### Evidence fingerprint

`IntelligenceFingerprint::evidence()` hashes:

- origin reference
- source
- type
- occurred-at
- confidence
- normalized facts
- related references

`evidenceReference()` produces a stable trace reference:

```text
evidence:<source>:<sha256>
```

### State fingerprint

`state()` hashes semantic State content:

- domain
- scope
- metrics
- facts
- Evidence references

It intentionally excludes `capturedAt`.

If the same State is observed later, its semantic state fingerprint remains the same.

### Snapshot fingerprint

`snapshot()` hashes:

- semantic state fingerprint
- captured-at

This means the same State observed at a different time becomes a separate snapshot.

`stateReference()` produces:

```text
state:<domain>:<snapshot-sha256>
```

This split supports both:

- idempotent retries for the exact same snapshot
- time-series history when unchanged State is re-observed later

## Study State V1

`StudyStateBuilder` is the first concrete implementation of the V53 `StateBuilder` contract.

V53.1 only derives factual State, not Readiness.

Current metrics:

- Evidence count
- Practice attempt count
- Recall review count
- Latest practice score
- Average practice score
- Best practice score

Current facts:

- whether practice Evidence exists
- whether recall Evidence exists
- observed strengths
- observed weaknesses

Task progress is intentionally not imported into these State metrics.

A Task may be 95% complete while practice Evidence still shows weak mastery. V53 State must be able to represent that disagreement.

## Evidence trace inside State

Each State evidence reference contains:

```json
{
  "trace": "evidence:native:<sha256>",
  "origin": "task_evidence:<id>"
}
```

The hash pins the exact normalized Evidence version.

The origin preserves auditability back to the existing source record.

## Durable State storage

V53.1 adds `intelligence_state_snapshots`.

Stored fields:

- user_id (nullable)
- plan_id (nullable)
- domain
- scope_type
- scope_id
- state_fingerprint
- state_reference
- captured_at
- metrics
- facts
- evidence_references
- small controlled metadata

The store does not accept arbitrary metadata.

Only these metadata keys are currently persisted:

- schema_version
- builder
- builder_version

This prevents provider payloads from leaking into State through a convenience metadata field.

## Idempotency

`state_reference` is unique.

Persisting the exact same StateSnapshot twice returns the same stored row.

The same semantic State at a later captured time creates a new row with:

- same `state_fingerprint`
- different `state_reference`

## Scope

V53.1 supports generic State scopes through:

- `scope_type`
- `scope_id`

Study initially uses scopes such as:

```text
scope_type = plan
scope_id   = <plan id>
```

Later phases may introduce narrower subject/unit scopes without changing the persistence contract.

## Why no duplicate Evidence table

Canovia already has useful durable sources:

- TaskEvidence
- StudyPracticeAttempt
- StudyRecallReview
- GitHub return data
- GuidedExecution
- WorkSession

V53.1 normalizes those sources instead of copying every raw source event into a new generic table.

A future generic Evidence store should only be added if a real domain requires durable observations that do not naturally belong to an existing source system.

## Non-goals

V53.1 does not implement:

- exam Readiness score
- release Readiness score
- Decision selection
- OpenAI reasoning
- automatic replanning
- automatic Task mutation
- user-facing State UI
- test-range image/PDF capture
- GitHub webhook expansion
- model training

## Next

V53.2 should consume StateSnapshot and implement:

- explainable gaps
- deterministic Readiness primitives
- confidence-aware Readiness
- Decision candidate selection
- durable Decision trace suitable for later Outcome evaluation

Study remains the first validation domain before the same mechanism is extended to Development.
