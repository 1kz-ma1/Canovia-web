# V41.9 Practice Demand & Question Candidate Operations

更新日: 2026-09-26

## 目的

V41.8.2で記録を始めた `practice_question_demands` を、Question Bank拡充の運営判断へ接続する。

同時に、Hybrid / Native AI演習で実際に生成された問題を即Question Bankへ入れず、公開前の `PracticeQuestionCandidate` として隔離し、人が品質を確認した問題だけを既存Question PackのDraftへ昇格できるようにする。

V41.9の運営ループ:

```text
実際のPractice Demand
  -> Bank供給 / AI補完不足を集計
  -> 不足が多い試験・重点topicを確認
  -> Native AI生成問題をCandidateとして蓄積
  -> Adminが問題文 / 選択肢 / 正答 / 解説 / learning metadataを確認
  -> Draft Question Packへ昇格
  -> 既存のReview / Publishedフロー
```

自動生成から自動公開へは接続しない。

## 1. Practice Demand Admin

Adminに `/admin/practice-demand` を追加する。

確認できる情報:

- 集計期間: 7日 / 30日 / 90日 / 全期間
- exam profile
- assembly mode
- 演習Session数
- 要求問題数
- Question Bank供給数
- AI補完が必要だった問題数
- 実際の生成数
- Bank充足率
- AI補完成功率
- exam profileごとの供給状況
- focus topicごとの不足Session数
- 最近のPractice Demand
- Question Candidate確認キュー

focus topicは1つの演習に複数含まれるため、不足問題数を各topicへ推定配賦しない。
V41.9では「そのtopicがfocusに含まれ、かつBank不足が発生したSession数」を需要シグナルとして扱う。

詳細分析は画面負荷を抑えるため最新5,000 Demandを上限とする。
上部の総Session数・要求数・供給数は対象期間全体を集計する。

## 2. Practice Question Candidate

新規 `practice_question_candidates` を追加する。

CandidateはQuestion BankのQuestionではない。
演習利用時に生成されたNative AI問題のうち、Question Bank由来でない問題だけを保存する。

保存項目:

- fingerprint
- status: pending / rejected / promoted
- provider / model
- exam_profile_key
- first / latest Practice Demand
- Native AI Run
- 公開用question payload
- review hints
- generation_count
- last_seen_at
- review data
- 昇格先Question Pack / Question
- reviewer / reviewed_at

### 保存するquestion payload

Native AI生成時にブラウザへ渡している以下だけをCandidateへ保存する。

- id
- prompt
- work_input
- response_fields

正答・grading_rule・解説をAI生成時点のCandidateへ推測追加しない。

## 3. 重複Candidate

fingerprintは次の情報から作る。

- exam_profile_key
- 正規化したprompt
- response_fields

同じfingerprintが再度生成された場合、新Candidateを増やさず既存Candidateの:

- latest demand
- generation_count
- last_seen_at
- model / run

を更新する。

同じDemandの再処理ではgeneration_countを増やさず、prepare_requestの冪等性を壊さない。

promoted / rejected Candidateを再生成しただけでpendingへ戻さない。

## 4. Admin Review

Candidate詳細で以下を確認する。

- 問題文
- 回答欄・選択肢
- exam profile
- focus topics
- 生成回数
- model
- provenance

pending Candidateには次の2操作を提供する。

### Promote

Adminが以下を入力・確認する。

- 昇格先Draft Question Pack
- external_key
- grading_rule
- learning_metadata
- explanation
- difficulty
- source_reference
- review note

Candidateのresponse_fieldsはそのままQuestionのresponse_schemaへ利用するが、それ以外は既存 `QuestionPackImportService` のQuestion検証契約を通す。

昇格後:

- Question.source_type = `ai_generated`
- Candidate.status = `promoted`
- promoted_question_pack_id / promoted_question_idを記録
- reviewer / reviewed_atを記録

### Reject

採用しないCandidateは理由を記録して `rejected` にする。
rejectedは必要な場合だけ `pending` へ戻せる。

## 5. Draft Only Boundary

Candidateから直接追加できるQuestion Packは `draft` のみ。

`review` / `published` / `retired` への直接昇格は禁止する。

したがって:

```text
AI generated
 -> Candidate
 -> human review
 -> Draft Question
 -> existing Pack review
 -> Published
```

の境界を必ず通る。

公開済みQuestion Packのimmutable version運用も維持する。

## 6. 学習者データの扱い

Candidateへ保存するのは問題生成結果と最小限の運営用文脈だけとする。

保存しないもの:

- 学習者の自由記述回答
- 誤答内容そのもの
- assessment feedback本文
- 個人名等をCandidate本文へ追加する処理

review_hintsのfocus topic / strategyは、どの不足を補うために生成されたかを確認する補助情報であり、Questionのlearning metadataとして自動確定しない。

## 7. 今回含めないもの

- Candidateの自動採点正解生成
- Candidateの自動品質判定
- Candidateの自動Published昇格
- 過去問サイト等からの自動収集
- 著作権・ライセンス判定の自動化
- topicごとの不足問数の推定配賦
- Question Packの自動作成
- AI Candidateだけを根拠にした自動調達判断

## 8. V41.9の完成条件

- Practice DemandをAdminから確認できる
- exam profile / focus topicのBank不足を確認できる
- Native AI生成問題だけがCandidateへ記録される
- 同一Demand再処理でCandidateが増殖しない
- Candidateを人が確認してDraft Questionへ昇格できる
- Published Packへ直接昇格できない
- 既存Question Pack公開フローを変更しない

## V58.13 Reliability feedback update

Question Candidate operations now feed a bounded signal into Practice
Reliability.

The signal uses:

- exam-profile scoped promoted / rejected Human Review decisions;
- repeat Candidate generation count as operational context;
- reuse of promoted Candidate Questions in StudyPracticeSession selections;
- assessed reuse when the Session has a StudyPracticeAttempt.

Pending Candidates are not included in the promotion-rate denominator.

Learner score / correctness is not used to judge Candidate quality.

Only Native AI / Hybrid AI question-quality Reliability receives the bounded
Candidate adjustment. Question Bank and external AI baselines remain unchanged.

See `docs/V58.13_QUESTION_CANDIDATE_RELIABILITY.md`.
