# V57.5 GitHub Connection & Private Repository Unification

## Goal

V57.5 makes GitHub App installation the canonical Repository connection path
for Canovia Developer and removes the historical assumption that Repository
inspection must be public.

Canonical user flow:

```text
Developer Home / GitHub settings
→ register Repository root
→ connect Canovia GitHub App
→ choose Repository in GitHub
→ verify exact installation
→ read-sync Public or Private Repository
→ webhook / Evidence / Developer Home
```

Public and Private Repositories use the same connected path.

## Capability boundary

Connection/read and write are separate capabilities.

```text
DeveloperGithubEvidence
→ connect GitHub App
→ verify installation
→ Repository read
→ PR / Issue / Commit / Branch / CI / Review / Deploy Evidence

DeveloperGithubWrite
→ optional write layer
→ Branch / Commit / Pull Request creation
```

Starting, completing or checking a GitHub App connection no longer requires
`DeveloperGithubWrite`.

Write capability does not decide whether a Repository is connected.

## Installation permission projection

Canovia stores two bounded readiness projections:

- `read_ready`
- `write_ready`

A Repository is `connected` when the installation grants at least:

- Contents: read or write
- Pull Requests: read or write

Write readiness additionally requires:

- Contents: write
- Pull Requests: write

Issues / Actions remain optional signals. Canovia reads them only when the
installation grants the corresponding permission.

Legacy connection metadata without `write_ready` remains compatible. Before
V57.5, `status=connected` could only be produced by the write-ready contract,
so legacy connected records are treated as write-ready until the next
authoritative connection check refreshes the projection.

## Private Repository support

The GitHub App installation token is the authoritative read credential for
connected Repositories.

Connected Repository snapshot:

```text
GitHub App JWT
→ exact Repository installation
→ installation access token
→ bounded Repository snapshot
```

The snapshot supports both Public and Private Repositories and stores only
bounded presentation data:

- Repository metadata
- up to 12 Branches
- up to 12 open Pull Requests
- up to 12 open Issues
- up to 10 recent Actions runs when permission exists

It never stores:

- source code
- diff / patch
- PR body
- Issue body
- commit message
- installation token
- App private key

## Public preview fallback

`GitHubRepositoryInspector` remains intentionally public-only.

Its role is reduced to:

> limited preview for an unconnected Public Repository

It is not an authentication or Private Repository path.

When a registered Repository is connected, manual Repository refresh uses the
GitHub App snapshot reader. When unconnected, refresh uses the public preview
reader.

Therefore:

```text
connected
→ GitHub App read
→ Public / Private

not connected
→ public preview
→ Public only
```

A service-owned read token must never expose a Private Repository through the
fallback preview.

## Connection UI

Repository connection presents three user-facing states:

1. **未接続**
   - connect GitHub App
2. **確認が必要**
   - approval pending / permission update / reconnect
3. **接続済み**
   - read synchronization available

Installation IDs, App IDs, Queue state and webhook diagnostics remain
operational detail rather than primary user copy.

Write is shown separately as **Optional Write**.

A read-only connected Repository remains fully valid for Developer Evidence.
The write form appears only when write capability and write readiness both
exist.

## Developer Home

When a Repository root exists but is not connected, Developer Home can start
the GitHub App connection directly.

When no Repository root exists, Developer Home links to Repository
registration.

Private Repository users are explicitly told they do not need to make the
Repository public.

## Legacy GitHub Workflow surface

GitHub Workflow remains available for connection settings, manual Artifact
registration and diagnostics.

The historical manual PR / Issue / Branch lanes are secondary detail and are
collapsed behind a detail surface. Developer Home remains the primary daily
workflow.

## Write safety

Execution GitHub Handoff accepts only a Repository that is:

- GitHub App connected
- write-ready

A read-only connected Repository must never become a write target merely
because its connection status is `connected`.

The actual GitHub write path still re-checks installation permissions
authoritatively at execution time.
