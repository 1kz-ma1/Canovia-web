# V58.11 Safe Plan Resource → Recall Handoff

Status: implemented / validated  
Branch: `feature/v58-11-safe-resource-recall-handoff`

## 1. Goal

Connect an existing Plan Resource to Recall Candidate extraction without
server-fetching the Resource URL.

```text
PlanResource reference
→ learner explicitly chooses Recall handoff
→ learner provides trusted file bytes or pasted text
→ StudyRecallSource(plan_resource_id)
→ existing Candidate extraction
→ Human Review
→ Recall Deck
```

The Resource URL remains a reference, not extraction input.

## 2. Why Resource URLs are not fetched

Current Plan Resources can reference:

- Google Drive
- OneDrive / SharePoint
- GitHub

A shared URL may represent:

- an HTML sharing page;
- authenticated content;
- a redirect;
- a repository/browser page rather than file bytes;
- private organization content.

V58.11 intentionally avoids generic server-side URL fetching.

This prevents introducing:

- SSRF risk;
- authentication/token ambiguity;
- accidental private-page capture;
- provider-specific scraping behavior;
- unstable content interpretation.

## 3. Provenance

V58.11 adds nullable:

`study_recall_sources.plan_resource_id`

Foreign key:

`plan_resources.id`

Delete behavior:

`nullOnDelete`

This allows direct Recall material and Resource-derived Recall material to share
the same Source model.

Deleting the Plan Resource does not delete Recall history or Candidate lineage.
Only the Resource provenance link becomes null.

## 4. Eligible Resources

A Resource is eligible for a Task when:

1. it belongs to the same Plan;
2. it is a `file` Resource;
3. it has no Task assignment, making it Plan-level material; or
4. it is explicitly linked to the current Task.

A Resource linked only to other Tasks is not offered and is rejected server
side if a crafted POST attempts to use it.

Cross-Plan Resources are rejected.

## 5. Trusted material input

The learner explicitly provides one of:

### File

Accepted:

- PDF
- JPEG
- PNG
- WEBP

Maximum:

- 10 MB

The file is stored on the existing private Recall Source path:

`study-recall-sources/{plan}/{task}/...`

### Text

Accepted:

- non-empty pasted text
- maximum 50,000 characters

The Resource URL itself is never treated as source text.

## 6. Extraction path

V58.11 reuses the existing:

`StudyRecallCandidateExtractionService`

There is no new extraction prompt, Candidate table or AI contract.

The Source stores:

- plan_id
- task_id
- plan_resource_id
- user / actor identity
- source_type
- explicit file/text material
- normal Recall Source status

Existing behavior remains authoritative for:

- Native AI execution
- Candidate fingerprint deduplication
- Candidate Human Review
- V58.7 failed Source retry
- Recall Deck promotion

## 7. URL isolation

The external Plan Resource URL is not sent to Native AI as extraction material.

The provider request receives only:

- the explicit uploaded image/PDF bytes; or
- the explicit pasted text.

Dedicated validation asserts that the Resource URL is absent from the Native AI
request and that no separate HTTP request is made to it.

## 8. Recall UI

When eligible Resources exist and automatic Candidate extraction is available,
Recall shows:

`登録済みResourceからRecall教材を作る`

Each Resource displays:

- title
- provider
- current Task-linked / Plan-level status
- explicit "参照元を開く" browser link
- file/text material form

The UI states:

"CanoviaはResource URLを自動取得しません。Recallに使う内容をファイルまたは本文として確認して渡してください。"

This makes the trust boundary visible to the learner.

## 9. Source provenance UI

Recent Recall Source rows display:

`Resource: <title>`

when `plan_resource_id` is still present.

The existing authorized private-file route remains the only way to view saved
Recall file material.

## 10. Failure behavior

Before provider execution, if file storage succeeds but Source creation fails,
the newly stored file is deleted.

After Source creation/provider execution starts, a Native AI failure keeps:

- Source row
- private material
- plan_resource_id
- failed Native AI run
- failed status

The learner can then use V58.7 explicit retry without selecting or uploading the
Resource material again.

## 11. Account deletion

Resource-derived Recall files stay inside the existing
`study_recall_sources.storage_path` contract.

`AccountDeletionService` already collects and deletes those paths before
removing user-owned Plan data.

V58.11 dedicated validation confirms that a Resource-derived private Recall PDF
is removed together with its Source and owned Resource on account deletion.

## 12. Entitlement

Automatic Resource → Candidate extraction uses the same:

`AutomaticAiExecution`

capability as direct Recall material extraction.

V58.11 adds no new entitlement or billing rule.

Manual Recall remains available on the Free path.

## 13. Resource contract remains unchanged

V58.11 does not enable general PlanResource device upload.

PlanResource remains a lightweight external reference contract.

The trusted file/text supplied for Recall is stored as a Recall Source, not as a
new persistent PlanResource file body.

This avoids silently overturning the existing Resource storage strategy.

## 14. Migration

One additive migration:

`2026_10_06_101500_add_plan_resource_id_to_study_recall_sources.php`

It adds:

- nullable `plan_resource_id`
- foreign key → `plan_resources.id`
- `nullOnDelete`

No backfill is required.

## 15. Boundaries

V58.11 does not:

- fetch Resource URLs;
- use Drive / OneDrive / GitHub APIs;
- enable generic Resource direct upload;
- auto-promote Candidates;
- change Recall scheduling;
- change V58.6 Task progression;
- change V58.8 batch ingest;
- change V58.9 outcome interpretation;
- change billing.

## 17. Result

Canovia now has a safe Resource-to-learning bridge:

```text
external Resource reference
→ explicit learner-confirmed material
```
