# V53.3 Reasoning Router

## Goal

V53.3 introduces a provider-neutral reasoning layer behind the V53 Decision boundary.

The deterministic V53.2 policy remains the baseline and fallback.

```text
State
  ↓
Readiness
  ↓
deterministic candidates
  ↓
deterministic baseline Decision
  ↓
Reasoning Router
  ├─ deterministic
  ├─ OpenAI
  └─ future Canovia model
  ↓
selected Decision
  ↓
Decision trace
```

V53.3 does not make AI the source of truth.

AI may select among Canovia-approved Decision candidates, but it cannot invent a new candidate, Task, Plan or Action.

## Separation of concerns

Natural conversation and Decision reasoning remain separate concerns.

OpenAI may continue to power conversational experiences, but V53.3 only covers structured Decision selection.

The strategic asset remains:

```text
State
→ Readiness
→ candidate set
→ selected Decision
→ Outcome later
```

## Existing Native AI reuse

V53.3 reuses the existing `NativeAiGateway`.

It does not introduce a second OpenAI client.

Existing Native AI already provides:

- OpenAI Responses API
- Structured Output
- provider/model config
- token usage
- request hashing
- failure tracking
- `store=false`
- `NativeAiRun`

V53.3 adds routing and Decision-specific observability above that gateway.

## CandidateDecisionEngine

V53.3 adds `CandidateDecisionEngine`.

It extends the existing `DecisionEngine` contract with explicit candidate generation.

`StudyDecisionEngine` now implements this interface.

This lets the Reasoning Router see the complete Canovia-approved decision set while retaining the same deterministic `decide()` baseline.

## Reasoning modes

Configured through `config/intelligence.php`.

### deterministic

Default mode.

No model call is made.

The V53.2 baseline Decision is selected.

### openai

Attempts structured OpenAI Decision selection when:

- actor may use `automatic_ai_execution`
- Native AI is configured
- provider succeeds
- returned candidate belongs to the allowed set

Any failure falls back to deterministic.

### auto

Escalates to OpenAI only when:

- there are at least the configured minimum number of candidates
- deterministic baseline confidence is at or below the configured threshold
- actor has the existing entitlement
- provider is available

High-confidence or single-candidate decisions remain deterministic.

Default thresholds:

```text
max baseline confidence = 0.70
min candidates = 2
```

These are configuration, not hard-coded product promises.

## Entitlement boundary

Reasoning Router uses the existing:

`FeatureAccessService -> FeatureKey::AutomaticAiExecution`

It does not create a separate Premium check or direct `is_premium` condition.

Pricing/entitlement policy can therefore change without rewriting Intelligence routing.

## OpenAI Decision reasoning

`OpenAiDecisionReasoningProvider` implements `DecisionReasoningProvider`.

OpenAI receives only normalized Decision context:

- State metrics
- State facts
- Readiness score / level / confidence
- Readiness components / structured gaps
- deterministic baseline type / reason / confidence
- candidate type / reason / priority / confidence / structured metadata

It does not receive:

- raw Study question bodies
- raw answers
- provider payloads
- session/cookie/CSRF data
- arbitrary private source documents
- Task/Plan free-text titles through this Decision route

The prompt explicitly requires OpenAI to choose exactly one candidate from the provided list.

The Structured Output schema constrains `selected_type` to the exact candidate enum.

## AI cannot increase evidence confidence

Final Decision confidence is:

```text
min(candidate confidence, provider selection confidence)
```

A model cannot make a candidate more trustworthy than the underlying Canovia evidence allows.

## Fallback

Fallback is deterministic.

Examples:

- `feature_not_entitled`
- `provider_unavailable`
- provider HTTP error
- invalid confidence
- candidate contract mismatch
- unexpected provider error

Fallback rows are recorded for observability but are not reused as permanent successful reasoning cache.

This means a temporary provider outage does not permanently lock that State to fallback behavior.

## Successful reasoning reuse

A successful exact reasoning request can be reused.

The request fingerprint contains:

- user / plan context
- Decision input fingerprint
- deterministic baseline type/reason/confidence
- normalized candidate set
- requested mode
- router version
- configured Native AI driver/model

If the same successful request is evaluated again:

- OpenAI is not called again
- the existing reasoning run is reused
- the same semantic Decision is reconstructed
- duplicate AI cost is avoided

Provider failures are not cached as success.

## Decision identity vs provider telemetry

Provider/model details are not part of semantic Decision metadata.

Decision identity describes the selected product Decision.

Reasoning telemetry separately records:

- route
- provider
- model
- Native AI run
- latency
- token usage
- estimated cost
- agreement with deterministic baseline

This keeps Decision identity stable when reasoning provenance changes.

## Reasoning observability

V53.3 adds `intelligence_reasoning_runs`.

Stored fields include:

- user / plan when available
- linked Decision trace
- linked NativeAiRun
- domain / scope
- State reference
- Readiness fingerprint
- Decision input fingerprint
- reasoning request fingerprint
- requested mode
- selected route
- provider / model
- status
- deterministic baseline Decision type
- selected Decision type
- baseline confidence
- selected confidence
- agreement with baseline
- fallback state/reason
- candidate count
- latency ms
- input/output/total token counts
- optional estimated USD cost
- controlled router metadata

## Cost observability

Provider pricing is not hard-coded.

Optional environment configuration:

- `CANOVIA_INTELLIGENCE_INPUT_USD_PER_MILLION_TOKENS`
- `CANOVIA_INTELLIGENCE_OUTPUT_USD_PER_MILLION_TOKENS`

If both rates are configured, `ReasoningCostEstimator` stores estimated USD cost from NativeAiRun token usage.

If pricing is not configured, cost remains null while token usage remains available.

This prevents stale provider pricing from becoming product logic.

## Quality observability

V53.3 records whether the selected Decision agrees with the deterministic baseline.

This is **not** itself a quality score.

Agreement/disagreement is only an evaluation signal.

Actual reasoning quality should later be evaluated against:

```text
Decision
→ Action
→ Outcome
→ State delta
```

## ReasonedDecisionOrchestrator

V53.3 adds a full generic path:

```text
StateSnapshot
+ ReadinessEvaluator
+ CandidateDecisionEngine
      ↓
Readiness
      ↓
candidates
      ↓
baseline Decision
      ↓
ReasoningRouter
      ↓
selected Decision
      ↓
DecisionTraceStore
      ↓
ReasoningRun linked to DecisionTrace
```

This is the preferred orchestration point for later domain surfaces that opt into reasoning.

Existing V53.2 `DecisionOrchestrator` remains valid for deterministic-only usage.

## Default behavior

Default reasoning mode is `deterministic`.

Merging V53.3 therefore does not automatically increase OpenAI traffic or cost.

A later feature integration must explicitly configure or request `auto` / `openai`.

## Non-goals

V53.3 does not implement:

- natural-language chat
- AI-generated Tasks
- free-form AI Action invention
- automatic Task mutation
- Study Capture
- Study workload prediction
- Action generation
- Outcome learning
- Developer Readiness
- user-facing reasoning controls
- provider pricing hard-coding

## Next
