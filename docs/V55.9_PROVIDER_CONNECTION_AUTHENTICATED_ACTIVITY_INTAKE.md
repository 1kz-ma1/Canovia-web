# V55.9 Provider Connection / Authenticated Activity Intake

## Goal

V55.9 externalizes the first part of the Execution Ecosystem return path without building a Marketplace or full OAuth platform.

Canonical flow:

```text
Canovia user
→ create external ProviderConnection
→ select that provider for a Plan capability
→ issue short-lived opaque execution_context
→ external provider executes
→ signed provider-neutral Activity request
→ Connection authentication
→ execution_context resolution
→ ExecutionActivity
→ TaskEvidence
→ existing Intelligence
```

The central security rule is:

```text
Provider payload
must not decide
user_id / provider_key / capability / plan_id / task_id
```

Those facts are resolved server-side from the authenticated connection and Canovia-issued context.

## ProviderConnection

New table:

```text
provider_connections
```

Fields:

- user_id
- provider_key
- public_id UUID
- secret_ciphertext
- label nullable
- status
- last_used_at nullable
- revoked_at nullable
- timestamps

Current statuses:

- active
- revoked

A connection belongs to one Canovia user and one concrete external provider key.

## External providers only

Connection creation requires:

```text
provider exists in ExecutionProviderCatalog
AND
provider.enabled = true
AND
provider.kind = external
```

Native providers cannot be converted into ProviderConnections.

This keeps:

```text
Canovia Native execution
!= external account/provider connection
```

## Credential creation

Authenticated browser route:

```text
POST /execution/providers/{providerKey}/connections
```

The route:

- requires Canovia login
- is throttled
- validates the provider through the Provider Catalog
- generates a random 256-bit connection secret
- stores only an encrypted ciphertext in the database
- returns the plaintext secret once in the creation response

The ProviderConnection model hides `secret_ciphertext` from serialization.

The plaintext secret is not stored separately.

## Why encrypted instead of hash-only

The current authentication scheme is HMAC.

Canovia must reproduce the expected HMAC for verification, so the connection secret needs to be recoverable server-side.

Therefore:

```text
plain secret
→ returned once
→ encrypted using Laravel Crypt
→ ciphertext stored
```

This differs from bearer-token verification, where a one-way hash would be sufficient.

## Revocation

Authenticated browser route:

```text
DELETE /execution/provider-connections/{connection}
```

Only the owning Canovia user can revoke the connection.

Revocation records:

- status = revoked
- revoked_at

Revoked connections cannot authenticate Activity requests.

## Stateless provider Activity API

New API route:

```text
POST /api/execution/activities
```

It uses the API route group rather than browser session/CSRF.

Rate limit:

```text
120 requests / minute
```

Maximum raw payload size:

```text
65,536 bytes
```

The raw body is used for signature verification but is not persisted.

## Authentication headers

Required:

```text
X-Canovia-Connection
X-Canovia-Timestamp
X-Canovia-Signature
```

### X-Canovia-Connection

ProviderConnection.public_id.

This ID is public routing identity, not a secret.

### X-Canovia-Timestamp

Unix timestamp in seconds.

Current tolerance:

```text
±300 seconds
```

Requests outside the allowed window are rejected.

### X-Canovia-Signature

Format:

```text
sha256=<64 hex chars>
```

Signing message:

```text
<unix_timestamp>.<raw_request_body>
```

Algorithm:

```text
HMAC-SHA256
```

Verification uses constant-time `hash_equals`.

## Replay model

V55.9 uses two layers:

1. short timestamp validity window
2. existing Activity idempotency

Activity identity remains:

```text
provider_key + external_key
```

An exact signed request replay within the time window cannot create duplicate Activity/Evidence records if the provider uses the same stable external key.

V55.9 does not add a global nonce/delivery table.

That can be added later if a provider contract requires strict once-only delivery semantics beyond idempotent state ingestion.

## Opaque execution context

External providers should not need to receive trusted internal routing fields directly.

Canovia issues:

```text
execution_context
```

as an encrypted, short-lived token.

Authenticated browser route:

```text
POST /plans/{plan}/tasks/{task}/provider-connections/{connection}/execution-context
```

Requirements:

- logged-in Canovia user
- Task edit permission
- Connection belongs to the current user
- current ExecutionResolver-selected provider matches the Connection
- Connection is active
- Provider supports the resolved capability

## Context lifetime

Current TTL:

```text
30 minutes
```

The encrypted context contains internally:

- schema version
- connection public ID
- actor user ID
- Plan ID
- Task ID
- capability
- issued_at
- expires_at

These fields are not returned separately to the external caller.

The external provider receives the opaque token.

## Why context is encrypted

The context serves two purposes:

1. integrity
2. opacity

The external provider should not be trusted to submit:

- a different user
- a different provider
- a different capability
- an arbitrary Task
- an arbitrary Plan

The provider sends the exact Canovia-issued token back.

Canovia decrypts and validates it after Connection authentication.

## Connection-bound context

A context issued for one ProviderConnection cannot be reused with another ProviderConnection.

Validation includes:

```text
context.connection_public_id
==
authenticated ProviderConnection.public_id
```

and:

```text
context.user_id
==
ProviderConnection.user_id
```

This prevents a second valid connection from stealing another connection's execution context.

## Provider availability check

Context resolution re-checks:

- Connection is still active
- Provider still exists
- Provider is enabled
- Provider still supports the encoded capability

Therefore disabling or revoking a provider path stops new authenticated intake even if an old context token still exists.

## Provider-neutral Activity envelope

Current API envelope:

```json
{
  "schema_version": "1.0",
  "execution_context": "<opaque token>",
  "activity": {
    "external_key": "provider-session-123",
    "type": "study_practice_completed",
    "title": "External Practice",
    "status": "completed",
    "started_at": "optional ISO-8601",
    "completed_at": "optional ISO-8601",
    "duration_seconds": 1200,
    "metrics": {}
  }
}
```

The provider does not need to send:

- provider_key
- user_id
- plan_id
- task_id
- capability

If those fields are supplied anyway, V55.9 does not use them as routing authority.

## Activity normalization

`ProviderActivityIntakeService` normalizes the Activity after Connection/context validation.

General normalized fields:

- external_key
- type
- title
- status
- started_at
- completed_at
- duration_seconds

Constraints include:

- bounded lengths
- normalized lowercase type/status
- known Activity status
- valid chronological timestamps
- duration <= 7 days

## Domain metrics

V55.9 does not accept arbitrary metrics into domain Intelligence.

Current first supported domain mapping:

```text
capability = study.practice
type = study_practice_completed
```

Allowed normalized metrics:

- score_percent
- strengths
- weaknesses
- weakness_topics

Study Practice completion requires a valid 0–100 score.

Unknown extra metrics are discarded.

Other Activity types currently store an empty normalized metric set through this provider-neutral API.

This is intentionally conservative.

## Raw payload boundary

The API does not persist:

- raw HTTP body
- signature
- Connection plaintext secret
- execution_context
- caller-supplied routing fields
- arbitrary extra Activity metrics

ExecutionActivity metadata only receives bounded internal intake facts:

- intake_schema_version
- provider_connection_id

## Task association

After context resolution:

```text

→ ExecutionActivityService::linkToTask()
```

The existing V55.6 rules remain authoritative:

- cannot move already-projected Activity to another Task
- cannot link Activity across Plans
- projection is idempotent
- TaskEvidence keeps traceability to ExecutionActivity

## Current ProviderConnection UX boundary

V55.9 provides the authenticated management endpoints needed to create/revoke a connection and issue execution context.

It does not add a polished end-user provider connection management screen.

The first real external provider should determine:

- connection UX

## Security boundaries

V55.9 establishes:

1. External Provider connections are user-owned.
2. Secret is returned once and encrypted at rest.
3. Activity intake is stateless and signed.
4. Signature covers timestamp + exact raw body.
5. Timestamp window limits replay duration.
6. Context binds execution to Canovia-issued scope.
7. Connection and context must match.
8. Provider/capability/user/Task routing is server-derived.
9. Revocation immediately disables authentication.
10. Raw provider payload is not persisted.
11. Arbitrary metrics do not automatically enter Intelligence.
12. Existing Evidence normalization remains authoritative.
