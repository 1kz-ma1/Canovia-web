# V58.61 — Study Adaptive Starting Point / Bookkeeping Grade 3 Foundations

## Why

Do **not** force everyone who mentions bookkeeping to study Grade 3 from chapter one and only then enter Grade 2.

Example:

> 「簿記3級の授業があるので復習をしつつ、余裕があれば2級にも進みたい」

Canovia must first observe the user's current understanding and then suggest an appropriate mixture of reviewing prerequisite topics and trying selected Grade 2 introductory material. User intention can change, and no diagnostic result should prevent the user exploring another grade.

## Current vertical slice

- `AdaptiveStartingPointPolicyService` is domain-independent: it accepts per-topic observed results, prerequisite keys, overall result, and whether the user wants to try more advanced material. It returns an advisory decision only.
- `BookkeepingPlacementDiagnosticService` is an original 12-question mini-check of selected Grade 3 fundamentals (basic entries, receivables/payables, cash/deposits, adjusting entries), grouped 3 questions per topic.
- `BookkeepingPlacementController` is accessible from Study Preparation on a bookkeeping Plan, even when the Plan has no Task. It uses the existing `StudyScoreObservation` model to persist one source-labelled result per explicit form submission, with stable request UUID, current actor, score percent and topic percentages. No migration or new persistence schema is introduced.
- Individual Plan authors and participants see **their own** diagnostic observations only, under existing Plan view/edit permissions.
- The 12-question mini-check is **not** the official Nissho test, not complete Grade 3 coverage, not a Grade 2 competency assessment, and not a Grade 3 pass estimate.
- Diagnostics never directly mark Task completed, increase Task progress, change Plan priorities, create extra Tasks, or enter a new Release Level.

## Decision contract

```text
Not yet observed / incomplete per-topic evidence
    → diagnostic_needed

Any prerequisite topic under 67% (small 3-question topic sample)
    → review_prerequisites

All prerequisite topics >= 67%
+ total >= 83%
+ user explicitly wants to try Grade 2
    → trial_next_grade (advisory; do NOT mark mastered)

Other observed results
    → review_and_verify
```

These thresholds are pilot heuristics, not qualification-grade proficiency standards. Reuse the general policy with different independently validated evidence definitions for other subjects.

An overall 83% with a weak adjusting-entry topic still prioritizes that weakness instead of unconditionally advancing.

The per-topic score and user-selected `_advance_interest` indicator are persisted only as a user-triggered mock exam record with label `Canovia簿記基礎診断` and metric key `bookkeeping_foundations_percent`. Subsequent visits reconstruct the same advisory decision from the saved results.

- **Provenance isolation:** the generic Study Score page and `StudyWorkspaceStateResolver` exclude this metric from external-score-baseline queries. In-app diagnosis does not become an official score or a Task completion.
- After grading, the learner may see correct-answer explanations and topic-specific next actions, then explicitly edit Plan Tasks. No automatic Task mutation occurs.
- `request_id` uniqueness is reused with `createOrFirst` for retry races; cross-Plan or cross-actor UUID reuse returns 409.

## Next slices before full Bookkeeping launch

1. Real Grade 3 **structured journal entry input** (multiple debit/credit rows, account selection, numeric totals, deterministic grading, balanced-entry validation, explained mistakes), not only four-option selections.
2. Enough versioned, reviewed original/appropriately licensed practice content across the official Grade 3 syllabus; actual Grade 2 topic graph and curated sample questions.
3. A **concept dependency graph** binding weak Grade 3 prerequisites to chosen Grade 2 units, with repeat observations and retention checks; one 12-question attempt alone may only recommend a trial, never certify mastery.
4. Learner's durable goal context for classes vs exam deadline vs Grade 2 stretch, then a non-destructive Plan/Task update proposal with explicit acceptance.
5. Manual mobile/desktop verification and release review before opening beyond current Study level.

## Risk / merge review

Although no migration is introduced, V58.61 adds a **new persisted assessment source** into `study_score_observations` that later Study features can consume. Review implications before deciding whether to merge this PR under the new deployment policy. CI success by itself does not approve a new user-facing assessment's content accuracy.
