# V58.0 Developer Workspace Focused Surfaces

## Goal

V58.0 changes Developer Workspace from one long information feed into focused,
switchable work surfaces.

The governing UX rule is:

> one screen = one information / operation lineage

The old Developer Home showed orientation, Next Action, GitHub Activity, active
Tasks, Release Readiness, detailed Execution Context and history in one vertical
page. That was useful for discovering the feature set, but noisy for daily use.

V58.0 keeps the same underlying Development Intelligence and GitHub contracts,
while changing only how the information is projected.

## Surface navigation

Developer Workspace exposes five server-rendered surfaces:

```text
今やること
リポジトリ
チーム
改善
プレビュー
```

The selected surface is represented by the query parameter:

```text
?surface=work
?surface=repository
?surface=team
?surface=improvements
?surface=preview
```

Unknown values fall back to `work`.

The selected Plan is kept in `plan_id`, and changing Plan preserves the
current surface.

Only the selected surface is rendered into the page DOM. V58.0 does not hide
four large panels with client-side CSS.

## Compact Developer shell

The old daily-use hero is removed.

The Developer shell now contains only:

- compact Developer identity
- current Development Plan selector
- five focused surface tabs

First-use explanation remains available through the existing Workspace
onboarding contract rather than occupying permanent daily screen space.

## Work surface

`work` is the default.

It contains the information required to continue development now:

- Next Action
- Current Focus
- primary action CTA
- optional reason
- active Tasks

Detailed Execution Context and the V57.6 Implementation Brief remain available,
but move behind:

```text
実装コンテキスト・Brief
→ 必要なときだけ開く
```

The rest of the active Task list is also collapsed by default.

This preserves V57.4–V57.8 behavior while reducing routine scroll length.

## Repository surface

`repository` answers:

- what is in this repository?
- what changed recently?
- what still needs Task association?
- what is the current Release state?

### Directory tree

The tree is fetched only when the Repository surface is explicitly opened.

Flow:

```text
connected Repository Artifact
→ exact GitHub App installation
→ short-lived installation token
→ Repository metadata
→ default branch commit
→ Git tree SHA
→ recursive Git tree
→ bounded path projection
```

Required permission:

```text
Contents: read or write
```

The tree reader does not fetch file contents.

Canovia receives only bounded metadata:

- path
- directory / file type
- depth
- file size where GitHub exposes it
- GitHub web URL

Default display limit is 320 entries and the server hard limit is 500.

The tree projection is response-only. It is not persisted to:

- PlanArtifact metadata
- TaskEvidence
- Development Intelligence snapshots
- a new repository-tree table

Private Repository access continues through the existing GitHub App
installation path.

### Activity and Release detail

Recent GitHub Activity is shown compactly next to the tree.

The existing full Activity → Task association controls remain available in a
collapsed detail surface.

Release Readiness and the existing seven Quality Gates also remain available in
a collapsed detail surface.

No GitHub operation or Release decision contract is replaced.

## Team surface

`team` uses existing collaboration facts:

- Plan owner
- Plan memberships
- owner / editor / viewer role
- explicitly assigned PlanArtifacts
- Tasks linked to those explicitly assigned artifacts
- latest Plan activity by member

V58.0 deliberately does not infer a Task owner from activity, commit author,
branch name or AI similarity.

If no explicit assignment fact exists, the UI says so.

Existing collaboration member management is reused under a collapsed Management
section when collaboration is enabled.

This gives the surface useful current-state visibility without inventing a new
team-assignment model.

## Improvements surface

`improvements` is deterministic in V58.0.

Candidates are derived from existing facts such as:

- GitHub connection not ready
- unresolved GitHub Activity
- failed / pending / unknown Release Gates
- paused development Tasks

No AI call is made simply by opening the surface.

Each candidate links back to the surface where the user can act on the issue.

Decision / Action / State history remains available under a collapsed history
section.

Future AI-generated improvement proposals can be added later behind an explicit
invocation boundary.

## Preview surface

V58.0 adds an optional Development Preview URL.

It is stored as a dedicated PlanArtifact:

```text
provider      = external
artifact_type = link
external_id   = canovia:development-preview
```

Only `http` / `https` URLs are accepted.

The configuration controller rejects:

- localhost
- `.localhost`
- `.local`
- private / reserved IP literals

The server does not fetch the preview URL, so configuring the preview does not
create an SSRF fetch path.

### Explicit load

The iframe has no `src` on page load.

The user must press:

```text
プレビューを読み込む
```

before the browser assigns the URL to the iframe.

The frame is sandboxed without `allow-same-origin`:

```text
allow-scripts allow-forms allow-popups allow-modals
```

Some sites reject embedding with `X-Frame-Options` or CSP
`frame-ancestors`. Therefore the Preview surface always keeps an
`外部で開く` fallback.

Canovia does not attempt to bypass remote framing policy.

## Remote-read boundary

Opening the default Work, Team, Improvements or Preview surface does not trigger
a Repository tree read.

The GitHub tree API is called only for an explicitly selected Repository surface
when:

- a Repository Artifact exists
- Developer GitHub Evidence access is allowed
- the GitHub App connection state is ready

This keeps routine Developer Home navigation lightweight.

## State mutation boundary

Simply switching surfaces does not change:

- Task progress
- Task status
- remaining minutes
- Release Gate state
- GitHub state
- Development Evidence

The Preview configuration is the only new persistent mutation in V58.0, and it
stores only the user-selected preview link artifact.

## Follow-ups

Useful later phases include:

- explicit Development Task assignee / status-sharing model
- authoritative Deployment environment URL → Preview suggestion
- repository sub-tree lazy navigation for very large repositories
- explicit AI improvement-analysis action, rather than automatic AI on page GET
