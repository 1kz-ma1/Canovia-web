## 0. 公開の目的と対象

初回公開の目的は機能一覧を見せることではない。**学習・開発で、目標→現在地→計画→次の行動→実行記録→再計画という一連の価値を無料で体験できるか検証すること**。複雑なMap/宇宙UIや将来構想の再現度では判定しない。

チャネルは別の意思決定とする。
- **Closed alpha**（推奨する最初の配布単位）：招待した少人数（仮に5名）のテスターに限定。必要に応じて「学習のみ」または「開発のみ」に絞れる。ユーザー実データを扱う場合は公開同様の認可・DB・復旧管理が必須。
- **Public early access Web**：無制限参加に耐えられる運用、規約・プライバシー・利用制限・インシデント対応が揃った後。Alpha成功だけで昇格しない。
- **iOS/TestFlight/App Store**：配布手段を明確化して別受入。WKWebViewでWeb更新が即時反映する場合は、既存のiPhoneユーザーに影響するWebリリースでも物理iPhoneスモークが必要。ネイティブの署名・課金要件は公開チャネルで別判定。

**候補選定と公開許可は別ゲート**。選定（scope selection）は「追加監査を受ける固定SHAを選ぶ」だけ。GOは後段の独立した認可判断であり、自動点数化しない。

## 1. 必須の製品循環（選定のP0条件）

以下が新規ユーザーに対してFree Pathで成立し、再ログイン・中断復帰しても記録が壊れないこと。

| Gate | 実利用シナリオ | 観察可能な合格条件 |
| --- | --- | --- |
| P0-01 入口 | 新規登録、Guest→Accountも想定 | 本人のPlanとUI状態が整合し、403/500/別ユーザーData表示がない |
| P0-02 現在地 | 目標を入力、既知情報を再利用 | 最低限の質問で実行可能なPlanを生成。AI停止時も公開対象のdeterministic/manual fallbackが使える |
| P0-03 今日の行動 | 再ログイン、Home/専用UI復帰 | 「今すべきこと」が一つ明示され、誤った画面への復帰や重複・失効したTaskの再提示がない |
| P0-04 実践 | 手動または専門実行導線を使う | 1件の実作業が行え、実行にAI/有料権限の強制はない |
| P0-05 実績 | 回答・WorkLog・TaskEvidence保存 | 保存結果が正しいPlan/Taskへ確定し、画面更新・再ログイン後に保持。二重POSTは二重記録しない |
| P0-06 適応 | 正解/間違い、実作業/状況変更を登録 | 事実とAI推論を分離し、次の行動が見直される。AI提案は無断で公開・完了・権限を変えない |
| P0-07 Free | 新規Freeユーザーが一周する | 基本の一連の操作を課金なしで達成。プレミアムのみの機能を説明なしに要求しない |
| P0-08 可観測性 | 非機密の操作成功/失敗 | 初回Plan→最初の実行→実績→次Actionを集計でき、個人情報や生成内容の過剰記録はしない |

**提案する定量的受入目標**（未計測・推奨値であり過去実績ではない）：
- 初回目標入力から実行可能なTask提示まで、観察テスター5名のうち**4名以上が10分以内、補助なし**。
- **5名全員**が作業の保存・再ログイン後の再表示を確認できる。データ喪失・権限逸脱は**0件**。
- 実行→次Actionの繋がりをテスターが自分の言葉で説明できるかを記録。5名中4名を初期目標とし、達成未満はオンボーディング/価値仮説を改めて検証する。
- これらは**製品体験の実ユーザー受入**であり、CIだけでPASSにしてはならない。

### Domainごとの必須シナリオと縮小規則

**学習**（公開する場合）：
1. 科目・試験/範囲と現在の理解度を設定し、今日やる問題/復習に辿り着く。
2. 公開で対応を明示した形式（例：単一選択、数値入力）の問題を解く。採点・解説・保存・途中再開が一連に動く。
3. 不正解や未理解が記録され、次回の復習/行動に反映。問題の正しさ・問題権利/出典・AI生成失敗時fallbackを確認。
4. 公開していない形式や問題源を「対応済み」と表記しない。学習領域だけがP0を通れば**学習限定Alpha**を選択可能。

**開発**（公開する場合）：
1. GitHubとの連携状態・権限範囲が明確で、未接続でも誤って進捗自動反映を約束しない。
2. Plan/Taskと実際の作業記録を紐づけ、手動Evidenceから次の行動を再構成できる。
3. PR/Issue/Commit連携を表に出す場合は、実GitHubリポジトリ・正しいユーザー権限・重複・取り消し・失効をE2E確認。未完成なら機能Flagと導線を閉じ、手動Evidenceを正式なfallbackとして表示。
4. 開発領域だけがP0を通れば**開発限定Alpha**を選択可能。

**両領域の同時公開は、両領域が独立にP0を通過した場合だけ**。未達領域はナビだけ隠すのではなく、直URL/API/entitlementの認可も再確認する。

## 2. 候補選定時の必須条件 — Selection Ready（GOではない）

- **Scope固定**：公開するドメイン/チャネル/Free機能/非公開の機能フラグと、「この候補の何がユーザー価値か」を1ページで示す。利用者に何を約束するかを明示。
- **事実の正確性**：対象のGit commit 40桁SHA、候補`release/*`、GitHub `production`との差分、既存候補からの未収録差分、すべての変更マイグレーションと依存関係を固定。V6.0/V6.1のローカルGit全件監査を実際に走らせ、truncated APIを全件と誤認しない。
- **P0機能の存在**：上表の必須循環に対する実装パス/CI/実機受入計画を対応付ける。不足機能は収録・修正するか、公開スコープを縮小。旧候補をCI成功だけで採択しない。
- **既知重大欠陥がない**：データ漏洩、他ユーザーへの権限横断、記録消失、誤自動確定、再ログイン不能、不可逆移行失敗は**1件でもSelection BLOCK**。P0の主要体験を止める不具合も同様。
- **依存関係が分かる**：古い候補に新しいmainの安全性修正が含まれない場合、当該修正の依存関係を確認し、欠落を許容しない。逆に`main`上の多数の機能をFeature Flagで隠してもDB/サーバー側変更は消えない。
- **実施可能性**：選定後に必要な全MySQLの移行リハーサル、Aiven metadata/ledger監査、バックアップ/復元リスク評価、Render/iPhone/Web受入に対し責任者と実行可能な手順がある。

選定結果には `SHORTLISTED_NOT_APPROVED`, `BLOCKED`, `NOT_ASSESSED` など人間向けの状態だけを用い、ソースコードのCI経由でproduction GOへ自動昇格しない。

## 3. 本番公開の必須条件 — Production GO（別承認）

- **完全な変更範囲とDB**：確定した`release/*`SHAで**全未適用 migration**がAiven実測ledger/物理スキーマと一致。MySQL 8.0/8.4使い捨てCI、既存行保持、旧アプリ互換、リカバリと所要時間を確認。想定外のDDL/未反映/partial DDLはSTOP。
- **実環境の本人性**：対象Render Live service/owner/branch/実稼働SHA、DB URLの実効接続先/権限、session/CSRF、worker、OAuth/MCP/AIのFeature Flagを証拠付きで確認。GitHub branchが同じでもRender Liveの証拠と見なさない。
- **バックアップと復元**：Aivenバックアップの有無・鮮度、実行可能な復旧手段・見積もり、**隔離復元の成否**を分けて記録。実ユーザーデータを扱う公開では復旧可能な運用手順が必要。限られた合成データの閉鎖テスト等で隔離復元を実施できない場合は、対象データと残余リスクを厳密に限定しオーナーが別途明示判断。PR #513のバックアップ存在報告を復元成功と扱わない。
- **回帰・セキュリティ**：全必須CI完了、Plan間情報漏れ0件、権限突破0件、記録消失0件。重大バグ（S0/S1）0件。S2は公開対象の循環を妨げず、既知制限/代替手段が明示されるものに限りオーナー判断。
- **Web/iOS実機**：公開チャネルの実ブラウザで新規登録→価値循環→ログアウト/再ログイン→再開を成功確認。Live Webを既存iOS WKWebViewが読む場合は物理iPhoneでも実施。AI停止、低速・失敗時、ファイル/外部リンク、403/419/429で誤操作/個人情報流出がない。
- **運用**：誤操作や5xx、AI API費用、Free利用限界、ユーザーフィードバックと監視責任者、公開停止/アプリ画像ロールバック手順を確定。
- **明示的な公開承認**：Protected `release/* → production` PR、必要なPromotion Policy/MySQL/Workspace/Recoveryチェック、オーナーの別途明示的GO、**merge commit**。初回はRender Auto Deploy OFFのまま、独立して承認された手動デプロイ。CI・GitHub PR・監査パケットの`exit 0`をGOに転用しない。

**時点の区別**：初回デプロイ前に確認できるもの（旧Live SHA、バックアップ、CI、DDL計画）と、デプロイして初めて確認できるもの（**新**Live SHA、実際の新環境でのログインや物理iPhone）を分離する。後者は**承認済み限定リリース→実測→拡大GO**のゲートとする。事後検証完了前に無制限公開にしない。

## 5. 初回Alpha後の評価（選定条件と混同しない）

招待者5名はあくまで**初期の検証規模案**。開始後に計測：
- 最初の行動提示・実行・記録のファネルと離脱段階
- 7日以内の自然な再利用と、何が再訪理由だったか
- 誤ったPlan/Taskへの保存、データ再利用失敗、復帰失敗
- 望まないAI質問、説明を求めたポイント、対応時間とAI原価

**4/5初回価値到達**を次の改善判断に使うことはできるが、単独で本番一般公開や支払い開始を自動許可しない。実装の品質が高くても価値仮説が弱ければ、体験を見直す。
