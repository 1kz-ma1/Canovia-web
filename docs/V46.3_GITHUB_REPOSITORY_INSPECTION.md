# V46.3 GitHub Repository Inspection

## Goal

Repository URLをCanoviaへ貼ったとき、URLカードだけではなく、
GitHub上の現在構造をread-only snapshotとして取得し、
V46.2 Repository Overviewへ重ねて表示する。

対象はまず公開Repository。

```text
Repository URL
    ↓
Canovia Repository Root
    ↓
GitHub read-only inspection
    ↓
Branch / Open PR / Issue / recent Actions
    ↓
Repository Overview
```

Canovia workflow stateとGitHub remote stateは引き続き分離する。

## Capability boundary

remote inspectionは既存FeatureKey:

`developer_github_evidence`

を利用する。

Manual GitHub Workflow Hub / Repository RootはFree pathのまま。
GitHubから構造を取得して転記摩擦を減らす部分だけをDeveloper capabilityとする。

新しいFeatureKey / Productは追加しない。

## Capture flow

Repository URLをQuick Captureすると:

1. PlanArtifactを先に作成
2. Repository Rootとして保存
3. userがDeveloperGithubEvidenceを利用可能ならGitHub inspectionを試行
4. 成功時だけ `metadata.github_repository_snapshot` へsnapshot保存
5. API失敗時もRepository capture自体は成功

これにより外部API障害やrate limitで入力を失わない。

PR / Issue / Branch URLのcaptureでは自動inspectionしない。

## Manual refresh

Repository Overviewから:

`GitHubから更新`

を実行できる。

必要条件:

- repository Artifact
- Plan edit permission
- DeveloperGithubEvidence entitlement

refreshでは現在のsnapshotを置き換えるが、
Task / Plan / Canovia workflow state / Evidenceを自動変更しない。

Repository Rootに古い `github_workflow_state` が残っている場合はrefresh時に除去する。

## GitHub REST snapshot

`GitHubRepositoryInspector` はbounded requestだけを行う。

取得:

- repository metadata
- branches: 最大12
- open pull requests: 最大12
- open issues: 最大12
- recent Actions runs: 最大10

Repository metadata:

- description
- default branch
- language
- visibility
- archived / fork
- stars / forks
- open_issues_count
- updated_at / pushed_at

Snapshot:

```text
metadata.github_repository_snapshot
  version
  source = github_rest
  repo_full_name
  fetched_at
  rate_limit_remaining
  repository
  branches[]
  pull_requests[]
  issues[]
  actions_runs[]
  limits
  warnings[]
```

GitHub Issues APIはPRも返すため、
`pull_request` keyがある項目をIssue一覧から除外する。

## Remote status boundary

Snapshotは取得時点のGitHub fact。

Canoviaの:

- 今やる
- レビュー待ち
- 修正必要
- マージ待ち
- 完了

をremote statusから自動変更しない。

例:

- PRがopenだからreviewにする
- Actions failureだからchangesにする
- mergedだからdoneにする

はV46.3では行わない。

将来automationを追加する場合もsuggestion / human confirmation boundaryを別途定義する。

## UI

Repository Overviewに `GITHUB NOW` を追加する。

表示:

- description
- default branch
- language / visibility
- Branch一覧
- Open PR
- Open Issue
- Recent Actions
- pushed_at
- snapshot fetched_at
- API warning

従来のCanovia側表示も残す。

```text
GITHUB NOW
  GitHubから取得した現在構造

CANOVIA REFERENCES
  Canoviaへ明示登録したURL

CANOVIA FLOW
  ユーザーが決めた作業状態

CONNECTED WORK
  Task / Artifactとの接続
```

GitHubとCanoviaの状態を同一視しない。

## Authentication / private repositories

V46.3はper-user GitHub OAuth / GitHub App installationをまだ実装しない。

公開Repositoryはtokenなしで取得できる。

optional:

`GITHUB_READ_TOKEN`

をserver-side service tokenとして設定できる。
用途は主にrate limit緩和であり、ユーザーごとのprivate repository権限として扱わない。
tokenがprivate repositoryへアクセスできる設定でも、Canovia側で `private=true` / 非public visibilityを拒否し、snapshotへ保存しない。

Private Repositoryを404等で取得できなかった場合、
Repository Rootは残して「GitHub接続が必要」と表示する。

## Security

- arbitrary URLへrequestしない
- github.com URLからparse済みのowner/repoだけをGitHub API pathへ使う
- owner/repoを再validationする
- API responseのhtml_urlもgithub.comのみUI linkとして採用
- tokenをsnapshot / log / metadataへ保存しない
- remote responseからCanovia canonical mutationしない
- bounded list size
- short connect / request timeout

## Evidence boundary

GitHub snapshot refresh自体はTaskEvidenceを作らない。

理由:
Repository全体を取得したことと、
あるTaskが実際に進んだことは別事実だから。

将来:

```text
GitHub authoritative event
  ↓
Task mapping candidate
  ↓
human / deterministic validation
  ↓
TaskEvidence
```

の境界を追加する。

## Non-goals

- per-user GitHub OAuth
- GitHub App installation
- private repository user access
- webhook
- background polling
- automatic lane mutation
- automatic Task progress
- remote objectを全件PlanArtifact化
- GitHub操作（merge / review / branch create等）
