# V56.18 Study Scenario Lab

## Goal

Provide an Admin-only QA surface that can generate realistic Study Plans for learning types the product owner cannot personally reproduce in everyday use.

The Lab is not a user-facing simulation feature.

It creates ordinary Canovia Study data owned by the current Super Admin, then opens the normal Study Workspace so the real State First stack can be validated.

## Access boundary

Routes live under:

```text
/admin/study-scenarios
```

They require:

1. existing `admin.access` middleware
2. `CANOVIA_STUDY_SCENARIO_LAB_ENABLED=true`

If the flag is false, the Lab returns 404 even for Super Admin.

This allows Render / iOS WKWebView validation without exposing the Lab to normal users.

## Fixture tracking

Add `study_scenario_fixtures`:

- user_id
- plan_id
- scenario_key
- scenario_version

Unique:

```text
user_id + scenario_key
```

Scenario Plans are normal Plans. The fixture table only marks which Plans are safe for the Lab to replace/delete.

The Lab never deletes a Plan without a matching fixture row owned by the current Admin user.

## Mutation semantics

### Create / recreate

Creating a scenario:

1. locate the current user's fixture for the scenario key
2. if present, delete only that fixture's Plan
3. cascade-delete the fixture Plan's dependent Study rows
4. create a fresh ordinary Plan / Task / Study state
5. create the fixture marker
6. redirect to the normal Study Workspace

No provider or AI calls are made.

### Delete one

Delete only the fixture-owned Plan for the current Admin user.

### Delete all

Delete only Plans referenced by the current Admin user's Study Scenario fixtures.

Real user Plans are never matched by title/category and are not deleted.

## Lab UI

Each card shows:

- scenario label
- Learning Type
- preloaded state
- expected primary surface / method
- current fixture status

Actions:

- Create & Open
- Open existing
- Recreate
- Delete

The Lab page itself must not create or mutate data on GET.

## Scenario data principles

Fixtures use normal application models:

- Plan
- Task
- StudyPracticeAttempt
- StudyScoreObservation
- StudyRecallItem

No fake UI-only state is injected.

This is deliberate: the normal Study Workspace must derive its state exactly as it would for real users.

## Validation

At minimum:

1. disabled flag returns 404 for Admin.
2. enabled Lab remains forbidden for non-Admin.
3. GET does not create any Plan/fixture.
4. AP current creates 3 Practice Attempts.
5. AP repeated gap renders Resource Study.
6. TOEIC baseline-known renders 480 / target 600 / gap 120 and separate Practice accuracy.
7. TOEIC baseline-missing still asks for external score despite Practice history.
8. school-test fixture has previous score but no Scope and renders Scope Organization.
9. memorization fixture creates due Recall items and renders Recall.
10. skill fixture has no Evidence and renders Practical Evidence.
11. ambiguous fixture renders Learning Type confirmation.
12. recreating one scenario replaces only its previous fixture Plan.
13. delete-all never deletes a real non-fixture Plan.
14. existing V56.17 / V56.16 / V56.15 / V56.14 / V56.13 regressions remain green.

## Non-goals

V56.18 does not:

- generate production demo data for users
- simulate external provider APIs
- bypass Study policies
- create fake front-end-only state
- change Study routing rules
- add AI traffic
