# V58.68 — Owner-corrected persistent Plan Domain

## Context

Legacy `Plan.category` conflates the subject of the project ("制作活動", "個人開発") with the Workspace that should render it. A real software development collaboration such as HINANEX was filed under "制作活動" and could not enter the normal Development Workspace without a temporary V58.63 session-specific rescue.

V58.67 allows conservative category inference for newly created Plans. V58.68 adds an **explicit persisted owner correction** without changing existing Plan categories or team collaboration.

## Data contract

- New column: `plans.workspace_domain_override`, nullable VARCHAR(24), default NULL. No backfill or rewrite of existing data.
- Supported values when explicitly chosen: `study`, `development`, `career`, `creative`, `general`. NULL means automatic legacy category profile.
- `PlanCategoryProfileService::forPlan` resolves the owner's override, if present, ahead of the existing `category` mapping. `forCategory` remains unchanged for backward compatibility.
- `is_collaborative` / Plan member roles remain independent from domain. Selecting Development never makes a Plan shared or changes membership.
- The owner uses `Plan edit → どのWorkspaceで扱いますか？` to set the correction. `Canoviaに任せる` removes the override and reverts to normal category mapping.
- Only the Plan owner can save an override (existing `PlanOwnershipService::authorizePlan`), not a shared editor/viewer. Legacy edit submissions without the new key leave the value unchanged.
- A conscious selection in the edit form also clears the *current actor's* old V58.63 per-browser exception to avoid stale UI state. It cannot reset another collaborator's voluntary per-browser preference.
- All downstream domain-sensitive systems using `forPlan` see the effective profile, including its Roadmap renderer and Development Intelligence. This is why the change requires full regression and does not silently rewrite any Plan.
- An owner override is a **user-confirmed product-domain choice**, not AI proof that Release Readiness requirements are satisfied.

## Risk and release gate

This PR adds a non-destructive nullable migration and changes the effective domain interpretation of a Plan **only after its owner explicitly edits it**. It does not backfill legacy Plans. It also introduces a potentially broad downstream effect by reusing `forPlan`; green cross-surface CI and thorough owner/viewer authorization tests are required.

The user has explicitly authorized merging all tested PRs for the ongoing implementation run. This authorization does **not** permit bypassing required CI, branch protections or claiming Render deployment was verified.

## Remaining P1.1 work

Persisted `specialization` (beyond the V58.67 inferred hint), richer owner-configurable roles and true team-specific Task ownership/dependency presentation remain future slices. Domain and collaboration are now separately modeled, but the full 3-axis product model is **not finished**.

Test suite: `tests/Feature/PlanDomainOverrideV5868Test.php`, plus the existing Development Creative rescue, Workspace routing and Plan creation CI suites.
