# V46.4 GitHub App Review-only Write Layer

## Goal

GitHubの操作を理解している人がチームに1人しかいなくても、
その人がRepositoryへCanovia GitHub Appを一度installすれば、
他のCanovia EditorはGitHub用語やCLIを直接扱わずに変更をレビューへ出せるようにする。

```text
Repository admin
  └─ Canovia GitHub Appを1回install
            ↓
Canovia Editor
  └─ 変更内容を明示して送信
            ↓
Canovia GitHub App
  ├─ default branchから canovia/* branch作成
  ├─ 1 fileをcommit
  └─ Pull Request作成
            ↓
Canovia
  └─ レビュー待ちArtifact
            ↓
Human review / GitHub merge
```

V46.4は「Canoviaがmainへ自動反映する機能」ではない。
GitHubへの変更は必ずreview-only PRとして止める。

## Authentication

個人Personal Access Tokenを共有しない。

server-sideにGitHub App credentialを保持する。

- `GITHUB_APP_ID`
- `GITHUB_APP_PRIVATE_KEY` または `GITHUB_APP_PRIVATE_KEY_BASE64`
- optional `GITHUB_APP_INSTALL_URL`

実行時:

1. App ID + Private Keyから短寿命JWTを作成
2. `GET /repos/{owner}/{repo}/installation` でそのRepositoryへのinstallationを確認
3. installation access tokenを発行
4. その一時tokenだけで対象Repositoryへwriteする
5. tokenをDB / metadata / logへ保存しない

GitHub Appに必要な最小permission:

- Metadata: read
- Contents: read & write
- Pull requests: read & write

Actions / Administration permissionは要求しない。

## Capability boundary

GitHubへのwriteはread-only inspectionと分離する。

- `developer_github_evidence`
  - Repository snapshotなどの外部取得
- `developer_github_write`
  - Branch / Commit / Pull Request作成

`developer_github_write` はFreeではdenyし、
Developer Packへmappingする。

これによりread accessを持つだけのactorがGitHubへwriteできない。

## Human authorization

write実行には以下をすべて要求する。

- authenticated Canovia user
- 対象Planへのedit permission
- `developer_github_write` entitlement
- 明示登録されたRepository Artifact
- 対象RepositoryへCanovia GitHub Appがinstall済み
- ユーザーによる明示submit

GitHub App installation自体はGitHub Repository管理者が行う。

GitHubに詳しい人の個人accountを他メンバーへ共有しない。
GitHub上の実行主体はGitHub App、Canovia上の依頼主体はCanovia userとして分離する。

## Write contract

V46.4の最小vertical sliceは1回につき1 file。

ユーザー入力:

- file path
- fileの完全な新内容
- commit message
- Pull Request title
- optional Pull Request body

CanoviaはGitHub APIから毎回authoritativeなdefault branchを取得する。

その後:

1. default branch refを取得
2. 対象fileが既存か確認
3. `canovia/YYYYMMDD-HHMMSS-xxxxxx` branchを新規作成
4. 既存fileならSHA付きupdate、新規pathならcreate
5. そのbranchからdefault branch向けPull Requestを作成

base branchやtarget branchをuser入力させない。
main / default branchへ直接PUTしない。

## Protected operations

V46.4では実装しない:

- default branch direct push
- force push
- merge
- branch delete
- file delete
- repository settings change
- collaborator / permission change
- release publish
- tag create
- Actions workflow write

`.github/workflows/**` はfile write対象として明示拒否する。

GitHub ActionsはPR branch上のcodeによって動作する場合があるため、
PR作成自体を安全の終点とはみなさず、人のreviewを必須とする。

## Size / scope limits

- 1 request = 1 file
- file content max 200KB
- file path max 240 chars
- PR body max 20,000 chars
- write endpoint max 3 requests / minute

multi-file change / patch apply / binary uploadはV46.4では扱わない。

## Canovia projection after success

Pull Request作成まで成功した場合のみ、
CanoviaへPR Artifactを作る。

```text
PlanArtifact
  provider = github
  artifact_type = link
  url = GitHub PR URL
  github_workflow_state = review
  github_write_origin
    repository_artifact_id
    requested_by_user_id
    executed_by = github_app
    base_branch
    branch
    file_path
    file_action
    commit_sha
    created_at
```

Repository Root metadataには最新writeの要約だけを
`github_last_write` として保持する。

collaborative PlanではPlanActivityへ
`github_repository_change_proposed` を記録する。

## Evidence / progress boundary

PRを作成しただけで:

- Task progressを変更しない
- Plan progressを変更しない
- TaskEvidenceを自動生成しない
- Taskをdoneにしない

PRが存在することはGitHub上のauthoritative factだが、
どのTaskの達成Evidenceとして扱うかは別契約とする。

将来はGitHub event → Task mapping candidate → human / deterministic validation → Evidenceの順で接続する。

## Failure semantics

GitHubはremote systemなのでDB transactionで全操作をrollbackできない。

Branch作成後にfile commitやPR作成が失敗した場合、
作業用BranchがGitHub側に残る可能性がある。

V46.4では自動branch deleteを行わない。
エラーmessageでRepository確認を促し、
Canovia PR ArtifactはPR作成成功後にだけ作成する。

Repository App未installの場合はbranch作成前に停止する。

## Private repositories

V46.3のservice-owned read tokenはpublic inspection専用のまま。

V46.4 Write Layerは別で、
Repository管理者がGitHub App installation時に明示的に対象Repositoryへ権限を与えた場合、
installation tokenのscope内でprivate Repositoryにもwriteできる。

これは個人account credentialの共有ではない。

## UI

Repository Overviewに `REVIEW-ONLY WRITE` surfaceを追加する。

GitHub用語を知らないEditor向けには:

- 「変更するファイル」
- 「ファイルの新しい内容」
- 「変更メモ」
- 「レビュー用タイトル」
- 「変更をレビューに出す」

をprimary languageにする。

補足としてCanoviaが内部で:

```text
Branch
 -> Commit
 -> Pull Request
 -> レビュー待ち
```

を行うことを示す。

## Execution Orchestration boundary

V46.4ではAI / Execution Packetから直接GitHub writeしない。

将来:

```text
Execution result
  ↓
GitHub change candidate
  ↓
Human confirmation
  ↓
GitHubRepositoryWriter
  ↓
Pull Request
```

として接続できる。

AIが生成した内容であっても、
write boundaryを通過する前にuser confirmationを要求する。

## Non-goals

- GitHub OAuth user identity
- PAT storage / sharing
- AI autonomous repository write
- multi-file commit
- patch/diff apply
- binary file upload
- branch deletion
- merge
- review approval
- webhook
- background polling
- automatic Canovia lane synchronization
- automatic Task progress / completion
