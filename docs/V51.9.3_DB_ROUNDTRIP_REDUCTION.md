# V51.9.3 DB Connection & Query Roundtrip Reduction

## 背景

V51.9.2をproductionへ反映後、iOS PWA実機で再計測した。

Client side:

- Home cache hit: 92ms
- Constellation cache hit: 73ms
- Long Task: 0
- Layout Shift: 0

UI mount / renderは主因ではない。

Server side:

- Home: 2.55〜2.82s / 23 queries
- Execution: 1.51s / 13 queries
- Timeline: 1.79s / 16 queries
- Core Bundle: 1.14s / 9 queries
- Constellation overview: 0.86s / 7 queries

各requestで最初のusers SELECTが約275〜295ms、その後の単純SELECTは約78〜85msだった。

これは:

1. requestごとのMySQL connection setup固定費
2. Render Singapore ↔ remote MySQL間のquery roundtrip

が支配的であることを示す。

V51.9.3はDB migrationやDB provider移行を行わず、まず接続再利用と明確なrelation N+1を削減する。

## 1. Opt-in persistent PDO

MySQL / MariaDB connection optionsへ:

`PDO::ATTR_PERSISTENT`

を環境変数 `DB_PERSISTENT` で有効化できるようにする。

default:

`DB_PERSISTENT=false`

productionのみtrueを設定する。

PHP-FPM workerが同じremote MySQL connectionをrequest間で再利用できる場合、毎request最初のqueryへ乗っているconnection setup costを削減できる。

### Boundary

persistent PDOはconnection stateをworker内で再利用する。

Canoviaはrequest単位でcustom SQL session variables / temporary tables / manual transaction stateを保持しない前提を維持する。

rollback:

`DB_PERSISTENT=false`

DB schema / credentials / source of truthは変更しない。

cold worker / deploy直後は新規connectionが必要なため、persistent connectionはすべてのrequestからsetup costを完全に消す保証ではない。

## 2. Execution availability batch

Production Execution request:

- total queries: 13
- plan_availability_rules: 3 queries
- plan_availability_overrides: 3 queries
- availability total: 約499ms

原因:

`UserStateService` / `RecommendationService` から `PlanProgressService::calculate()` がPlanごとに呼ばれ、その内部 `loadMissing()` がavailability relationをPlan単位で取得していた。

NavigationControllerでowned Plans取得時に:

- availabilityRules
- availabilityOverrides

をeager loadする。

Plan数に関係なくavailability SELECTは各relation 1回にする。

Recommendation / progress semanticsは変更しない。

## 3. Timeline availability batch

Production Timeline request:

- total queries: 16
- plan_availability_rules: 3 queries
- plan_availability_overrides: 3 queries
- availability total: 約499ms

`AchievementProjectionService::isCompleted()` が各Planに対して `PlanProgressService::calculate()` を呼ぶため、Timelineでも同じN+1が発生していた。

TimelineのCoreContext featuresへ `availability` を追加し、全Plan分をrelationごとに1 queryでbatch loadする。

Core BundleではCalendarが既にavailabilityをloadしているため、Shared CoreContextにより追加queryは発生しない。

## 4. Regression contract

Feature testで4 Planを作成し:

- Execution plan_availability_rules SELECT = 1
- Execution plan_availability_overrides SELECT = 1
- Timeline plan_availability_rules SELECT = 1
- Timeline plan_availability_overrides SELECT = 1

を固定する。

DB persistent optionはsource contractとdefault-off configを固定する。

## 5. Next decision

V51.9.3 production反映後に以下を再計測する。

- first users query max_ms
- Home total db_ms
- Execution availability query count / db_ms
- Timeline availability query count / db_ms
- Core Bundle db_ms

persistent connectionでfirst-query costが落ちても、remaining queryが約80ms/roundtripのままなら、次の大きな選択肢は:

- query countのさらなる削減
- application / DB region整合
- DB provider/region移行

になる。

DB migrationなし。
