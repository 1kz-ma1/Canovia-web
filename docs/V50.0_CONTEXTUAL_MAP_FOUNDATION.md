# V50.0 Contextual Map Foundation

## 目的

Map UIをCanovia全体の標準NavigationとしてClassicへ置き換えることを前提にせず、Mapが明確な価値を持つContextだけで使えるよう、既存実装の責務境界と観測基盤を整理する。

V50.0では具体的なMap / Classic自動切替ルールを決めない。

行うのは:

- 現在表示しているMapの役割を明示する
- 現在の構造複雑度をread-only snapshotとして観測する
- 既存TelemetryをSurface Role別に比較できるようにする
- Global / Contextual Mapを将来分離できるコード境界を作る

ユーザー向けNavigation・既定Surface・Map表示条件は変更しない。

## UI責務

### Classic

Classicは旧UIではない。

主な責務:

- 入力
- 編集
- 一覧
- フォーム
- 設定
- 日常的なTask操作
- 小規模なPlan管理

### Dashboard

1つのContextを理解し、判断し、次のActionへ進むSurface。

Plan Dashboard / Task Detail / Document Canvas等を含む。

### Map

複雑な構造を理解・整理・探索するSpatial Surface。

主な責務:

- 全体構造
- 関係
- Dependency
- Parallelism
- Blocker
- Spatial grouping
- Exploration

Map内ですべての編集を完結させることは要求しない。

## Map Surface Role

現在のMap requestへdescriptive roleを付与する。

```text
global_navigation
plan_context
collaboration_context
reflection_context
execution_context
hierarchy_context
```

Roleは「どのSurfaceを優先表示するか」を決めない。

### Scope

`global_navigation` のみ `global`。

その他は `contextual`。

## Complexity Snapshot

`MapComplexitySnapshotService` は現在のGraph / Spatial Roadmapから構造観測値を作る。

現在のschema v1:

- node_count
- edge_count
- plan_count
- task_count
- dependency_count
- cluster_count
- parallel_cluster_count
- phase_count
- blocked_count
- has_dependencies
- has_parallelism
- has_blockers

Snapshotには以下を入れない。

- score
- complexity_score
- threshold
- preferred_view
- recommendation

V50.0では「Task 30件ならMap」等の判断を実装しない。

## Map DOM contract

Map rootへ以下を追加する。

```text
data-map-surface-role
data-map-surface-scope
data-map-complexity-schema
data-map-complexity-node-count
data-map-complexity-edge-count
data-map-complexity-plan-count
data-map-complexity-task-count
data-map-complexity-dependency-count
data-map-complexity-cluster-count
data-map-complexity-parallel-cluster-count
data-map-complexity-phase-count
data-map-complexity-blocked-count
```

Complexity値はClient Telemetryへ自動送信しない。

## Telemetry

既存Map Behavior Eventへ構造ラベル `surface_role` のみ追加する。

保存しない:

- Complexity counts
- Plan title
- Task title
- Node label
- user content
- automatic-view score

BehaviorEventControllerで `MapSurfaceRole::telemetryValues()` にwhitelistする。

### Role別集計

MapTelemetryServiceは各Surface Roleについて:

- views
- focus_rate
- classic_action_rate
- back_per_flow

を集計する。

既存eventでroleがないものは `unknown` として扱う。

Admin dashboardではRole別集計を表示するが、そこからMap / Classicの優先Surfaceを自動決定しない。

## 将来のAutomatic View

V50.0では未実装。

将来候補:

```text
Structural Snapshot
    +
Surface Role
    +
Telemetry evidence
    +
User preference
    ↓
View recommendation
```

ただしAutomatic / Classic / Map等の具体的なPreference model、閾値、score式はユーザーテスト後に決める。

## Inbox / Command Center

V50.0では新しいInbox Mapを実装しない。

既存Global MapとInbox Command Centerの責務を混ぜないため、Surface Role Foundationを先に置く。

Inbox Mapを作る場合は別Surfaceとして扱い、Global Navigationをそのまま改名して流用しない。

## Existing Map assets

破棄しない。

再利用対象:

- Semantic Zoom
- Node / Edge renderer
- Spatial Memory
- Plan Dashboard
- Spatial Roadmap
- Document Camera
- Container=Zoom / Leaf=Detail
- Collaboration Projection
- Telemetry flow

これらをGlobal Map専用技術ではなくContextual Spatial Surfaceの共通資産として扱う。

## Non-goals

- Global Map削除
- ClassicをPrimaryへ強制切替
- Inbox Map実装
- Automatic View score
- Automatic View threshold
- user preference setting
- A/B assignment
- AIによるView選択
- DB migration
- Complexity snapshot persistence

## 次に判断可能になること

V50.0以降は、Global / Plan / Collaboration / Reflection / Executionを同じ「Map」という一括指標ではなく、Surface Role別に観測できる。

これにより後続で:

- Global Mapを残す範囲
- Plan Mapを提示する条件
- Collaboration Mapを強く出す条件
- Inbox Command Centerの独立Surface化
- Automatic Viewの閾値

を、実利用データと構造複雑度を分けて判断できる。
