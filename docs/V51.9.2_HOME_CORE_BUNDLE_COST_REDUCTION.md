# V51.9.2 Home / Core Bundle Cost Reduction

## 背景

V51.9でExecutionのTask dependency N+1を除去し、V51.9.1でproduction sessionをRedisへ移した。

Redis切替直後のproduction requestでは:

- session_driver: redis
- session_query_count: 0
- session_query_ms: 0
- DB query_count: 0
- redirect request elapsed: 4.98〜6.73ms

となり、database session時に毎request約430〜550ms発生していた固定費は解消した。

V51.9.2では、Home / Timeline / Core Bundle内に残るSQL roundtripを削減する。

## 1. Timeline adjustment N+1

旧Timelineは:

```php
$plans->each(fn (Plan $plan) => $plan->loadMissing('adjustments'));
```

としており、Plan数に比例して `plan_adjustments` SELECTが増える。

V51.9.2では全PlanをEloquent Collectionへまとめ:

```php
(new EloquentCollection($plans->all()))->loadMissing('adjustments');
```

で1 queryへbatch化する。

TimelineはCore Bundleの対象Surfaceなので、直接Timelineだけでなくidle bundle costにも効く。

## 2. Timeline collaboration relation gating

Timelineは従来、共同Planがなくても `activity_logs` featureを必ずloadしていた。

V51.9.2では:

- tasks
- work_logs

をcommon pathでloadし、`is_collaborative=true` Planが1件以上ある場合のみactivity logsをhydrateする。

共同Planが存在する場合のTimeline semanticsは維持する。

## 3. BehaviorEvent recordOnce session fast path

`BehaviorEventLogger::recordOnce()` / `recordOnceSafely()` は、同じsession内で直前に同じeventを記録済みでも、dedupe確認のためbehavior_eventsへ `exists` queryを投げていた。

recordOnce自体が:

- session_id
- event type
- Plan
- Task
- time window

でdedupeする契約なので、Redis sessionへ直近記録timestampを保持する。

同じwindow内ではDB queryなしでreturnする。

Session markerがない場合は従来どおりDB existsを確認するため:

- deploy直後
- session再生成後
- Redis restart後

も既存DB dedupe semanticsを維持する。

## 4. Home State Snapshot write throttle

`UserStateService::captureDaily()` はHomeを開くたびに同日の `user_state_snapshots` をupsertしていた。

V51.9.2では通常Home requestで:

- 初回: 即capture
- 同一session / 同日 / 10分未満: skip
- 10分以上: refresh
- 日付変更: throttleを無視して新しい日をcapture

とする。

Prefetchは従来どおりcaptureしない。

これは表示stateの計算自体をcacheする変更ではない。Home表示は毎回最新計算を使い、永続snapshot writeだけを抑える。

## 5. Home WorkSession relation sharing

Homeでは従来:

1. Dashboard active/pending WorkSessionを `with(plan, task)`
2. Continuity latest WorkSessionを `with(plan, task)`

として、Session本体だけでなくPlan/Task relation queryも重複していた。

V51.9.2ではContinuityServiceへHome専用contextを追加する。

検索scopeは従来どおり分離して保持する:

- active / paused / pending update: actor_token scope
- continuity latest: owned account Planはcross-device、guest Planはactor_token scope

その2 queryで得たWorkSession modelを結合し、Plan / Task relationをそれぞれ1回だけbatch loadする。

DashboardPresentationServiceはこのpreloaded contextを受け取り、独自のWorkSession queryを行わない。

## 6. Trend query gating

Homeのbehavior sampleがanalysis threshold未満の場合、trend UIは利用されない。

V51.9.2では `analysisReady=false` の場合:

`user_state_snapshots` trend SELECT自体をskipし、空Collectionを返す。

analysisReadyになった場合のtrend contractは維持する。

## 7. Core Bundle boundary

V51.9.2ではCore Bundle endpointやJSON contractは変更しない。

維持:

- Roadmap / Timeline / Calendar shared CoreContext
- one bundle request
- current relation reuse
- direct fragment fallback

まずTimeline N+1等の内部queryを削った後、production再計測でhead-of-line blockingが残るか判断する。

## 8. Regression contract

testsで以下を固定する。

- 8 PlanでもCore Bundleのplan_adjustments SELECTは1回
- non-collaborative accountではplan_activity_logs SELECTは0回
- repeated HomeではrecordOnce dedupe用behavior_events exists queryを発生させない
- State Snapshotは10分window内でrewriteしない
- 日付変更時は新日Snapshotを即作成
- Home WorkSession contextは2 Session query + batch Plan/Task hydration
- existing Core Bundle / Instant Navigation / Home semanticsを維持

## DB migration

なし。
