# V55.8 External Activity Integration Validation

## Goal

V55.8 validates the first complete Execution Ecosystem return loop for Study Practice.

Canonical validation flow:

```text
Study Current Action
→ selected External Provider
→ launch validation surface
→ normalized provider result
→ ExecutionActivity
→ explicit Task link
→ TaskEvidence
→ TaskEvidenceAdapter
→ Study Intelligence
→ refreshed Current Action / Readiness
```

This is still a validation implementation.

V55.8 does **not** add a public provider API, OAuth connection, webhook authentication, Marketplace, Developer Portal, or real third-party service.

## Relationship to V55.6 / V55.7

V55.6 established:

```text
Capability
→ Provider Catalog
→ PlanExecutionPreference
→ ExecutionResolver
→ ExecutionActivity
→ TaskEvidence
```

V55.7 added:

```text
Study Workspace
→ provider setup
→ one-tap Start
→ ExecutionLaunchResolver
→ validation external surface
```

V55.8 connects the return path:

```text
validation external surface
→ provider result intake
→ Activity
→ Evidence
→ Study Intelligence
```

## Validation result intake

New route:

```text
POST /execution-validation/study/{plan}/tasks/{task}/result
```

The route is only available while:

```text
CANOVIA_EXECUTION_SETUP_VALIDATION_ENABLED=true
```

The current validation route is Canovia-user authenticated and requires edit permission on the target Task Plan.

It is **not** the future external provider authentication design.

The selected execution provider must still resolve to:

```text
validation.study.practice.external
```

Otherwise the intake returns 404.

## Input

The validation surface accepts a normalized Practice result:

- activity_key
- score_percent
- duration_minutes optional
- strengths optional
- weaknesses optional

`activity_key` is a provider-scoped stable UUID used to validate idempotent delivery.

Strength / weakness text is normalized into bounded lists before reaching the Activity model.

The validation controller does not store arbitrary request payload as Intelligence facts.

## ExecutionActivity

The result is recorded as:

```text
provider_key:
validation.study.practice.external

capability:
study.practice

type:
study_practice_completed

status:
completed
```

Normalized metrics:

- score_percent
- strengths
- weaknesses
- weakness_topics

Validation-only trace metadata may remain on `ExecutionActivity.metadata`, but that metadata is not automatically projected into TaskEvidence.

## Idempotency

`ExecutionActivityService` continues using:

```text
provider_key + external_key
```

as the idempotency boundary.

Repeated delivery of the same Activity key updates the same Activity.

After Task linkage, Evidence projection uses:

```text
execution-activity:{activity_id}
```

as the TaskEvidence external key.

Therefore:

```text
same provider result redelivered
→ same ExecutionActivity
→ same TaskEvidence
```

rather than duplicate Evidence.

## Explicit Task linkage

External Activity remains conceptually independent of Canovia Task structure.

The validation route currently knows the launched Task, so it explicitly calls:

```text
ExecutionActivityService::linkToTask()
```

This produces:

```text
ExecutionActivity.plan_id
ExecutionActivity.task_id
ExecutionActivity.task_evidence_id
ExecutionActivity.linked_at
```

The architecture still preserves:

```text
provider result
!= TaskEvidence until Canovia links it
```

Future provider APIs may receive Activity before Task matching is known.

## Domain Evidence projection

V55.6 projected every Activity into generic:

```text
execution_activity_observed
```

V55.8 introduces the first explicit domain mapping.

Only when all conditions are true:

```text
capability = study.practice
type = study_practice_completed
status = completed
score_percent is valid
```

does `TaskEvidenceExecutionActivityProjector` emit:

```text
study_practice_assessed
```

Other Activity types remain:

```text
execution_activity_observed
```

This avoids treating arbitrary external activity as Study mastery evidence.

## Evidence allowlist

The Study Practice Evidence contains only known normalized facts:

- execution_activity_id
- provider_key
- score_percent
- strengths
- weaknesses
- weakness_topics
- evidence_summary

The projector does not copy `ExecutionActivity.metadata`.

It also does not expose the whole Activity `metrics` object to Intelligence for domain Evidence.

Therefore:

```text
raw/provider trace
→ stays outside Intelligence

known Study semantics
→ allowlisted TaskEvidence
→ TaskEvidenceAdapter
→ EvidenceObservation
```

## Evidence source

External provider Activity maps to:

```text
EvidenceSource::External
```

Native execution remains:

```text
EvidenceSource::Native
```

Study Intelligence is source-neutral after the factual Evidence boundary.

## Study Intelligence integration

`StudyPlanIntelligenceService` already reads:

- study_practice_assessed
- study_recall_reviewed

No parallel Study scoring engine is added.

After Activity linkage, V55.8 refreshes the existing Study Adaptive Action pipeline.

External Practice Evidence can therefore affect existing:

- practice_attempt_count
- latest_score_percent
- average_score_percent
- best_score_percent
- strengths
- weaknesses
- scope mastery
- Readiness
- Decision
- Current Action

through existing Study rules.

## Progress safety

V55.8 preserves:

```text
external score
!= Task progress

Activity completed
!= Task completed
```

The result intake does not mutate:

- Task progress_percent
- Task status
- Task remaining_minutes

Even a 100% external Practice result is factual learning Evidence, not automatic Task completion.

Any future progress mutation must remain a separate user/policy decision.

## Validation surface

The existing non-production external validation page now includes a simulated provider result form.

Purpose:

```text
launch
→ perform simulated external work
→ return normalized result
→ observe Canovia response
```

This is intentionally not a real provider SDK.

It validates the domain contracts before public external integration work begins.

## Authentication boundary

Current V55.8 result submission requires an authenticated Canovia user with Task edit permission.

This is only a safe validation mechanism.

Future real provider intake must separately define:

- provider authentication
- account linking
- signature/token validation
- replay protection
- provider ownership
- rate limits
- connection revocation
- audit behavior

V55.8 does not pre-decide that design.

## Database impact

No new migration.

V55.8 reuses:

- execution_activities
- task_evidences
- plan_execution_preferences
- existing Intelligence persistence

## AI / network cost

V55.8 adds:

- no external network request
- no OAuth request
- no GitHub request

The validation external provider remains local simulation.

## Next

The next architecture question is no longer whether Activity can return to Intelligence; that loop now works.

Recommended next validation boundary:

```text
provider connection / authenticated external intake
→ provider-neutral Activity endpoint
→ safe Task association
→ existing projection
```

Before building a public API, define:

- ProviderConnection / account ownership
- authentication mechanism
- Activity schema/versioning
- replay/idempotency guarantees
- Task association rules
- privacy / retention boundary

Do not jump directly to Marketplace or Developer Portal.
