# V48.9 Collaboration Review Candidate

> **V49.0 update:** Collaboration hierarchyをProject-firstへ変更したため、Review Waiting ShortcutはL2 Purposeへ直接入らず、review itemを持つShared Projectだけを表示するL1 Project selectionへ遷移する。explicit `collaboration_state=review` truthは変更しない。

## 目的

V48.8でReflection方向のcandidateを追加したため、V48.9ではCollaboration方向を最小単位で有効化する。

追加するのは:

> 既存Collaboration Purpose「レビュー待ち」へのShortcut

1種類だけ。

「相手待ち」「外部Tool」「自分が進める」はV48.9ではcandidate化しない。

## Canonical truth

レビュー候補の存在条件には:

`PlanArtifact.metadata.collaboration_state = review`

という人が明示したstateだけを使う。

以下からreview状態を推測しない:

- GitHub Pull Request URL
- assigned user
- activity log
- provider
- PR / CI / merge status

V44.5のHuman Review contractをそのまま維持する。

## Destination

```text
/map?level=l1
    &intent=collaboration
    &collab_context=review
```

candidate ID:

`satellite:collaboration:review`

node type:

`satellite_collaboration`

semantic anchor:

`intent:collaboration`

position role:

`satellite-4`

## Signals

V45.6の4軸とweightを変更しない。

### importance

review artifactを持つShared Planのeffective priority最大値。

理由:

`重要な共同Planにレビューがある`

### usage_frequency

review item数を3件で1.0へ正規化。

理由:

`レビュー項目がまとまっている`

### recency

review artifactの最新updated_atを既存bucket decayで評価。

理由:

`最近レビュー待ちになった`

### continuity

明示review stateは人が変更するまで継続中のqueueであるためbase 0.55。

複数review item / 複数Shared Planなら小さく加算し、最大1.0。

理由:

`レビュー待ちが継続中`

## Density

既存契約を維持:

- automatic threshold 0.55
- max 2
- same semantic anchor max 1

review itemが1件存在しても必ず表示するわけではない。

低priority + staleなreview state等はthreshold未満ならL0へ出さない。

## Explainability

V48.8で導入したcandidate-specific reason labelを再利用する。

AI reasoningは使わない。

## Pin

V48.9ではCollaboration ShortcutをPin対象にしない。

account-level Pinは引き続きPersonal Planのみ。

自動attentionで価値を検証してからmanual Pin範囲を広げる。

`satellite_collaboration`

新規永続化なし。

candidate / score / positionを保存しない。

## 次

V48.9後はExecution方向について、既存fixed Execution Intentを複製せずにL0へ昇格できる独立Contextがproduction dataに存在するかを再評価する。

適切な独立Contextがなければ、L0の4方向を見た目の対称性のためだけに埋めない。

## Execution方向の再評価結果

V48.9時点でExecution anchorへ追加できるproduction candidateを再評価した。

候補として確認した意味領域:

- current Task
- recommended primary action
- AI Practice等のTask-bound Tool
- 今日の実行導線 / navigation surface

結論:

V48.9では `intent:execution` anchorへ新candidateを追加しない。

理由:

### current Task / primary action

PlanのL3 Execution Contextそのものであり、Personal Plan ShortcutがすでにそのPlanのExecutionへ直接遷移する。

別のExecution Satelliteとして同じContextを複製すると、L0上で:

```text
Plan Shortcut
Execution Shortcut
```

が同じPlan / Taskへ向かうケースが増え、航路短縮ではなく入口重複になる。

### Task-bound Tool

V45.6で定義済みの境界を維持する。

AI Practice等は:

```text
Plan
  -> Task
      -> Tool
```

というTask Contextの従属物であり、L0へ独立昇格しない。

### 今日の実行導線

固定L0 `実行` Intentのfallback / semantic destinationと意味が近く、Satellite化するとfixed Intentの複製になる。

## Candidate Expansion一巡後のL0契約

automatic candidate source:

- Plan
  - active Personal Plan
  - anchor: `intent:plan`
- Reflection
  - Recent Reflection Lens
  - anchor: `intent:reflection`
- Collaboration
  - explicit Review Waiting Purpose
  - anchor: `intent:collaboration`
- Execution
  - none

Execution方向を空けることは未実装ではなく、現在のdata / semantic contractに基づく意図的判断。

将来以下の条件を満たすContextができた場合のみ再検討する。

- Taskから独立して再訪する
- fixed Execution Intentそのものではない
- authoritative usage / state signalを持つ
- 複数階層を飛ばす価値がある
- L0 densityを悪化させない
