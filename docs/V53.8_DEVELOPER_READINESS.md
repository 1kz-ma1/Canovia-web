# V53.8 Developer Readiness

## Goal

V53.8 interprets normalized Development Evidence as release-oriented State, Readiness, Decision and one Current Action.

```text
Development Evidence
→ Task-correlated Development State
→ Release Readiness
→ largest missing quality gate
→ Decision
→ Current Action
→ new Evidence
→ State / Action refresh
```

The central rule is:

> GitHub activity is evidence of reality, not percentage progress.

A commit, merged Pull Request or successful deployment can strengthen Release Readiness, but none of them independently means that the requirement is complete.

## Boundary from V53.7

V53.7 owns provider ingestion:

```text
GitHub webhook
→ authoritative GitHub REST re-fetch
→ TaskEvidence
→ DevelopmentEvidenceCollector
→ EvidenceObservation[]
```

V53.8 starts at `EvidenceObservation[]`.

It does not parse raw webhooks, call GitHub to invent missing state, or inspect source code.

## Task-correlated release candidates

Release gates are evaluated per Task.

Canovia must never combine unrelated evidence such as:

```text
Task A: CI success
Task B: Production deploy success
Task C: verification passed
────────────────────────────────
≠ one Ready release
```

`DevelopmentStateBuilder` groups Development Evidence by `task_id` and builds one gate state per Task.

A deterministic focus candidate is then selected from those Task states. Failed release work receives highest attention, followed by the most advanced release-stage work, recency and stable Task identity.

Task `progress_percent`, `remaining_minutes` and Task status are not imported as Development State truth.

## Release Quality Gates V1

V53.8 evaluates seven gates:

1. implementation
2. CI / automated test
3. review
4. merge
5. production deploy
6. verification
7. specification synchronization

V1 weights:

| Gate | Weight |
| --- | ---: |
| implementation | 20 |
| CI / test | 20 |
| review | 15 |
| merge | 15 |
| production deploy | 15 |
| verification | 10 |
| specification synchronization | 5 |

The weights create an interpretable readiness score, but **Ready is not score-only**.

All seven gates must be passed for `ReadinessLevel::Ready`.

Any current failed gate produces `Blocked`.

Otherwise an observed release candidate is `Developing`.

No usable Development Evidence keeps readiness score null and level `Unknown`.

## Implementation gate

Implementation is observed, not inferred from Task progress.

V1 semantics:

- linked Branch head only → pending
- linked Commit → passed
- linked Pull Request → passed
- no implementation Evidence → unknown

A new authoritative implementation SHA starts a new release generation and invalidates downstream gates that belonged to the previous generation.

## CI gate

Normalized `pull_request_ci_observed` maps:

- success → passed
- failure → failed
- pending → pending
- no observation → unknown

When a new implementation SHA is observed, old CI does not automatically carry forward to the new change.

## Review gate

Review is not reduced to the latest arbitrary review event.

V53.8 keeps the latest active APPROVED / CHANGES_REQUESTED decision per reviewer using an anonymized reviewer key.

The raw reviewer identity does not cross the Intelligence boundary.

Review policy:

- any unresolved CHANGES_REQUESTED → failed
- otherwise at least one active APPROVED → passed
- review activity without a current decision → pending
- no review Evidence → unknown
- DISMISSED removes that reviewer's current decision

A later comment from another reviewer therefore does not erase an existing approval, and approval from one reviewer does not erase another reviewer's unresolved changes request.

## Merge gate

Pull Request state / merge Evidence maps:

- merged → passed
- open → pending
- closed without merge → failed
- no merge path → unknown

The transition from the reviewed PR head to its merge commit is treated as the same release lineage. It does not erase the CI / Review gates that were established for the merged head.

A later new implementation commit is a new generation and invalidates those downstream gates.

## Deploy gate

Only an authoritative successful **production** deployment passes the Release Deploy gate.

- production + success → passed
- failure / error → failed
- staging or other non-production success → pending
- other observed deployment state → pending
- no deployment Evidence → unknown

Deployment SHA is retained as bounded State.

If the latest deployment SHA no longer matches the current implementation/release SHA, the old deployment is stale and the Deploy gate returns to pending.

This prevents a previous production deployment from satisfying a later code change.

## Verification gate

GitHub cannot prove that a deployed feature actually works in the user's real environment.

V53.8 therefore does not infer verification from:

- merge
- CI
- deployment
- Guided Execution free text
- Task completion
- elapsed time

Verification is explicit Human Confirmation stored as:

`development_quality_gate_confirmed`

Allowed verification states:

- passed
- failed

A verification confirmation is bound to:

- current Production Deployment ID
- current deployed SHA

The confirmation is valid only while those references still match the current release candidate.

A new deployment automatically makes the previous verification stale and returns the gate to pending until the new Production release is checked.

## Specification synchronization gate

Spec synchronization is also explicit Human Confirmation.

Allowed states:

- passed
- failed
- not_required

`not_required` is an explicit decision, not a silent assumption.

A Spec Sync confirmation is bound to the current implementation/release SHA.

If the code SHA changes later, the previous Spec Sync confirmation becomes stale and the gate returns to pending.

This protects handoff/product documentation from remaining "confirmed" after implementation changes.

## Manual confirmation authority

`DevelopmentQualityGateService` accepts only:

- verification
- spec_sync

It requires a valid release SHA for both gates and a Production Deployment ID for verification.

The browser does not submit authoritative SHA / deployment identity.

`DevelopmentReadinessController` first evaluates the current Development State, requires the target Task to be the current Release candidate, derives the current authoritative references server-side, and then records the confirmation.

Directly replaying a form for an old Task or old release cannot confirm the current release.

Request UUID is used as the TaskEvidence external key component so one form submission retry is idempotent while later deliberate confirmations remain auditable events.

## Readiness score

V1 score is the sum of passed gate weights.

Examples:

```text
implementation  passed  20
CI              passed  20
review          passed  15
merge           passed  15
deploy          passed  15
verification    unknown  0
spec sync       unknown  0
──────────────────────────
Readiness               85
Level            Developing
```

A score of 85 does not imply Ready because release-critical facts are still missing.

Ready requires every V1 gate passed.

## Gap model

The evaluator emits structured missing/failed gap codes, including:

- `development_evidence_missing`
- `implementation_missing`
- `implementation_in_progress`
- `ci_unverified`
- `ci_pending`
- `ci_failed`
- `review_unverified`
- `review_pending`
- `review_changes_requested`
- `merge_unverified`
- `merge_pending`
- `merge_failed`
- `production_deploy_missing`
- `production_deploy_pending`
- `production_deploy_failed`
- `verification_unconfirmed`
- `verification_pending`
- `verification_failed`
- `spec_sync_unconfirmed`
- `spec_sync_pending`
- `spec_sync_failed`

These gaps drive deterministic Decision candidates rather than being converted into Task progress.

## Decision policy

`DevelopmentDecisionEngine` ranks current release problems.

Failure recovery receives priority over advancing the release.

Current deterministic Decision types:

- `connect_development_evidence`
- `fix_ci`
- `address_review_feedback`
- `fix_deployment`
- `fix_verification`
- `replace_closed_pr`
- `establish_implementation`
- `establish_ci`
- `obtain_review`
- `merge_change`
- `deploy_release`
- `verify_release`
- `sync_spec`
- `release_ready`

V53.8 introduces no new OpenAI request.

The deterministic Development policy is the authoritative baseline.

## Current Action

`DevelopmentActionGenerator` converts the selected Decision into one current `ActionProposal`.

Examples:

- CI failed → "失敗しているCIを直す"
- Changes requested → "レビュー指摘を解消する"
- merge complete but production deploy missing → "ProductionへDeployする"
- deploy complete but verification missing → "実機・本番で動作確認する"
- verification complete but spec sync missing → "仕様と実装を同期する"
- every gate passed → "Release Readyを確認する"

V53.8 does not create a new Task from these Actions.

Development Task projection can be designed later where it adds value; the current implementation reuses the existing Task as the Evidence correlation boundary.

## Durable Intelligence history

Existing generic V53 stores are reused:

- `StateSnapshotStore`
- `DecisionTraceStore`
- `ActionProjectionStore`

Controlled Development metadata was added to the existing allowlists.

Same semantic State + same semantic Action reuses the current Action projection.

When Evidence changes the State and therefore the Decision/Action, the previous active Action is superseded.

Repeated page views do not create a new current Action merely because `captured_at` changed.

## Automatic refresh

Development Current Action is refreshed after:

- signed GitHub webhook synchronization
- manual GitHub Return synchronization
- explicit Verification / Spec Sync confirmation

The primary GitHub or confirmation operation remains the source event. Intelligence projection failure is fail-soft and must not fabricate or roll back GitHub facts.

Webhook refresh only evaluates Plan IDs that actually received synchronized Evidence.

## Minimal V53.8 surface

GitHub Workflow receives a diagnostic Development Intelligence surface when one Development Plan is selected.

It shows:

- Release Readiness score
- readiness level
- confidence
- current Release candidate Task
- Current Action and reason
- seven Quality Gates
- explicit Verification controls
- explicit Spec Sync controls

Verification controls are only available after Production Deploy is currently passed.

Spec Sync controls require current implementation Evidence.

If a confirmation becomes stale because release identity changed, the surface explains that re-confirmation is required.

The final cross-domain Intelligence presentation remains V53.9.

## Privacy boundary

Development Intelligence keeps bounded decision facts.

Allowed examples:

- Task / Artifact reference
- PR number and state
- CI state
- merge state
- anonymized reviewer decision key
- Commit / release SHA
- deployment ID / environment / status
- gate status

Excluded:

- raw GitHub webhook payload
- reviewer login identity in Intelligence
- Issue body/title
- PR body
- commit message
- source code
- file diffs
- Deployment payload/description
- arbitrary free-form provider metadata

## Task mutation policy

V53.8 never turns Release Readiness into legacy Task completion.

It does not change:

- Task progress percent
- Task status
- remaining minutes
- workflow lane

```text
Release Readiness = goal-relative release state
Task progress      = legacy execution projection
```

They remain separate.
