# V58.74 — Revision-bound Owner-approved 3-Step Action Draft

## Scope and behavior
P1.2 phase: a Plan owner can explicitly prepare a **three-step** action sequence
from a proposed V58.71–73 Draft (self-report, WorkLog, typed Evidence or mixture).
Step 1 reflects the current editable suggested next action. Steps 2/3 are
transparent, Domain-specific generic checkpoints (Study, Development, Career,
fallback). They are NOT AI inference, proven dependencies or a guaranteed plan.

- Creates `plan_action_draft_steps` with unique position within each Draft,
  source `evidence_revision`, editable title and accepted Task reference.
- Preparation is inert: no canonical Task, priority, progress or collaborator
  access is changed. Same-revision prepare retry preserves edited step titles.
- Owner edits all three titles as one scoped form. Only owner may prepare, edit,
  accept or dismiss, even on collaborative Plans.
- The view labels all three as **unapproved**, shows the sequential prerequisite
  rule, and requires explicit bundle acceptance with a fingerprint of the exact
  reviewed titles/order/revision. The old single-Task acceptance remains intact
  for drafts with no prepared steps.
- A new evidence revision (V58.72/73 refresh) makes prepared steps stale:
  they cannot be edited/accepted; owner may explicitly rebuild, warned that
  manually edited step titles will be replaced. No automatic rebuild.
- One transaction locks the Draft and creates exactly 3 todo Tasks, with
  canonical task_dependencies for Step2→Step1 and Step3→Step2, mirrored
  `depends_on_task_id` for older readers. All are within this Plan.
  `accepted_task_id` links every step to its created Task; parent Draft stores
  the first Task for existing compatibility. Retry on accepted Draft is inert.
  Atomic rollback protects against partial import.
- Events for collaborative Plans are recorded within the approval transaction.
  If an approved Task is later deleted, the Draft remains accepted and does not
  recreate it on a retry.
- No external AI calls, cost, auto-scheduling, user-assignment inference,
  or changes to old Tasks. No employer/skill-mastery claims.

## Remaining
This is deliberately a small, linear 3-step proposal, not an AI-authored
multi-level or branching dependency graph. Automatic prioritization, optional
AI cost budgets/fallback, actionable confidence and richer Evidence synthesis
still need validation. P1.2 remains partial. P1.3 spotlight not yet started.
Production and native/PWA E2E remain unverified.


## Adaptive Context v0.5 Phase 0 / G3 slice 8 — last-mile approval source fence (2026-10-12)

V58.71–V58.74 intentionally require **explicit Plan owner confirmation** before adding a single Task or a three-step bundle. Existing revision, candidate-text and bundle-step fingerprints prevent two-device edits of the *proposal*, but previously did not verify that underlying user-selected `WorkLog` / `TaskEvidence` had remained intact between composition and approval. A corrected/deleted/moved source could still create a Task from stale evidence.

The G3 bounded fix adds `PlanActionDraftApprovalSourceGuard` inside the existing atomic `accept()` transaction, after reloading and **locking the current Plan** and checking the current actor's owner/guest cookie, then locking the Draft, its WorkLog/TaskEvidence sources and referenced Task rows. Sources that were moved/deleted, no longer in the Plan, relinked to a Task in another Plan, changed in displayed fields, or changed in a complete raw-source hash (new proposal snapshots) cause **HTTP 409 and zero new Tasks, dependencies, activity logs or accepted-step mutations**. Owner changes deny 403. Historical accepted drafts remain idempotent. Owner self-report does not need a provider source and retains the existing path.

Newly composed multi-WorkLog and typed Evidence snapshots retain a `source_signature` SHA-256 of the local source version, computed using CanonicalJson and capturing correction-sensitive fields without copying confidential Career text/provider metadata to the draft. The signature is only internal audit metadata, not an external proof of authority or unguessable token. Legacy V58.71 single WorkLog drafts lack the full signature, so their displayed source action/outcome and live Plan/Task association are rechecked. This intentionally narrower legacy fallback cannot detect hidden-field corrections without a stored initial source version.

A conflict **never** silently refreshes/re-approves a stale proposal: the owner must revisit the current evidence and create/review a revised proposal. This slice does not add unattended acceptance or Task status updates. Existing `applyRefresh()`, `prepareSteps()` and other draft mutation endpoints still need a separately scoped source-freshness assessment; only the **Task-creating acceptance commit** is fenced here. Real multiworker PostgreSQL lock interleavings, remote GitHub App revocation not reflected locally, sources outside V58 Drafts and independent V53 Action materialization remain open G3 acceptance items.

No migration, DB record deletion, entitlement/billing adjustment, OAuth/MCP change, Render operation or device deployment is part of this slice.
