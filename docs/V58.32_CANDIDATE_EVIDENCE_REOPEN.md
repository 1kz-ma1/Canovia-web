# V58.32 Candidate Evidence Revision / Reopen

## Goal

Living Profileのhigh-impact Context Update Candidateを、
単純な `candidate key + dismissed` から
**Evidence revision + signal strength** を持つライフサイクルへ拡張する。

Core rule:

```text
dismissed candidate
+ same-strength evidence
→ keep dismissed

dismissed candidate
+ materially stronger evidence
→ reopen as pending
```

Dismissを無視して繰り返し表示しない。
一方で、現実の利用状況が明確に変わった場合は再確認できる。

## First scope

V58.32の適用対象は:

```text
development_advanced_support
```

のみ。

汎用Contractは将来他candidateへ拡張可能だが、
V58.32で任意candidateの自動再openは実装しない。

## Candidate evidence fields

High-impact candidate may contain:

```text
signal_strength
evidence_fingerprint
evidence_revision
```

Dismiss時:

```text
dismissed_signal_strength
dismissed_evidence_fingerprint
dismissed_evidence_revision
last_dismissed_at
```

Reopen時:

```text
status = pending
reopened_at
reopen_reason = stronger_evidence
evidence_revision += 1
```

## Reopen condition

All must be true:

```text
status = dismissed
AND current signal_strength > dismissed signal_strength
AND current fingerprint differs from dismissed fingerprint
```

Fingerprint changeだけでは不十分。

同じsignal strength内で観測件数が変わっても、
Dismissed candidateは再openしない。

## Development signal

Current deterministic evidence:

Base:

- GitHub integration connected

Stronger:

- multiple connected Development repositories
- recent Development activity
- recent Pull Request / Commit activity

Signal strength:

```text
1 = connected foundation

2 = multiple repositories
    OR recent activity >= 3 with PR/Commit evidence

3 = stronger compound activity
    OR PR/Commit activity >= 3
```

These thresholds are initial deterministic product heuristics.

They are not:

- developer skill classification
- productivity score
- seniority inference
- code quality judgment

## Meaning

The candidate means:

> Repository-based advanced Development support may be more useful now.

It does NOT mean:

> the user became an advanced developer.

Self-reported Development experience remains unchanged.

## Observed Context

V58.32 may record bounded observed Development facts:

```text
observed_context.development_behavior = {
  connected_repository_count,
  recent_activity_count,
  recent_pr_or_commit_count,
  observed_at
}
```

These are behavior/environment facts, not an experience level.

## Pending candidate update

If candidate is still pending and stronger/different evidence arrives:

- update evidence
- update signal strength
- update confidence
- increment evidence revision when fingerprint changes
- do not emit another CandidateCreated prompt event

A still-pending confirmation should not multiply notifications.

## Dismissed candidate

Dismiss stores the current evidence snapshot.

After dismissal:

```text
same signal
→ no reopen

same strength but different fingerprint
→ no reopen

higher signal strength + new fingerprint
→ reopen
```

## Repeated dismissal

Example:

```text
signal 1
→ candidate
→ dismiss

signal 2
→ reopen
→ dismiss

more signal-2 observations
→ stay dismissed

signal 3
→ reopen
```

This prevents nagging while still allowing Living Profile to notice real growth/change.

## Confirmed candidate

Confirmed candidate never reopens.

Stronger evidence may be observed, but:

```text
status = confirmed
→ remains confirmed
```

Feature Readiness remains enabled.

## Legacy compatibility

Older dismissed candidate without:

- signal_strength
- fingerprint
- evidence_revision

is treated as dismissed at baseline signal strength 1.

Therefore:

```text
same connected-only signal
→ remains dismissed

clear signal >= 2
→ may reopen
```

This preserves prior user choice.

## Telemetry

Reuse:

`context_update_candidate_created`

Metadata may include:

- candidate_key
- signal_strength
- evidence_revision
- reopened
- reason

No raw repository URL, PR title, commit SHA, source code, or user text is copied into Behavior Event metadata.

## UI

When reopened:

> より強い観測事実が増えたため再確認しています。

The UI must explain this is not the same evidence being repeated.

## Release boundary

Minimum:

```text
L1 Early Access Core
```

Manual review:

- `candidate_evidence_reopen`

Check:

- initial signal 1 candidate
- dismiss
- same signal no reopen
- same-strength fingerprint change no reopen
- signal 2 reopen
- second dismiss
- signal 3 reopen
- confirmed candidate never reopens
- legacy dismissed candidate compatibility
- self-reported experience preserved
- Guidance preserved

## Non-goals

Not implemented:

- AI evidence scoring
- arbitrary candidate reopen
- experience auto-promotion
- productivity scoring
- code quality inference
- user notification outside Living Profile
