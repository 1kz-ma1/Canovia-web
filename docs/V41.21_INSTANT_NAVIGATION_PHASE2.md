# V41.21 — Instant Navigation Phase 2: Core Fragments

## Goal

V41.20 Phase 1で主要画面を共通Shell上へSoft Navigationできるようにした。

Phase 1ではbackground GETもLaravelのFull HTMLを生成し、そのHTMLからPage領域だけを抽出していた。

V41.21ではInstant Navigation GETだけ最小のFragment Layoutを使い、Shell生成そのものをスキップする。

対象:

- Home
- Inbox
- Roadmap
- Timeline
- Calendar

## Rendering boundary

通常のHard Navigation:

```text
controller
  -> page view
  -> layouts.app
     -> Header / Mobile Header
     -> Release Notes
     -> Guide / Onboarding
     -> Settings
     -> Access label / Product Grant
     -> Feedback shell
     -> Mobile navigation
     -> Page
```

Instant Navigation:

```text
controller
  -> same page view
  -> layouts.instant
     -> compact shell metadata
     -> Page
     -> Companion entry
```

ControllerとPage Bladeは共通のまま維持する。

## Fragment layout selection

Core 5 viewsは以下のrequest headerだけFragment Layoutを選択する。

- `X-Canovia-Instant-Navigation: prefetch`
- `X-Canovia-Instant-Navigation: navigate`

それ以外のrequestは従来どおり `layouts.app` を利用する。

未知のheader valueではFragment Layoutへ入らない。

## Compact metadata

Fragment responseはShell markupを再送せず、`#canovia-instant-meta` に次の状態だけ含める。

- mobile section label
- desktop nav state
- mobile nav state
- feedback context

Client runtimeはFragment metadataを優先し、Full HTMLから取得した場合のみ既存DOMをfallbackとして読む。

## Dynamic payload

Fragment responseに含めるもの:

- Page content
- flash status
- Guest protection where needed
- sync status
- offline snapshot
- Companion entry for current context

Fragment responseに含めないもの:

- Desktop App Header
- Mobile App Header
- Settings dialog
- Release Notes dialogs
- Guide catalog / runner
- Onboarding shell
- Feedback dialog shell
- footer
- mobile tabbar markup
- Vite asset tags
- global decorative shell

これらは初回Hard Loadで読み込んだShellをそのまま再利用する。

## Server-side benefit

Full Shellでのみ必要だった処理をFragment requestから外す。

Focused regressionでTimelineをFull / Fragment比較し、Fragment時に:

- `release_notes`: 0 query
- `user_product_grants`: 0 query

になることを固定した。

Page自身に必要なPlan / WorkLog等のqueryはこのPhaseでは維持する。

## Observability

V41.17 performance logへ追加:

- `response_bytes`
- `instant_fragment`

既存:

- `instant_navigation=prefetch|navigate`
- elapsed_ms
- db_ms
- query_count
- table summary

と組み合わせて、本番でFull requestとFragment requestのserver time / response sizeを比較できる。

## Correctness boundaries

- POST / mutationはFragment化しない
- Core以外の画面はFull Navigation
- Controller business logicは変更しない
- Page BladeはHard / Fragmentで共通
- auth / authorization boundaryは変更しない
- Companion contextはFragmentごとに再生成
- Fragment parse失敗時はV41.20のfail-openでFull Navigationへ戻る

## Next

Phase 2後もControllerが各Page用データを個別にDBから組み立てるコストは残る。

次段階ではShared Core Contextを導入し、

```text
Plan / Task / Progress / Evidence
        ↓
Shared Core Context
        ↓
Home / Inbox / Roadmap / Timeline / Calendar
```

のように、主要画面間で同じデータ取得を再利用できる構造へ進める。
