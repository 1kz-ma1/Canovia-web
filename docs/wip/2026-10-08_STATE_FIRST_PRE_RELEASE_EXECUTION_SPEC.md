# Canovia 一時実装仕様書 — State-first 先行リリース整理
更新日: 2026-10-08 / 状態: **ACTIVE・TEMPORARY** / 実装の根拠: latest `main` + 本文で明示したユーザー合意

> この文書は複数PRにまたがる**実装順序・依存関係・検証ゲート**を一時的に固定するためのもの。Future Architecture の確定仕様ではない。PR進行ごとにチェックを更新し、完了後は確定仕様を既存の `docs/Vxx` 群と `docs/CANOVIA_PRODUCT_SPEC.md` に反映し、この一時ファイルを削除する。実装済みと構想を混同しない。

## 0. 意思決定・目的

- 先行ユーザーの実体験を第一の検証対象とする。簿記を学びたいユーザーと、向き不向きが未確定で就活を始めるユーザーが、初回に**次の行動を選び実行できる**こと。
- Canovia が取得できる既知情報をユーザーに「決めさせない」。**既知の公式情報・本人の状況・観測Evidence・AI推論・未確認**を厳密に区別する。
- 計画は事前の入力義務ではなく、**行動・結果・本人の意思**から段階的にDraftが育つ。Plan/Taskの自動書き換えは別承認とする。
- Overview は全Modeのカタログではなく、**本人の関連性・現実の現在地・最優先Action**を簡潔に投影する。
- Domain（学習/開発/就活）、Collaboration（個人/チーム）、Specialization（簿記/ソフトウェア開発/学校制作等）を混同しない。カテゴリはユーザーが主導で選ぶべき入力ではなく、内部分類・補助情報へ段階的に移す。
- 個人・チーム間の権限境界、課金/認証、データ意味論を破壊しない。安全な小規模PRはCI成功とリスク審査後にagent merge可。データ更新・分類移行・権限/個人情報・本番設定等は**十分な検証とCI成功後にマージ可能（2026-10-08オーナー包括承認）**。

### P0.1の決定事項と非決定事項

- **事実**: `PlanCategoryProfileService::forCategory('制作活動')` は `creative`、`DevelopmentWorkspaceController` は `development` のみを抽出。既存の`is_collaborative` はチーム属性。
- **禁止**: `制作活動` の全PlanをDevelopmentへ変更すること。 `is_collaborative` だけで開発だと断定すること。本人に無断で既存カテゴリや共有権限を書き換えること。
- **最初の実装**: Development Workspaceで本人がアクセスできる旧 `creative` Planを**別枠の候補**として見つけられるようにする。利用者が「開発の計画として開く」を選択したPlanを表示できるようにする。明示的選択と通常のProfileは区別する。既存のCreative系のPlanは引き続き通常はOverviewで扱う。
- **永続化の最終設計**: 本人承認によるDomain設定と、Collaborative/Team区別を後続のP1.1で扱う。新規Schema・自動カテゴリ移行は独立PRに分離する。
- **UI差分**: 同じDevelopment Workspaceの中で個人=自身の次Action、チーム=自分の担当/全体状況/依存の阻害要因を優先。既存`team` Surfaceを再利用し、メンバー表示がない場合に作業不能にしない。

## 3. Study既知情報の出所契約 (P0.2)

| Source | 例 | ユーザーへの確認事項 | やってはいけないこと |
|---|---|---|---|
| Official / curated | 応用情報技術者・日商簿記の適用年度別出題範囲 | 受験日・レベル・学習環境 | `confirmed_scope_count=0`だけで「試験範囲が未確定」とすること、曖昧なまま内容を創作すること |
| User-specific scope | 学校の定期テスト範囲、教科書の進捗、授業プリント | 未登録の範囲表や教材の内容 | 公的試験のシラバスと同一視すること |
| Observed practice | 診断・過去問・仕訳入力の採点 | 結果の確認や修正 | 基礎12問から合格可能性や級全体の習熟を断定すること |
| Inference / missing | AIの仮説、まだ観測されない理解度 | 不足情報を最小限に確認 | 推論を確定事実やユーザーが決めた方針として保存すること |

Scopeには `source`, `reference`, `version/applicable_period`, `verified_at`, `confirmation_state` の出所契約を置き、取得失敗時も既知と未取得を区別する。問題集の原文転載や自動スクレイピングは許諾・利用条件を確認するまで行わない。

## 4. UXの共通受入条件

1. 初回にカテゴリ選択やタスク/ロードマップ手動作成を強要しない（分類は内部で推定し、曖昧なら短く聞く）。
2. 必要な学習・就活行動を先に提示し、情報入力のための情報入力を最優先にしない。
3. Overviewは関連するPlanと重要な通知に絞り、空の専門ModeやInbox(0件)を大きく表示しない。
4. Plan Draftに未確定/本人承認済みを表示。Task、目標、公開状態、権限を無断で上書きしない。
5. 見逃したガイドはいつでも計画画面から再閲覧可能。演出は一度きりで、作業の邪魔をしない。
6. iOS WebView・PWA・PCで戻る/再読込/再送後の状態が一致する。
7. GitHub連携はDevelopment開始の必須条件にしない。チームの観測Evidenceと本人の進捗を分ける。

## 5. 検証ゲートとリリース

- 各Sliceで別PR、変更したロジックをFeature/Unit回帰テストで実証、既存の必須CIを完了。
- データスキーマ・保存意味論・所有/閲覧権限・診断PDF・AIによる実データ更新・Release Level変更はユーザーの手動マージ判断。
- 画面表示・文言・ドキュメント等の可逆な低影響変更は条件を満たせばagent squash merge可。mainのCI通過はRenderの本番反映確認ではない。
- V58.62 **PR #342は競合修正後にCI再成功、main統合済み（commit 9a014f3）**。次の簿記課題は内容と問題数、定着測定の拡張。
- 先行利用前には AP/簿記/Career/チーム開発それぞれで新規登録から実機E2E、403/500・非ログイン・権限・リロード・データ削除導線を確認。
- 個人情報の解析や音声機能は安全ゲート未通過では非公開。CareerのBeta/Release Levelを自動昇格しない。
