# V57.1 Developer Activity Observation

## Goal

V57.1 introduces a pre-Evidence observation layer for connected GitHub repositories.

The Developer V1 loop becomes:

```text
GitHub App
→ webhook / connection bootstrap
→ authoritative GitHub App REST read
→ DevelopmentActivityObservation
→ future Task association
→ existing TaskEvidence
→ Development Intelligence
```

The central boundary is:

> Observation is a real GitHub fact, but it is not Task Evidence until a Task relationship is confirmed.

## Why this layer exists

V53.7 intentionally requires an explicit GitHub Artifact ↔ Task link before writing non-PR Development Evidence.

That is safe, but it means a newly connected repository cannot yet explain its existing development activity to the user.

V57.1 fills that gap without weakening the Evidence boundary.

## Database

New table:

```text
development_activity_observations
```

Identity:

```text
plan_id + provider + external_key
```

Stored fields are bounded provider facts:

- repository Artifact
- kind
- provider number where applicable
- canonical URL where available
- bounded title where the authoritative reader already exposes one
- state
- ref
- SHA
- occurred_at
- last_observed_at
- future Task suggestion fields
- resolution status

Resolution status:

- `unlinked`
- `suggested`
- `linked`
- `ignored`

V57.1 does not yet calculate Task suggestions.

## Authority rule

Webhook payload is still only a routing signal.

```text
signed webhook
→ routing target
→ GitHub App REST re-fetch
→ Observation
```

Raw webhook body is not copied into the observation table.

## Webhook intake

Existing `ProcessGitHubWebhookDelivery` keeps the V46/V53 Evidence flow and additionally projects each connected Development repository event into an Observation.

Supported observation kinds:

- `pull_request`
- `issue`
- `branch`
- `commit`
- `deployment`

Repeated delivery updates the existing Observation instead of creating duplicates.

Observation creation never mutates:

- Task status
- Task progress
- remaining minutes
- workflow lane
- TaskEvidence relationship

## Connection bootstrap

After a repository connection becomes `connected`, Canovia queues:

```text
BootstrapGitHubDevelopmentActivity
```

The bootstrap performs a bounded read of:

- up to 20 open Pull Requests
- up to 20 open Issues when the installation grants Issue access
- up to 20 recent commits on the default branch

No commit message, diff, patch, Issue body, PR body or source code is stored.

This gives a new Developer Workspace useful context immediately instead of waiting for the next webhook.

## Development-only scope

Observations are created only when:

1. the root Artifact is a connected GitHub repository
2. installation ID matches
3. the Plan category is Development
4. the Plan owner has Developer GitHub Evidence capability

A repository connected to a non-Development Plan does not enter the Developer observation layer.

## UI boundary

V57.1 is a foundation change.

It does not yet redesign Development Workspace or expose Task association controls.

Those belong to:

- V57.2 Task Association
- V57.3 Developer Home V1

## Safety

V57.1 preserves:

```text
GitHub activity != Task progress
GitHub activity != Task completion
Observation != Evidence
```

Existing V53.7 / V53.8 remain authoritative for Task Evidence and Release Readiness.

## Adaptive Context v0.5 / Phase 0 G2 — GitHub observation revision fence (2026-10-12)

The original V57.1 identity (`plan_id + github + external_key`) and the existing human-confirmed Task association policy are unchanged. Incoming webhook content is **only a routing trigger**; the GitHub App REST response supplies the observation.

The original `updateOrCreate()` could apply a slow, stale fetch after a newer fetch. G2 introduces two **nullable, additive** version columns on `development_activity_observations`: `source_updated_at` and `source_revision_id` (the latter is a GitHub Deployment status ID). A DB transaction, unique-key `createOrFirst` and `lockForUpdate` protect the comparison and write as one critical section:

- PR / Issue: use GitHub's entity `updated_at`, **not** webhook receipt order or the `occurred_at` event time (which may represent merge/close).
- Deployment: use the latest GitHub status update time and, for same-second statuses, the increasing status ID. Distinct Deployment IDs are distinct observations.
- Branch: GitHub Branch REST supplies no entity revision or ancestry; use the **REST fetched_at** as a weaker per-branch observation watermark. This blocks a previously fetched older observation, but **does not prove that a newer-fetched response contains a newer head**. Future G2 hardening may require Git ancestry or serialized live refresh for branch concurrency.
- Commit: SHA is immutable; preserve the originally created observation on replay, including its originally recorded ref. Do not compare commit timestamps as if they were mutable entity versions.
- Equal/older revisions, and incoming records missing their version when the row already exists, never replace existing provider fields. An equal-second PR/Issue update with changed content is intentionally postponed until a strictly newer GitHub `updated_at` appears. This is a conservative integrity guard, not guaranteed real-time convergence.

Old rows are **not rewritten in bulk**. Until a first valid revision is stored, their existing `occurred_at` is used as a conservative lower bound. This can delay a legitimate update for an ambiguous historical row; operator review is preferable to silently reducing a previously observed version.

When an authoritative GitHub fetch fails, the webhook job's existing retry policy remains in force and the observation is not modified. A newer accepted version updates only normalized GitHub observation fields. In particular it **does not** overwrite `resolution_status`, `suggested_task_id`, Task progress or `TaskEvidence`. A stale Bootstrap response follows the same rule as a delayed webhook.

### Acceptance and residual limitations

The G2 test matrix extends `DeveloperActivityObservationV571Test`: issue newest→oldest→same-second conflict, stale Bootstrap after merged PR, newer PR update, Deployment equal-second status IDs, Branch observation timestamp, immutable Commit replay, failed REST fetch → retry, and preserved Task association status. Tests execute under an isolated SQLite fixture in CI; separate multi-worker PostgreSQL/MySQL transaction race, GitHub API visibility shifts / force-pushes, and real installation webhook timings still need dedicated acceptance. **This change is not proof that every GitHub-derived Evidence, release gate, and cache path has the same revision policy.** Those writers retain their existing independent contracts.

No new Fact store, cross-domain permission grant, automated Task mutation, new MCP endpoint, pricing change or live Render deployment is part of G2.
