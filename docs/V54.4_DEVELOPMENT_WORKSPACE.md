# V54.4 Development Workspace

## Goal

V54.4 turns Development Mode into a dedicated Development Home.

The surface should answer, in one screen:

```text
Release Readiness
→ Biggest Release Gap
→ Current Action
→ Quality Gate state
→ GitHub / Evidence / History
```

V54.4 is presentation and navigation work over the existing V53.7 / V53.8 Development Intelligence loop.

It does not introduce a second release model and does not add AI traffic.

## Entry

Development Workspace canonical route:

```http
GET /workspace/development
```

named:

```text
workspace.development.index
```

V54.4 changes Development Mode entry behavior:

- GET `/workspace/development` renders Development Home
- persistent Development selection redirects to Development Home
- Overview and Study behavior remain unchanged

The static Development route is registered before the generic `/workspace/{workspaceMode}` route.

## Workspace / Plan relationship

Development Intelligence remains Plan-scoped.

Development Home:

1. loads every accessible Plan whose `PlanCategoryProfile` is `development`
2. orders them using existing Canovia Plan priority semantics:
   - Plan priority
   - nearest deadline
   - stable Plan ID
3. selects the first Plan by default
4. accepts explicit `?plan_id=...` only for an accessible Development Plan

Invalid, inaccessible, or non-Development explicit Plan IDs return 404.

Only the selected Plan is evaluated by Development Intelligence.

## Empty states

### No Development Plan

The Development Workspace remains a valid surface.

It shows:

- Development Workspace identity
- explanation of the release loop
- CTA to create a Development Plan

It does not bounce back to Overview.

### Development Plan exists but no Release Evidence

This is the GitHub-first empty state.

When V53.8 has no `focus_task_state` / Release Evidence:

```text
GitHub / Task link
→ authoritative GitHub Evidence
→ Development State
→ Release Readiness
→ Gap
→ Current Action
```

The UI does not manufacture a numeric Release Readiness score.

Primary CTA opens the existing GitHub Workflow for the selected Plan.

Viewing Development Home never creates Evidence, Task, Artifact, or network traffic.

## Populated Development Home

Once a Release Candidate Task is observed, the main hierarchy is:

### 1. Release Readiness

Show existing V53.8:

- score
- state
- confidence
- passed gate count
- failed count
- pending count
- unknown count

No new score is calculated.

### 2. Biggest Release Gap

Use the existing V53.8 Decision through `DevelopmentIntelligencePresentationAdapter`.

No second Gate-ranking algorithm is introduced.

### 3. Current Action

Use the existing Development Adaptive Action.

Action routing remains existing behavior:

- task execution → Execution Orchestration
- GitHub workflow action → GitHub Workflow board
- Verification / Spec Sync → existing Quality Gate confirmation surface

Development Workspace itself does not duplicate mutation forms.

### 4. Quality Gate summary

Show all seven authoritative Gate states:

- implementation
- ci
- review
- merge
- deploy
- verification
- spec_sync

Statuses:

- passed
- failed
- pending
- unknown

Display is read-only on Development Home.

### 5. Release Candidate context

When available, show bounded context from `focus_task_state`:

- Task
- PR number
- branch
- head SHA (short)
- deployment environment
- evidence count
- stale Verification / Spec Sync warnings

Do not expose raw provider payloads, diff content, commit messages, issue bodies, or other private GitHub content.

### 6. Development navigation

Development Home exposes:

- Current Action
- Release Readiness
- Quality Gates
- GitHub
- Evidence
- History

GitHub / Evidence / Gate mutation routes continue to use the existing GitHub Workflow surface.

## History

V54.4 reuses `IntelligencePresentationHistoryService`.

Show bounded recent:

- Decisions
- Actions
- State snapshots / Evidence counts

No new history table is introduced.

## Authorization

Development Home uses existing `PlanOwnershipService`.

Supported read access remains:

- owner
- collaborative editor
- collaborative viewer
- guest-owned Plan

Mutation capability remains governed by the existing destination surfaces.

## Workspace Mode semantics

`workspace.development.*` is a strong Development route hint.

A stored Study or Overview preference does not override the semantic Development Workspace context.

Opening Development Home does not erase the stored preference.

## Performance

Development Home evaluates Intelligence for only one selected Development Plan.

Other Development Plans are loaded only for selector metadata.

No GitHub API request is made merely by rendering Development Home.

No new AI/provider request is made.

## Compatibility

V54.4 preserves:

- GitHub Workflow
- GitHub App connection
- V53.7 Developer Evidence sync
- V53.8 Development State / Release Readiness / Decision / Action
- explicit Verification / Spec Sync confirmations
- Task execution orchestration
- Study Workspace
- Overview
- Workspace Mode persistence

## Non-goals

V54.4 does not:

- duplicate GitHub Workflow board
- duplicate Quality Gate mutation logic
- introduce new Release scoring
- auto-connect GitHub
- auto-create Tasks or Artifacts
- fetch GitHub on GET
- mutate Task progress from Readiness
- expose raw GitHub provider payloads
- add AI traffic
- change Plan category or billing
