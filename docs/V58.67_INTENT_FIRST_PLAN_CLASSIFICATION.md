# V58.67 — Plan Intent Classification (Domain / Collaboration / Specialization Slice 1)

## Why this exists

Prior UX asked users to choose internal categories ("個人開発" or "制作活動") before they could create a project. This hid a team development project such as HINANEX from Development when it was saved under Creative. V58.63 already provides explicit legacy Plan rescue; this slice prevents *new* Plans from requiring users to classify themselves.

## Implemented behavior

- New goal forms still require only the title. Category is optional and hidden in advanced settings. The help text says that Canovia will decide from title/description if the activity is unambiguous and otherwise leave it unclassified.
- `PlanIntentClassificationService` returns independent **nonpersisted** `domain`, `specialization`, and `team_hint` plus a legacy `category` suggestion. It uses a small, explainable exact-phrase heuristic; not AI certainty and not a diagnosis.
- For new Plans **only when no explicit category is supplied**, the backend uses the specific Workspace entry point (if any) or the conservative intent classifier to choose a compatible existing category. Ambiguous text stays `category = null`, and no mode is forced.
- If the user explicitly selects a category, it remains authoritative, even when the title looks like another domain. A mismatch between explicit mode and category still returns to Plan rather than redirecting incorrectly.
- Example input `HINANEX防災支援システムをチームで開発する` is assigned the Development category `ソフトウェア開発`; not "制作活動" and not "個人開発." Older "制作活動" records are never auto-migrated.
- **Collaboration is a separate explicit opt-in.** A phrase such as "チームで" is a hint, **not permission** to turn on sharing or invitations. The collaboration checkbox is made prominent in the simple Plan form; server-side `PlanCollaborationService` remains the only enable path.
- Category remains editable on Plan edit. No migration, no backfill, no user rights changes, and no new stored profile fields.

## Security / evidence boundaries

This bounded slice neither analyzes private document content nor invokes third-party APIs. Classification is a convenience best effort and can be wrong; it never changes existing Plans or silently enables collaboration. Public/workspace visibility still respects existing profile and Plan ownership logic, and ambiguous intent must not be assigned to a specialist Mode.

## Remaining P1.1 work

- An explicit **persisted Domain** independent from legacy category, with user correction path and backwards-compatible resolver; only after a separately reviewed schema/contract.
- Team specialization and Task ownership/dependency UI beyond the existing Team Surface.
- Clear confidence/provenance, better distinguishing artistic projects from software development without misleading UI.
- Reliable representation of `Specialization` rather than inferring again from the free-text category; no fixed taxonomy for every kind of study/development.
- Full cross-surface compatibility (Overview/Study/Development/Career/Intelligence). Do **not** mark P1.1 finished from this slice.
