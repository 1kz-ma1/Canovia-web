# V57.2 Developer Task Association

## Goal

V57.2 turns V57.1 GitHub observations into human-confirmable Task associations.

Canonical flow:

```text
DevelopmentActivityObservation
→ deterministic Task suggestion
→ Human Confirmation
→ PlanArtifact ↔ Task link
→ authoritative GitHub re-fetch
→ existing TaskEvidence
→ Development Intelligence refresh
```

The central rule remains:

```text
suggestion != association
association != Task progress
GitHub activity != Task completion
```

## Matching

V57.2 does not use an LLM.

Candidates are limited to:

- the same Development Plan
- Tasks not in done / cancelled
- unresolved GitHub observations
- PR / Issue / Branch / Commit observations

Signals, ordered by authority:

1. explicit Task identifier in GitHub title/ref
2. normalized Task title contained in title/ref
3. multilingual character n-gram similarity

A suggestion is written only when:

```text
top confidence >= 0.72
AND
top - second >= 0.10
```

Otherwise the Observation remains `unlinked`.

Suggestion fields:

- suggested_task_id
- suggestion_confidence
- suggestion_basis
- resolution_status = suggested

No Task relation is created by matching alone.

## Human Confirmation

Development Workspace exposes unresolved observations.

The user may:

- accept the suggested Task
- choose another eligible Task
- ignore the Observation

Link requests re-check:

- Plan edit authorization
- Development category
- Observation belongs to Plan
- Task belongs to Plan
- Task is not done / cancelled
- Observation is linkable

## Artifact projection

On confirmation, Canovia creates or reuses the matching GitHub PlanArtifact.

Supported V57.2 kinds:

- pull_request
- issue
- branch
- commit

Branch URL is derived from the already-connected repository root when the Observation itself does not carry a URL.

Deployment remains observation-only in V57.2 because it is better attached through an already-associated PR / Branch / Commit rather than represented as an arbitrary standalone link.

## Evidence refresh

After the explicit relation is stored:

- PR uses existing GitHubReturnEvidenceService
- Issue / Branch / Commit use GitHubDevelopmentEvidenceService
- GitHub REST is re-fetched authoritatively
- TaskEvidence is projected through the existing Evidence pipeline
- Development Intelligence refreshes when Evidence was written

Remote refresh is fail-open for the relation:

```text
Task association saved
+
temporary GitHub failure
=
keep association
and retry from later webhook / sync
```

## Progress safety

V57.2 never writes:

- Task progress_percent
- Task status
- remaining_minutes

A GitHub relation is evidence routing, not completion.

## UI boundary

V57.2 adds a compact GitHub Activity association section to Development Workspace.

It does not yet perform the V57.3 Developer Home redesign.

V57.3 remains responsible for:

- Current Action first hierarchy
- recent GitHub activity as a primary surface
- compact Readiness / Gate presentation
- removing product-validation telemetry from user-facing development surfaces
