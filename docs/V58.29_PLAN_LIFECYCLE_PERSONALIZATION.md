# V58.29 Plan Lifecycle Personalization Refresh Triggers

## Goal

Living ProfileのContext Refresh Triggerへ、Canovia CoreのPlan lifecycleを接続する。

Implemented triggers:

```text
new_plan
plan_completed
```

このVersionの目的は:

> Planの意味ある節目をContext再評価の契機として観測する。

であり、Plan内容・Guidance・Personalizationを自動変更することではない。

## Source of truth

- `docs/CANOVIA_PERSONALIZATION_SPEC.md`
- `docs/V58.27_LIVING_PROFILE_FOUNDATION.md`
- `docs/V58.28_STUDY_BEHAVIOR_PERSONALIZATION.md`
- current Plan / Task model and mutation contracts

No new Plan status column is introduced.

## New Plan trigger

A newly created authenticated owner Plan:

```text
PlanController::store
+ Plan.wasRecentlyCreated
+ Personalization Context exists
→ observed plan_lifecycle.last_created_plan_id
→ trigger = new_plan
→ Living Profile refresh
```

Idempotent `createOrFirst()` retry does not re-fire the trigger.

Observed Context:

```text
observed_context.plan_lifecycle = {
  last_created_plan_id,
  last_created_at,
  ...
}
```

## Plan completed trigger

Canovia currently has no single authoritative `plans.complete` command.

Plan completion is derived from current Task state.

V58.29 observes Task model updates centrally.

Trigger condition:

```text
Task status/progress changed
+
current Task is complete
+
Plan has >= 1 non-cancelled Task
+
all non-cancelled Tasks are complete
+
authenticated request user owns Plan
+
Personalization Context exists
+
Plan has not already emitted completion in V58.29 memory
→ trigger = plan_completed
```

Task complete semantics follow current product behavior:

```text
status = done
OR
progress_percent >= 100
```

Cancelled Tasks do not prevent Plan completion.

## Centralization

Do not duplicate completion hooks across:

- TaskController
- WorkLog
- Study Practice
- Recall
- GitHub Evidence
- Review Assistant
- other Task mutation surfaces

Instead V58.29 uses the Task model update event as a single observation boundary.

This event is guarded.

It only acts when:

- an HTTP request exists
- request user is authenticated
- request user is the Plan owner
- a Personalization Context already exists

It does not silently create a Personalization profile.

## Observed Context

On first observed completion:

```text
observed_context.plan_lifecycle = {
  recent_completed_plan_ids: [...],
  last_completed_plan_id,
  last_completed_task_id,
  last_completed_at,
  ...
}
```

`recent_completed_plan_ids` is bounded to the most recent 20 Plan IDs.

This is dedupe memory, not a canonical historical archive.

## Reopen / re-complete behavior

V58.29 deliberately emits `plan_completed` only once per remembered Plan ID.

Example:

```text
Plan completed
→ trigger emitted

Task reopened
→ no completion trigger

same Plan completed again
→ no second trigger in V58.29
```

Why:

V58.29 does not yet have an evidence fingerprint / completion revision contract.

A later Active Spec may distinguish:

- genuinely new completion cycle
- duplicate mutation
- reopened Plan
- materially changed Plan

using a stronger fingerprint.

## Context refresh telemetry

Existing event:

```text
context_refresh_triggered
```

Metadata:

```text
trigger = new_plan
trigger = plan_completed
```

Unlike short-window workspace/manual refresh events, these lifecycle events are not deduped only by event type + Plan.

The lifecycle adapter itself provides semantic dedupe, so both:

```text
new_plan
plan_completed
```

can be preserved even when they happen close together.

## What refresh may do

Living Profile refresh continues to use current deterministic rules only.

A Plan lifecycle trigger may re-evaluate existing rules such as:

- recent Workspace surface priority
- existing high-impact capability candidate conditions

V58.29 does not introduce a new Plan-based inference rule.

## What does NOT change

V58.29 does not automatically modify:

- Plan title
- Plan description
- Plan category
- Plan Tasks
- Task progress
- self-reported Context
- Guidance Level
- experience level
- entitlement
- Release Level

It only records lifecycle facts and requests re-evaluation.

## Ownership / collaboration boundary

Only the authenticated Plan owner updates their Living Profile.

A collaborator completing a shared Task must not silently mutate the owner’s Personalization Context.

Future team/shared Context requires a separate explicit contract.

## Guest boundary

Guest Plans do not create Living Profile state.

The current owner-token guest flow remains unchanged.

## Release boundary

Minimum:

```text
L1 Early Access Core
```

No new public route.

Manual review:

- `plan_lifecycle_personalization`

Check:

- genuinely new Plan → `new_plan`
- idempotent Plan form retry → no duplicate
- incomplete Plan → no `plan_completed`
- last active Task completes → one `plan_completed`
- cancelled Task does not block completion
- reopen + re-complete → no duplicate in V58.29
- user without Personalization Context → no profile creation
- collaborator / non-owner → no owner Context mutation

## Migration

None.

## Deferred

Not implemented:

- completion revision / evidence fingerprint
- re-open / re-complete semantic revision
- Plan completion Growth Experience
- automatic Plan-direction changes
- new Goal trigger
- return-after-absence trigger
- long-usage trigger
- multi-user shared Context
