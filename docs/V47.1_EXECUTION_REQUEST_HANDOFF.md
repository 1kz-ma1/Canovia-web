# V47.1 Execution Request Handoff

## Goal

V46.1 Conversational Inbox / Canovia Companionで受け取った「これから何かを進めたい」という意図を、
V47.0 Execution Orchestrationへ安全に引き継ぐ。

V47.1で追加する境界は次のとおり。

```text
Inbox / Companion
      ↓
Execution Request Candidate
      ↓
Human Confirmation
      ↓
Canonical Execution Request
      ↓
Execution Orchestration Context
      ↓
Execution Packet
```

Execution Requestは「何を進めたいか」という確認済みの意図であり、
Execution Packetは「現在のPlan / Task / Dependency / Evidenceを踏まえて、今どう進めるか」を導出した指示である。
両者を同一視しない。

## Architectural decision

Execution Request専用のDB Entityは追加しない。

TaskをSource of TruthとするV47.0の原則を維持し、
Human Confirmation後のExecution Requestは対象TaskのExecution Orchestration sessionへ一時的に保持する。

```text
execution_orchestration.{plan_id}.{task_id}
  context_fingerprint
  actor_type
  available_minutes
  execution_request
  packet
  handoff_prompt
```

Execution RequestをTask description / next_action_note等へ自動転記しない。
Request確認だけでTask progress / status / Plan dataを変更しない。

## Canonical contract

```json
{
  "schema_version": "1.0",
  "flow": "execution_request",
  "source": {
    "type": "inbox_item | companion_candidate",
    "id": 123,
    "title": "入力元の表示名"
  },
  "target_plan": {
    "id": 10,
    "title": "Plan"
  },
  "target_task": {
    "id": 56,
    "title": "Task"
  },
  "instruction": "ユーザーが今回進めたいこと",
  "actor_type": "human | ai | human_ai | external",
  "available_minutes": 30,
  "confirmation": {
    "state": "confirmed",
    "confirmed_by": "user"
  }
}
```

IDsはAI出力から採用しない。
Plan / TaskはCanoviaの現在データから人が選択・確認したものだけをcontractへ入れる。

## Inbox flow

Inbox Intelligenceは新しいrouting destinationとして `execution_request` を提案できる。

意味:

- これから既存Taskを進めたい
- AI / 人 / 外部システムへ実行指示を渡したい
- 「この作業をやって」「次へ進めて」のようなfuture action

対して、すでに起きた作業結果・成果・確認事実は `task_evidence` とする。

AI suggestionはPlan / Task IDを返さない。
Inbox reviewでユーザーが以下を確認する。

- destination = execution_request
- Plan
- Task
- 今回してほしいこと（execution_instruction）
- actor type
- available minutes（任意）

execution_instructionはInbox本文を初期値にできるが、最終的にはHuman Reviewで明示確認する。画像 / PDFだけのCaptureでも、実行リクエストへ進める場合は今回の意図を文章で確認する。

Confirm後にのみ `ExecutionRequestHandoffService` がcanonical requestをsessionへ置き、
Execution Orchestration画面へ遷移する。

InboxItemは通常routingと同じくprocessedとなり、
`metadata.routing_confirmed`へdestination / plan_id / task_id / confirmed_atを記録する。

## Companion flow

CompanionはTask Contextが選択されている場合だけ
`prepare_execution_request` Mutation Candidateを提案できる。

Payload:

```json
{
  "instruction": "今回進めたいこと",
  "actor_type": "human_ai",
  "available_minutes": 30
}
```

Candidateは未反映状態で表示し、人が
「確認して実行整理へ進む」を押すまでOrchestrationへ渡さない。

Apply時もTask / Planは変更しない。
Candidate自体はhuman-confirmed handoffとしてappliedへ遷移し、
`applied_target_type=execution_request` と対象Task IDをauditとして残す。

## Orchestration boundary

Execution Requestが存在する場合、ExecutionPacketServiceはPromptへ
`CONFIRMED EXECUTION REQUEST` として含める。

ただし優先順位は以下。

```text
Security / Orchestration safety rules
  > canonical Plan / Task / Dependency / protected scope / confirmed facts
  > human-confirmed Execution Request intent
  > generated Execution Packet
```

Requestはユーザーの意図として尊重するが、以下を上書きできない。

- unmet Dependency
- protected scope
- confirmed constraints
- canonical target Plan / Task
- Evidenceで確認されていない完了状態

Requestとcanonical contextのtargetが矛盾する場合、
AIは別Taskへ越境せず `confirmation_required` とする。

V47.0のblocked execute fail-safeもそのまま適用する。

## Reset / stale semantics

Execution Packet / external handoff promptのResetでは、
Human-confirmed Execution Requestを保持する。

理由:
Requestは「今回何をしたいか」の確認結果であり、
Packetはその時点のContextから再生成可能なProjectionだからである。

Packet / Prompt生成後にTask / Dependency / Evidenceが変わった場合のみstale判定する。
Requestを確認しただけの状態をstaleとは表示しない。

## Native / External AI

Execution Request contract自体はFree / Premiumに依存しない。

- External AI handoff: 既存Free path
- Native Packet generation: 既存AutomaticAiExecution entitlement

新しい課金境界は作らない。

## Safety / ownership

- Inbox Itemは既存ownership scopeを通す
- selected Plan / TaskはPlanOwnershipServiceで検証する
- Companion Candidateはthread/user ownershipを検証する
- AIがIDを選ばない
- Human Confirmation前にdispatchしない
- Request確認だけでTask progressを更新しない
- RequestからDependencyを自動変更しない
- Requestから他Taskのscopeを自動変更しない

## Non-goals

V47.1では以下を行わない。

- durable ExecutionRequest table
- queue / jobとしての自動dispatch
- autonomous multi-agent execution
- 担当者アカウントの自動割当
- AIによるPlan / Task自動選択
- Request確認時のTask mutation
- Packet完了の自動Evidence化
- GitHub / Slack等への自動送信

これらはExecution Request / Packet / Evidenceの責務が安定してから別段階で検討する。
