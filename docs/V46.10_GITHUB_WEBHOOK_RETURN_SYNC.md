# V46.10 GitHub App Webhook Return Sync

## Goal

V46.7で手動だった「GitHubから結果を確認」を、
GitHub App Webhookをtriggerとして安全にbackground同期できるようにする。

```text
GitHub
  Review / PR / CI event
        ↓
signed GitHub App Webhook
        ↓
Canovia stateless endpoint
        ↓
signature verification
        ↓
minimal durable delivery inbox
        ↓
queue
        ↓
GitHub API authoritative re-fetch
        ↓
V46.7 GitHubReturnEvidenceService
        ↓
TaskEvidence / Return Snapshot
        ↓
existing Execution Context becomes stale
        ↓
Human-confirmed Task Decision
```

Webhook payload自体をTask truthとして採用しない。
Webhookは「再確認すべき変化がGitHubにあった」というtriggerだけに使い、
実際のReview / Merge / CI stateは既存GitHub App tokenでGitHub APIから再取得する。

## Endpoint

```text
POST /api/integrations/github/webhook
```

API routeとして登録し:

- web sessionを使わない
- CSRF cookieを要求しない
- First Run / browser UI middlewareを通さない
- JSON responseだけを返す

GitHub AppのWebhook URLにはproduction origin + 上記pathを設定する。

## Authentication

Canovia運営者がGitHub App側とRender等のserver側に同じWebhook secretを設定する。

server env:

```text
GITHUB_APP_WEBHOOK_SECRET=...
```

GitHubから受け取る:

```text
X-Hub-Signature-256: sha256=...
```

raw request bodyに対してHMAC-SHA256を計算し、
`hash_equals` でconstant-time比較する。

signature不一致は401。
Webhook secret未設定は503。

Webhook secret / signature / installation tokenはDBへ保存しない。

## Payload boundary

最大payloadはapplication layerで1MBまで。

永続化しない:

- raw JSON
- Pull Request body
- Review comment body
- source code
- user-generated webhook text
- signature

永続化するrouting factだけ:

- GitHub delivery ID
- event name
- action
- repo_full_name
- installation ID
- PR number list
- processing status / counts / bounded error
- received / processed time

これによりprompt injectionや不要なsecret / text retentionの面積を増やさない。

## Supported events

V46.10でtriggerとして扱う:

- pull_request
- pull_request_review
- workflow_run
- check_run
- check_suite

`ping` は署名確認後にpongだけ返す。

workflow_run / check_run / check_suiteでpayloadにPull Request referenceがない場合は
acknowledgeしてignoreする。

未対応eventもacknowledgeしてignoreし、
Canovia側でremote stateを推測しない。

## Durable delivery inbox

`github_webhook_deliveries` を追加する。

主なcolumn:

- delivery_id unique
- event_name
- action
- repo_full_name
- installation_id
- pull_request_numbers
- status
- matched_artifacts
- synced_tasks
- skipped_entitlement
- attempts
- last_error
- received_at
- processed_at

Delivery ID unique constraintをidempotency keyとする。

同じdeliveryの再送:

- accepted / processing / processed / ignored → duplicateとして200
- failed → 同じdeliveryを再queue可能

controller側は `firstOrCreate` + unique indexを使い、
concurrent duplicateにもrace-safeにする。

## Queue boundary

署名確認とminimal persistenceだけをWebhook requestで行い、
GitHub API readはqueue jobへ渡す。

Job:

`ProcessGitHubWebhookDelivery`

- tries = 4
- timeout = 90s
- backoff = 15 / 60 / 180s

productionではdatabase queueを処理するworkerが必要。

例:

```text
php artisan queue:work --sleep=1 --tries=4 --timeout=90
```

RenderではCanovia web serviceとは別にBackground Worker等で上記queue workerを常時動かす。

workerが停止していてもsigned deliveryはjobs tableへ残るが、
Return Evidenceはworker再開まで更新されない。

## Artifact routing

Webhook payloadのrepo / PRだけからTaskを推測しない。

候補PR Artifact:

- provider = github
- external_id = webhook PR number
- artifact URLをparseしたrepo_full_nameがevent repoと一致

さらにRepository rootを確認する。

- same Plan
- provider = github
- artifact_type = repository
- parsed repo_full_name一致
- github_app_connection.status = connected
- stored installation_id = webhook installation_id

V46.6 originにrepository_artifact_idがある場合はそのrootへ限定する。
ないmanual PR Artifactでも、same Planの明示接続済みRepositoryが一致すれば処理できる。

Task mappingはPR Artifactへ明示linkされたTaskだけ。

AI mappingは行わない。

## Entitlement boundary

background syncはUI actorが存在しないため、
Plan ownerをautomationのbilling principalとして扱う。

`DeveloperGithubEvidence` がPlan ownerに許可されている場合だけremote API syncを行う。

許可がない場合:

- deliveryはsigned factとしてaudit可能
- GitHub APIを追加取得しない
- Evidenceを作らない
- skipped_entitlementをcount
- deliveryはignored

Webhookを使って有料Capabilityを迂回しない。

## Authoritative re-fetch

Webhook payloadの:

- merged
- review state
- CI conclusion

等はTaskEvidenceへ直接保存しない。

queue jobはeventから対象PRを特定した後、
`GitHubReturnEvidenceService::sync()` を呼び、
既存 `GitHubRepositoryWriter::inspectPullRequestReturn()` でGitHub REST APIを再取得する。

そのため:

```text
Webhook payload = trigger
GitHub REST API = authoritative remote state
Canovia TaskEvidence = bounded local projection
```

という境界を維持する。

## Return side effects

Webhook background syncで変更できる:

- PR Artifact github_return_snapshot
- idempotent GitHub TaskEvidence
- Execution Context fingerprintの自然なstale化

変更しない:

- Task status
- Task progress
- remaining_minutes
- Dependency graph
- github_workflow_state
- Task Decision
- Distribution
- Packet generation

Task完了等はV46.8のHuman Confirmationを引き続き必須とする。

## Installation isolation

Webhook installation_idと、
Canovia Repository Artifactに保存した
`github_app_connection.installation_id`
が完全一致する場合だけ処理する。

一致しないdeliveryではGitHub APIを呼ばない。

これにより同名Repositoryや別Organization installationとの混線を避ける。

## UI

GitHub App Webhook secretがserverに設定されている場合、
Execution OrchestrationのRETURN LAYERへ:

`GitHub App Webhook 自動同期`

を表示する。

既存「GitHubから結果を確認」もmanual re-checkとして残す。

Webhookが有効でもTask Decisionは自動適用しない。

## GitHub App operator setup

Canovia運営者が1回行う:

1. GitHub AppのWebhookをActive
2. Webhook URL:
   `https://<canovia-host>/api/integrations/github/webhook`
3. Webhook secretを生成
4. GitHub AppとRender等の `GITHUB_APP_WEBHOOK_SECRET` に同じsecretを設定
5. event subscribe:
   - Pull requests
   - Pull request reviews
   - Workflow runs（CIを使う場合）
   - Check runs / Check suites（必要な場合）
6. production queue workerを常時起動

一般ユーザーはWebhook secretを設定しない。
ユーザー側の作業は従来どおり対象RepositoryへCanovia GitHub Appをinstall / approveすることだけ。

Organization policyでApp event / permissionの承認が必要なら、
Canoviaはその承認を迂回しない。

## Failure behavior

### Invalid signature

401。
DB persistence / queue dispatchなし。

### Unsupported or non-PR event

202でacknowledgeしignore。

### Queue dispatch failure

503。
deliveryをfailedとして記録する。
GitHub retry / redeliveryで同deliveryを再queueできる。

### Worker/API failure

queue retry。
Evidenceはstable external keyでidempotentなので、
途中まで成功してretryされてもduplicateを作らない。

最終失敗はdelivery status = failed + bounded last_error。

## Privacy / logs

Application logへ出してよい:

- delivery ID
- event name
- repo_full_name
- exception class

出さない:

- raw payload
- review body
- PR body
- source code
- webhook signature
- GitHub token
- Private Key

## Migration

あり:

`github_webhook_deliveries`

これはremote GitHub stateのmirrorではなく、
外部event ingestionのidempotency / retry / audit boundary。

## Non-goals

- Task auto-complete
- automatic Evidence Decision apply
- webhook payloadをsource of truth化
- automatic merge
- actor auto-assignment
- Packet auto-regeneration
- Distribution auto-submit
- full GitHub event archive
- raw webhook payload storage


## V53.7 evolution

V53.7はV46.10のWebhook安全境界を置き換えず、Development Intelligenceへ拡張する。

V46.10の原則:

```text
Webhook payload = trigger
GitHub REST API = authoritative remote state
TaskEvidence = bounded local projection
```

はそのまま維持する。

追加されたrouting target:

- Issue number
- Push branch + commit SHA
- Branch name
- Deployment ID

追加されたsupported event:

- issues
- push
- create（branch only）
- deployment
- deployment_status

非PR eventでも、raw webhook contentをTaskEvidenceへ直接投影しない。接続済みRepositoryと明示link済みArtifact/Taskを確認し、FeatureAccessを確認した後にGitHub App RESTでauthoritative stateを再取得する。

V53.7以降のnormalized Evidence:

- pull_request_observed
- pull_request_review_submitted
- pull_request_ci_observed
- pull_request_merged
- github_issue_observed
- github_branch_observed
- github_commit_observed
- github_deployment_observed

これらはDevelopment activityの事実であり、自動Task progress / completionを意味しない。V53.8がRelease Readinessとquality gate interpretationを担当する。

詳細は `docs/V53.7_DEVELOPER_EVIDENCE_SYNC.md` を正とする。
