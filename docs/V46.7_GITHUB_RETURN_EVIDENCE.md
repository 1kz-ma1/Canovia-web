# V46.7 GitHub Return / Evidence Bridge

## Goal

V46.6でCanoviaからGitHubへ出したPull Requestの結果を、
GitHubをauthoritative sourceとしてCanoviaへ戻す。

```text
Execution Packet
  ↓
GitHub Change Candidate
  ↓
Human Confirmation
  ↓
Pull Request
  ↓
Review / CI / Merge on GitHub
  ↓
explicit Return Sync
  ↓
GitHub Evidence
  ↓
Execution Context becomes stale
  ↓
人がTask状態を確認
  ↓
次のPacket / Distributionを再生成
```

Return LayerはGitHub remote stateをCanoviaのTask statusやworkflow laneへ直接写経する機能ではない。

## Source of truth

GitHub上の以下をauthoritative factとして読む。

- Pull Request current state
- merged flag / merged_at / merge commit
- submitted Pull Request reviews
- optional GitHub Actions workflow runs
- optional Check Runs
- optional Commit Status

Canovia URL、session、古いsnapshotからremote resultを推測しない。

## Authentication

Private Repositoryを含むExecution HandoffのReturnは
V46.4〜V46.5と同じGitHub App installation tokenを使う。

個人PAT / user OAuth tokenは使わない。

Pull Request / Reviewの取得には:

- Pull requests: read または write

を要求する。

V46.4 Write LayerですでにPull requests: writeを要求しているため、
Review / Merge returnだけなら追加permissionは不要。

CI signalはoptional。

- Actions: read
- Checks: read
- Commit statuses: read

のうちGitHub App installationが実際に持っているpermissionだけを利用する。
permissionがないCI sourceへ無理にアクセスせず、warningとしてUIへ表示する。
GitHub App registrationへoptional permissionを後から追加する場合、既存OrganizationではGitHub側の再承認が必要になり得るため、Canoviaは承認前のpermissionを利用可能とは扱わない。

企業Organizationで追加permission承認が難しい場合でも、
Review / Merge Returnは維持できる。

## GitHubRepositoryWriter read extension

既存GitHub App authentication境界を再利用するため、
`GitHubRepositoryWriter::inspectPullRequestReturn()` を追加する。

名前はWriterだが、このmethod自体はread-only。

取得:

```text
GET /repos/{owner}/{repo}/pulls/{number}
GET /repos/{owner}/{repo}/pulls/{number}/reviews

optional by installation permission:
GET /repos/{owner}/{repo}/actions/runs?head_sha=...
GET /repos/{owner}/{repo}/commits/{head_sha}/check-runs
GET /repos/{owner}/{repo}/commits/{head_sha}/status
```

Return snapshotにはsource code本文を保存しない。

## Return snapshot

PR PlanArtifact metadata:

```text
metadata.github_return_snapshot
  version
  source = github_app_rest
  repo_full_name
  fetched_at

  pull_request
    number
    title
    state
    draft
    merged
    merged_at
    merged_by
    merge_commit_sha
    head_sha
    head_ref
    base_ref
    updated_at
    closed_at
    url

  review_summary
    approved_reviewers
    changes_requested_reviewers
    latest_decisions[]

  ci
    state = success | failure | pending | unknown
    actions_runs[]
    check_runs[]
    combined_status

  warnings[]
```

snapshotはGitHubのbounded read projectionであり、GitHubそのもののmirrorではない。

## Review semantics

submitted review eventをTask Evidenceとして記録する。

```text
type = pull_request_review_submitted
source = github
external_key = github:{repo}:pull:{number}:review:{review_id}
```

metadata:

- review state
- reviewer
- review id
- review URL
- reviewed commit id
- PR number / URL

APPROVED / CHANGES_REQUESTED / COMMENTED / DISMISSEDをfactual eventとして扱う。

「APPROVED reviewが1件ある」ことと
「Repository policy上merge可能である」ことを同一視しない。

UIでは「承認確認 N人」「修正依頼 N人」と表現し、
Canovia独自の最終approval判定を作らない。

## Merge Evidence

GitHubが `merged=true` を返した場合:

```text
type = pull_request_merged
source = github
external_key = github:{repo}:pull:{number}:merged
confidence = 1.0
```

metadata:

- merged_at
- merged_by
- merge commit SHA
- head SHA
- head/base ref
- PR URL

Merge Evidenceは強いfactual evidenceだが、
Taskの成功条件を満たしたこととは別。

そのため:

- Taskを自動doneにしない
- progressを100%にしない
- dependencyを自動解放しない

## CI Evidence

利用可能なGitHub App permissionからCI signalをboundedに取得する。

CI aggregate state:

- failure
  - failure / timed_out / cancelled / action_required / stale等を確認
- pending
  - queued / in_progress / pending等を確認
- success
  - available signalが完了し、failure / pendingがない
- unknown
  - permissionなし / signalなし /判断不能

```text
type = pull_request_ci_observed
external_key = github:{repo}:pull:{number}:ci:{head_sha}
```

同じhead SHAのCI状態はupdateOrCreateで現在値へ更新する。
新しいcommitでhead SHAが変われば別Evidenceになる。

CI stateはTask progressを直接変更しない。

## Task mapping

Return EvidenceをどのTaskへ入れるかをAIに判断させない。

対象は:

1. current route Task
2. same Plan
3. PR ArtifactがTaskへ明示link済み

をすべて満たすTaskだけ。

V46.6で作ったPRはorigin Taskへ自動link済みなので、
そのlinkをreturn routing contractとして再利用する。

PR URLだけからTaskを推測しない。

## Idempotency

GitHub eventにはstable external keyを使う。

- review: review id
- merge: repo + PR number + merged
- CI: repo + PR number + head SHA

同じReturn Syncを何度実行しても同一eventのEvidenceを重複追加しない。

GitHubへのremote readが完了した後、PR Artifact snapshot更新とTaskEvidence updateOrCreateは1つのDB transactionで反映する。remote read中はDB transactionを保持しない。

## Context reevaluation

GitHub Evidenceが追加・更新されると、
ExecutionOrchestrationContextServiceのcanonical contextが変化する。

その結果:

- sync前に作られたExecution Packetはstale
- stale PacketからGitHub Change Candidateを作らない
- Distribution targetもcanonical context変化に応じて再評価対象になる

ただしReturn Layerは新しいPacketを勝手に生成しない。

UIでは:

- EvidenceをPlan / Taskへ反映
- 担当Contextを再評価

の導線を出す。

## Workflow lane boundary

`github_workflow_state` はCanovia側の作業判断レイヤー。

GitHub remote stateが:

- merged
- changes requested
- CI failed
- approved

になっても、Return SyncはCanovia workflow laneを自動変更しない。

例:

```text
GitHub: merged
Canovia lane: review
```

という一時的不一致は許容する。

remote factは `github_return_snapshot` とTaskEvidenceに記録し、
workflow laneの変更は人が行う。

## Progress boundary

Return Syncで自動変更しない:

- Task progress
- Task status
- Plan progress
- Dependency completion
- github_workflow_state

Return Syncで変更する:

- PR Artifact `github_return_snapshot`
- idempotent GitHub TaskEvidence
- collaborative PlanActivity audit

## UI

Execution OrchestrationのGitHub Handoff内へ
`RETURN LAYER` を追加する。

表示:

- Remote PR: Open / Closed / Merged
- Review: 承認確認 / 修正依頼
- CI: 成功 / 失敗 / 実行中 / 未取得
- Last Sync
- optional permission warning

Action:

- GitHubから結果を確認
- EvidenceをPlan / Taskへ反映
- 担当Contextを再評価

Merge確認済みでも
「Taskを自動完了していない」ことを明示する。

## Enterprise boundary

企業OrganizationではCI read permission追加が承認されない可能性がある。

V46.7はCI permissionを必須化しない。

最小構成:

- Contents: write
- Pull requests: write
- Metadata: read

だけでV46.4〜V46.7のWrite + Review / Merge Returnは成立する。

CIが必要なOrganizationだけOptional permissionを追加する。

CanoviaはOrganization policyを迂回しない。

## Non-goals

- webhook
- background polling
- automatic merge
- automatic review approval
- Task auto-complete
- progress auto-apply
- dependency auto-unblock
- Canovia workflow lane auto-sync
- AIによるTask mapping
- GitHub branch protection判定の再実装
- GitHubのmergeability独自判定
