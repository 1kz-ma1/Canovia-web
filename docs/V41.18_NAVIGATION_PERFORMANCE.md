# V41.18 — Navigation Performance

## Purpose

V41.17のproduction計測で、主要画面の待ち時間の96〜99%がDB待ちであり、
1 queryごとにおおむね80ms前後の固定コストが積み上がっていることを確認した。

V41.18 Step 1ではDBプランや構成を変更せず、Canovia側で削れる往復を先に削減する。
計測基盤は残し、merge後にproductionで再計測する。

## Changes

### Request-scoped behavior history

Baseline / User State / Recommendation Personalization / Recommendation /
Dashboardが個別に取得していたBehaviorEventとcompleted WorkSessionを、
1 request内ではRequestBehaviorHistoryから共有する。

BehaviorEventは最大90日、completed WorkSessionは最大28日をbounded historyとして取得し、
各consumerは必要な期間へmemory上でfilterする。

AI Plan Funnel等の不要なBehaviorEventは共有履歴へ含めず、
意思決定に必要なevent typeだけを取得する。

### Dashboard work-session reuse

- previous completed sessionは共有履歴から導出
- pending plan updateとactive sessionは1 queryへ統合
- process highlight用のtoday sessionsも共有履歴を再利用

### User State snapshot

Home表示ごとのupdateOrCreateをupsertへ変更。
存在確認SELECT + writeではなく1 statementで日次snapshotを保存する。

### Release Notes hot path

通常画面ごとに行っていたSchema::hasTable(release_notes)を削除。
productionのpublished release notesはfile cacheへ10分保存し、
ReleaseNoteのsave/delete時に即invalidateする。

DB cacheは使わないため、Aivenへのcache lookupを追加しない。

### Duplicate navigation tap guard

通常のsame-origin navigationを1回押した直後に:

- clicked linkをaria-busyへ
- pointer interactionを一時lock
- 120ms後にloading overlay
- 同一documentで続くnavigation tapをprevent
- pageshowでlock解除
- navigationが成立しなかった場合は8秒でfail-open

modified click / new tab / download / mailto / telは対象外。

## Preserved boundaries

- Recommendationのscoringロジックは変更しない
- User Stateの計算式は変更しない
- Plan / Task / Evidence semanticsは変更しない
- database session driverはこのStepでは変更しない
- V41.17 performance loggingは継続する

merge/deploy後、Home / Inbox / Roadmap / Timeline / Navigateを通常操作し、
V41.17のcanovia.performanceログで以下を比較する。

- elapsed_ms
- db_ms
- query_count
- duplicate_query_count
- behavior_events / work_sessions / information_schema / release_notesのtable summary

database sessionの固定コストは残るため、
Step 1後も主要ボトルネックであれば次Stepでsession strategyを検討する。
