# V58.70 — Plan Specialization as a separate, owner-confirmed dimension

## Goal

P1.1 separates a Plan's effective **Domain** (Study / Development / Career / Creative / General), **Collaboration** (personal / team), and **Specialization** (bookkeeping / software / occupation exploration, etc.). This is independent of earlier category text and does not require the user to choose categories during onboarding.

## Existing foundations

- V58.63: reversible HINANEX legacy-Creative Development access, per-browser selection.
- V58.67: `PlanIntentClassificationService` suggests domain, specialization and a team hint from objective text **without enabling collaboration**.
- V58.68: `plans.workspace_domain_override` allows **owner-confirmed** effective Workspace choice, leaving `category` and `is_collaborative` unchanged.
- V58.69: read-only team Task prerequisites and blockers, no inferred assignees.

## Implementation

- Add nullable `plans.workspace_specialization_override` VARCHAR(48), **no backfill**.
- `PlanSpecializationService::forPlan` returns `domain`, `key`, `label`, `source`, and `allowed`:
  - `owner_confirmed` only when an explicit override is compatible with the current effective Domain;
  - `inferred` only if the text classifier's inferred Domain matches the Plan's effective Domain and its specialization is allowed there;
  - `unconfirmed` otherwise. No forced category, no AI invented precision.
- Owner can select or reset specialization via a separate POST-equivalent PUT form on the Plan edit page. Selecting an activity never changes Workspace, category, collaboration members, Tasks or progress.
- The main Plan update flow retains a specialization if compatible. When the owner changes effective Domain such that the confirmed specialization is no longer valid, the incompatible specialization is cleared. No other Plan is touched.
- Owner-only authorization and server-side `Rule::in` against the **effective Domain** prevent cross-Domain values or collaborator writes. Unauthorized user cannot inspect the owner's Plan edit route either.
- A non-owner participant can still see their existing shared Plan according to existing access controls; this capability does not add edit permission.
- Taxonomy currently includes **Study**: bookkeeping, certification, school test, skill; **Development**: software, web service, game; **Career**: job search, occupation exploration; **Creative**: creative work. **General** remains unclassified.

## Important boundaries

- An inferred specialization is a tentative **label** only, not readiness, proof of certification, or a reason to auto-change tasks.
- Do **not** infer team membership from the Plan's title; `is_collaborative` stays explicit.
- Do **not** presume an HINANEX Plan is software development just because its title reads `HINANEX`. Owners can confirm the correct activity manually.
- Existing category fields and public/default rendering remain backward compatible, with no forced data migration.
- As the specialization taxonomy changes, current persisted values must remain safely read-only/fallback unless still domain-compatible.

## Validation

`tests/Feature/PlanSpecializationOverrideV5870Test.php` checks inference vs confirmation, reset, owner-only edits, invalid cross-Domain values, legacy Creative with Development override, other Plan isolation, and automatic removal of incompatible specialization on explicit Domain switch.

Migration is **nullable and non-destructive**. CI and migration recovery must pass before a merge. Render deploy and production user records remain separately unverified.
