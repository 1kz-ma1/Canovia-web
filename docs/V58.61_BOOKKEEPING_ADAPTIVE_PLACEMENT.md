# V58.61 — 簿記の現在地診断（Study Adaptive Starting Point）

## Goal / user scenario

「学校で簿記3級を学習している。理解度に応じて授業内容を復習し、余裕があれば2級へ進みたい。」

Canovia should not force a fixed `3級を全範囲完了 → 2級` sequence. A learner can review a weak prerequisite and trial a new grade independently. The diagnostic informs—not controls—that choice.

## Implemented user path

1. An existing Study Plan whose title or description explicitly mentions `簿記` shows `現在地を診断する` in Study **学習準備**.
2. User selects whether to prioritize 3級 review or also try 2級; takes 12 original Canovia multiple-choice journal-entry questions (3 each across 4 foundation topics).
3. Server grades deterministically (correct keys never included in the rendered question form before submission), provides answer feedback, topic scores, and concrete next-action examples. The user must explicitly edit Plan Tasks; nothing is automatically changed.
4. If a prerequisite topic has <67% (0–1 of 3 correct), suggest targeted review, regardless of the overall score or advance preference. The reusable, pure `AdaptiveStartingPointPolicyService` makes this decision from ordered prerequisite keys, per-topic evidence, overall result and user stretch interest.
5. If no such gap is found, overall >=83%, and user opts to explore 2級, suggest **trialing introductory 2級 content** while maintaining periodic 3級 reviews. This is **not** 3級 mastery, Grade 2 readiness, or pass prediction.
6. Otherwise, suggest review and a different future check; never block grade advancement.
7. Record the score, four topic-level scores and the user's advance interest under the current user's Plan. Revisit the result and allow a new diagnostic without overwriting old records.

A 12-question check is intentionally only a first hypothesis: it does not evaluate the entire Nissho 3級 scope, practical input-speed, retention, or a full 2級 prerequisite map. It is a **small working vertical slice** rather than complete 3級/2級 course coverage.

## Existing schema reuse, separated provenance

Persistence reuses `study_score_observations` with:

- `metric_key = bookkeeping_foundations_percent`
- `metric_label = 簿記3級基礎の現在地`
- `source_kind = mock_exam` with `source_label = Canovia簿記基礎診断`
- `components = {basic_journal, receivables_payables, cash_deposits, adjusting_entries, _advance_interest}`
- `score_value = 0..100`, `unit = percent`

**Do not** treat this in-app diagnostic as a separate official grade score, AP/TOEIC/IELTS scaled result, or completed Task evidence. The generic external score page and `StudyWorkspaceStateResolver` exclude this dedicated `metric_key` from external-score-baseline projections. The result is visible only on its dedicated bookkeeping route, filtered by actor / Plan. Plan Task progress, status, and evidence tables are unchanged.

No new tables, autonomous Task mutations, paid-only behavior, or prompt AI calls are introduced. Same `request_id` retry converges on the existing row and cannot reuse an observation belonging to another Plan/actor.

## Checks / release policy

Regression tests: `tests/Feature/BookkeepingPlacementV5861Test.php`, plus the existing Study Workspace / Score Baseline suites. CI needs to test those routes together.

This is a narrowly scoped additive UI and deterministic grading flow. If any required CI fails, or a concerning stored-data/permissions behavior appears, leave the PR open. `main` merge is not production verification.
