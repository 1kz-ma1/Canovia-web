# V46.8 GitHub Evidence → Task Decision

## Goal

V46.7でGitHubからCanoviaへ戻したReview / Merge / CI Evidenceを、
Taskへ直接自動適用せず、人が確認できるTask Decision Candidateへ変換する。

```text
GitHub Return Snapshot
        ↓
deterministic decision
        ↓
Task Decision Candidate
        ↓
Human Confirmation
        ↓
Task state mutation
        ↓
Execution Context stale
        ↓
Packet / Distribution再評価
```

GitHub Evidenceは事実、Task状態はCanovia上の判断であり、両者を分離する。

## Non-AI decision

V46.8のCandidate生成にAIは使わない。

入力:

- current Task state
- linked Pull Request Artifact
- latest `github_return_snapshot`

からdeterministicに候補を生成する。

AIが:

- Taskを選ぶ
- 完了を決める
- 進捗率を推測する
- GitHub signalの優先順位を勝手に決める

ことはない。

## Candidate

`GitHubEvidenceDecisionService::candidate()`

Candidate:

```text
schema_version
flow = github_evidence_decision
task_id
pull_request_artifact_id
pull_request_number
recommendation
headline
reason

signals
  merged
  approved_reviewers
  changes_requested_reviewers
  ci_state
  head_sha
  merge_commit_sha

allowed_actions[]
proposed
  complete
  continue
  wait

snapshot_fingerprint
task_fingerprint
```

Candidateは表示ProjectionでありDB Entityにしない。

## Recommendation semantics

### Task already done / progress >= 100

`no_change`

GitHub EvidenceはContextとして残すが、
Return Layerから完了状態を上書きしない。

### Task cancelled

`no_change`

Return Layerから自動再開しない。

### merged + no negative signal

`complete`

完了候補として表示する。

ただしmergeだけでTaskを完了しない。
「Task成功条件を満たした」とユーザーが確認した場合だけ反映する。

### merged + changes requested / CI failure

`manual_review`

GitHub上で相反するsignalが存在するため、
Canoviaは優先順位を決めない。

Human Confirmationで:

- complete
- continue
- wait

から選択できる。

### changes requested / CI failure

`continue`

Task progressを下げず、
現在Taskをdoingとして修正Actionへ戻す候補。

### CI pending

`wait`

status / progress / remainingを変えず、
次の確認Actionだけ更新する。

### approved / CI success but not merged

`wait`

merge確認前なのでTask完了候補にはしない。

## Mutations

### complete

Human Confirmation後のみ:

```text
status = done
progress_percent = 100
remaining_minutes = 0
progress_reason = GitHub merge + user confirmation
```

### continue

Human Confirmation後のみ:

```text
status = doing
next_action_note = review / CI failureに応じた修正Action
```

変更しない:

- progress_percent
- remaining_minutes

GitHubの否定的signalから「何%戻ったか」を推測しない。

### wait

Human Confirmation後のみ:

```text
next_action_note = 次にGitHubで確認するAction
```

変更しない:

- status
- progress_percent
- remaining_minutes

## Confirm-time revalidation

Task mutationの直前にGitHubを再取得する。

```text
UI表示
  snapshot fingerprint = A
  task fingerprint = X
        ↓
ユーザー確認
        ↓
GitHub Return Sync
        ↓
fresh snapshot fingerprint = ?
fresh task fingerprint = ?
```

A / Xと一致する場合だけ反映する。

GitHubまたはTaskが変わっていた場合:

- 最新GitHub Evidenceは保存する
- Task mutationは行わない
- 最新状態を再表示
- Human Confirmationをやり直す

## Snapshot fingerprint

`fetched_at` のような同期時刻だけではstaleにしない。

fingerprint対象:

- PR number / state / draft / merge state
- merge commit / head SHA
- head/base ref
- PR updated / closed state
- latest reviewer decisions
- CI aggregate state
- bounded Actions / Checks signal
- combined status summary

remote stateの意味が変わったときだけCandidateをstaleにする。

## Task fingerprint

Task側は:

- title / description
- status
- progress
- remaining
- progress_reason
- next_action_note
- estimate
- priority
- activation cost
- updated_at

を含む。

Human Confirmation中にTaskが変更された場合は反映しない。

## Transaction boundary

GitHub remote readはDB transaction外で行う。

fresh remote stateを確認後、
Task mutationだけをDB transaction + row lockで反映する。

distributed transactionは作らない。

## Audit

反映成功時:

`github_evidence_decision_applied`

をPlanActivityへ記録する。

metadata:

- action
- PR Artifact ID
- PR number
- snapshot fingerprint
- Evidence IDs
- before
- after

GitHub Evidence自体のactorと、
Task判断を確定したCanovia userを分離して追跡できる。

## UI

RETURN LAYER内へ `EVIDENCE DECISION` を追加する。

表示:

- recommendation
- current Task status / progress
- Merge signal
- Review signal
- CI signal
- 実際に変更されるTask field

Human action:

- このTaskを完了として反映
- 修正対応を続ける
- 次の確認Actionだけ更新

ボタン押下前に「GitHubを再確認する」ことを明示する。

DeveloperGithubEvidence capabilityまたはGitHub App設定がない場合、
Candidateは読めるが反映Actionは出さない。

## Context reevaluation

Task mutation後はTask canonical stateが変わるため:

- current Execution Packet
- Distribution target

は通常のcontext_fingerprint機構でstaleになる。

V46.8は新しいPacketを自動生成しない。

ユーザーが現在Contextから再生成する。

## Progress safety

V46.8で自動推測しない:

- PR approved → progress %
- CI success → progress %
- changes requested → progress decrease
- CI failure → progress decrease
- merge → auto done

完了だけはGitHub merge factを根拠にCandidateを出せるが、
100% / doneへのmutationには必ずHuman Confirmationを要求する。

## Non-goals

- Task自動完了
- 自動progress適用
- 自動dependency unlock
- follow-up Task自動生成
- Issue自動生成
- GitHub merge
- AIによるTask state decision
- webhook
- background polling
- Organization policy bypass
