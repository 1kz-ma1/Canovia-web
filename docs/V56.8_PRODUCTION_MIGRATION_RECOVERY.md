# V56.8 Production Migration Recovery

## Goal

Restore Render production deployment after schema/migration drift blocked every deploy from V53.2 onward.

## Incident

Render service `Canovia` is configured correctly:

- repository: `1kz-ma1/Canovia-web`
- branch: `main`
- auto deploy: enabled

The last live deploy is V53.1.

Starting with V53.2, deploy startup repeatedly failed while running Laravel migrations:

`SQLSTATE[42S01]: Base table or view already exists: 1050 Table 'intelligence_decision_traces' already exists`

The physical table exists in production, but Laravel still considers
`2026_10_04_000200_create_intelligence_decision_traces_table` pending.

That mismatch keeps the old V53.1 instance live even though newer commits build successfully.

## Recovery contract

The V53.2 migration becomes safely idempotent for one specific drift case:

1. if `intelligence_decision_traces` does not exist, create it exactly as before
2. if it already exists, verify the complete expected column contract
3. only when that contract is complete, return successfully so Laravel can record the migration as applied
4. if any required column is missing, fail loudly instead of silently accepting a partial schema

No production rows are dropped or rewritten.

## Scope

This change does not alter:

- Intelligence semantics
- table columns
- indexes or foreign-key definitions for fresh installs
- application behavior
- Current Action
- Workspace Mode
- Study / Development logic

It only reconciles migration bookkeeping with an already-existing production table.

## Validation

Validation must cover:

- fresh migration chain still succeeds
- calling the V53.2 migration against an already-complete table is idempotent
- V53.2 Intelligence Decision / Readiness regression remains green
- frontend build and Blade compile remain green
