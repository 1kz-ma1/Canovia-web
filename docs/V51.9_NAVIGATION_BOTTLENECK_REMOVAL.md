# V51.9 Navigation Bottleneck Removal

## 背景

V51.8をiOS PWA実機で計測した結果、Client sideのCore Surface切替はcache hit時に約92〜108msだった一方、Execution (`/navigate`) のserver処理が最大約13.98秒まで伸びていた。

該当request:

- elapsed: 13,984ms
- DB: 13,684ms
- query count: 158
- Task query count: 143
- identical Task SELECT: 142回
- identical Task SELECT total: 約11,988ms

別requestでも:

- elapsed: 4,319ms
- query count: 41
- identical Task SELECT: 26回
- duplicate Task SELECT total: 約2,130ms

Client mountは0〜1msであり、主因はUI描画ではなくserver DB N+1だった。

## Root Cause

`RecommendationService::recommend()` はcandidate Taskごとに:

`$task->dependencyIds()`

を呼ぶ。

`Task::dependencyIds()` はcanonical relation `prerequisites` がload済みならmemory上のCollectionを使うが、未loadなら:

`$this->prerequisites()->pluck('tasks.id')`

を実行する。

NavigationControllerはTaskを:

- prerequisite (legacy singular)

のみeager loadしており、

- prerequisites (canonical many-to-many)

をloadしていなかった。

そのためTask数に比例してcanonical dependency queryが発生していた。

## Fix

NavigationControllerのowned Plans読込時に:

- tasks.prerequisite
- tasks.prerequisites

を同時にeager loadする。

Recommendation scoringやdependency判定ロジックは変更しない。

## Regression Contract

多数Task + canonical task_dependenciesを持つPlanで `/navigate` をrenderしても、Task table SELECT数はTask数に比例して増えてはならない。

Feature testでTask related SELECTを計数し、bounded query contractを固定する。

## Scope

V51.9 first passでは実機で最大のボトルネックのみを優先する。

その後の候補:

- database session roundtrip
- Home query count
- Core Bundle prefetch cost
- repeated recommendation profile calculations

これらはN+1解消後の再計測値で優先度を判断する。

## No migration

DB schema変更なし。
