# V58.13 Question Candidate Reliability Signal

Status: implemented / validated  
Branch: `feature/v58-13-question-candidate-reliability`

## 1. Goal

Reflect Question Candidate Human Review and real Question Bank reuse into
Practice Reliability without confusing learner performance with question
quality.

```text
Native AI Candidate
→ Human Review
   ├ promoted
   └ rejected
→ promoted Question Bank asset
→ selected / assessed reuse
→ bounded operations signal
→ Practice Reliability question_quality
```

V58.13 converts an existing product-operation loop into a small empirical signal
while retaining the deterministic Reliability baseline.

## 2. Learner correctness is explicitly excluded

V58.13 does not use:

- learner score_percent;
- per-question correct / incorrect ratio;
- weakness_topics;
- learner mastery;
- Task progression.

A valid difficult question can produce low correctness. Learner correctness is
therefore not interpreted as Question quality.

Dedicated validation changes an assessed learner result from correct / 100% to
incorrect / 0% and confirms the Candidate Reliability signal does not change.

## 3. Exam-profile scope

Candidate operations are scoped by:

`exam_profile_key`

The key is resolved from:

1. current Practice strategy `exam_profile.key`;
2. existing Session `selection_context.strategy.exam_profile.key`.

If no exam profile is available:

- status = unavailable;
- Candidate adjustment = 0;
- existing Practice Reliability remains unchanged.

## 4. Human Review metrics

For the resolved exam profile, V58.13 projects:

- candidate_count;
- generation_occurrence_count;
- pending_count;
- reviewed_count;
- promoted_count;
- rejected_count;
- promotion_rate_percent.

Definition:

```text
reviewed_count = promoted + rejected
promotion_rate = promoted / reviewed
```

Pending Candidates are intentionally excluded from the promotion-rate
denominator because no Human Review decision exists yet.

`generation_occurrence_count` sums each Candidate's existing
`generation_count`, preserving repeat-demand information without treating it
as an approval signal.

## 5. Reviewed Question reuse

Promoted Candidates already point to:

`promoted_question_id`

V58.13 scans at most the latest 500 StudyPracticeSessions and intersects their
`selected_questions.question_id` values with promoted Candidate Question IDs.

Metrics:

- reused_question_count;
- selected_reuse_count;
- assessed_reuse_count;
- current_session_promoted_candidate_count.

Definitions:

### selected_reuse_count

Every selected promoted-Candidate Question occurrence in the bounded Session
window.

### assessed_reuse_count

Selected promoted-Candidate Question occurrences in Sessions that have at least
one StudyPracticeAttempt.

This is operational reuse evidence only.

The attempt's score and correctness are never read by the signal.

### reused_question_count

Unique promoted Candidate Questions that were selected at least once.

### current_session_promoted_candidate_count

How many selected Questions in the current Session came from promoted Candidate
assets.

## 6. Minimum review boundary

V58.13 does not change Reliability after only a few admin decisions.

Minimum Human Review sample:

`5 reviewed Candidates`

If:

`reviewed_count < 5`

then:

- status = observing;
- applied_adjustment = 0.

The UI can still show that Candidate operations have started.

## 7. Evidence-strength projection

V58.13 uses evidence volume to scale how much the Human Review signal can affect
the baseline.

```text
review_weight = min(1, reviewed_count / 20)
reuse_weight  = min(1, assessed_reuse_count / 20)

evidence_strength =
  0.75 * review_weight
  + 0.25 * reuse_weight
```

UI exposes:

`evidence_strength_percent`

This value is a bounded maturity / evidence-volume indicator.

It is not:

- a confidence interval;
- statistical significance;
- measured model accuracy.

Human Review volume has the larger weight because promotion / rejection is the
direct quality-control boundary. Assessed reuse strengthens evidence maturity
but does not itself imply quality.

## 8. Raw Human Review adjustment

Neutral Human Review center:

`70% promotion rate`

Raw adjustment:

```text
round((promotion_rate_percent - 70) / 5)
```

Then clamp:

`-6 ... +6`

Examples:

- 100% promotion → raw +6
- 70% promotion → raw 0
- 40% promotion → raw -6

This is a product calibration, not a statistical estimate of true Question
quality.

## 9. Applied adjustment

After the 5-review minimum is met:

```text
applied_adjustment =
  round(raw_adjustment * evidence_strength)
```

Then clamp again:

`-6 ... +6`

This means an early 100% promotion sample cannot immediately add the full +6.

Example validated path:

```text
5 / 5 promoted
0 assessed reuse
→ raw +6
→ applied +1

5 / 5 promoted
20 assessed reuse
→ stronger evidence volume
→ applied +3
```

## 10. Provider boundary

Candidate adjustment affects only:

- native_ai;
- hybrid_ai.

It modifies only the existing:

`question_quality`

axis.

Baseline values remain:

- Question Bank = 95;
- Hybrid AI = 84;
- Native AI = 74;
- External AI = 66.

For Native / Hybrid:

```text
question_quality =
  clamp(
    base_question_quality
    + candidate_adjustment,
    0,
    100
  )
```

Question Bank receives no additional Candidate adjustment because a promoted
Candidate used from Question Bank is already under the reviewed Bank contract.

External AI receives no Candidate adjustment because Canovia's Candidate
operations do not govern that source.

## 11. Reliability output

`StudyPracticeReliabilityService` now returns top-level:

`candidate_signal`

The existing `question_quality` metric additionally exposes:

- base_score;
- candidate_adjustment.

The existing overall Reliability weighting remains unchanged:

- question quality 30%;
- grading reliability 30%;
- coverage 20%;
- method fit 20%.

V58.13 changes only the bounded input to the question-quality axis.

## 12. UI

Practice Reliability now exposes a collapsed:

`Question Candidate運営実績`

detail when an exam-profile Candidate signal is available.

It shows:

- Human Review count;
- promoted count;
- assessed reuse;
- Signal strength;
- promotion rate;
- selected reuse;
- current Session promoted-Candidate selections;
- applied Reliability adjustment.

The UI explicitly states:

`学習者の正答率はQuestion品質の判定に使っていません。`

This prevents the operational quality-control signal from being confused with
learner performance.

## 13. Disclaimer

Practice Reliability still explicitly says it is not measured AI accuracy.

The disclaimer now states that, when available, a small Candidate Human Review /
reuse signal is included in addition to:

- source provenance;
- grading method;
- Question Bank coverage;
- Study Activity fit.

## 14. Performance boundary

Reuse projection scans at most:

`500 recent StudyPracticeSessions`

This keeps the current implementation bounded while avoiding a new aggregate
table or migration.

If Candidate operations grow enough that this bounded read becomes expensive, a
later version can introduce durable aggregate telemetry without changing the
V58.13 output contract.

## 15. No migration / provider call

V58.13 uses existing:

- practice_question_candidates;
- questions;
- study_practice_sessions;
- study_practice_attempts.

No migration is required.

The signal is DB-only and performs no Native AI or external-provider request.

## 17. Result

Practice Reliability now distinguishes three different things:

```text
deterministic provider baseline
+ bounded Human Review operations signal
+ bounded reviewed-question reuse maturity
```

while continuing to exclude learner correctness from Question quality.

This completes the V41.10 follow-up "Question Candidate品質・利用実績をReliabilityへ反映"
at the operational reliability boundary.
