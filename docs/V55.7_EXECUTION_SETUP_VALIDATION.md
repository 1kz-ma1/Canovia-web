# V55.7 Execution Setup Validation

## Goal

V55.7 validates the first user-facing Execution Ecosystem choice without turning provider selection into a mandatory execution screen.

The UX rule is:

```text
Planning / Workspace
→ show provider choice only when more than one viable provider exists

Normal Start
→ one action
→ stored preference or safe default
→ resolved provider
→ launch
```

Study is the first validation domain.

No real third-party API, OAuth connection, public provider API, or external Activity callback is introduced.

## Relationship to V55.6

V55.6 established:

```text
Execution Capability
→ Provider Catalog
→ PlanExecutionPreference
→ Execution Resolver
→ ExecutionActivity
→ TaskEvidence
```

V55.7 adds the first visible selection and launch layer:

```text
Study Workspace
→ Execution Setup
→ PlanExecutionPreference
→ normal Study Start
→ Execution Resolver
→ Execution Launch Resolver
→ Native route or Validation External surface
```

The V55.6 Activity model is not yet connected to the Validation External surface.

## Feature flag

The external validation provider is opt-in:

```text
CANOVIA_EXECUTION_SETUP_VALIDATION_ENABLED
```

Default:

```text
false
```

When disabled:

- no Validation External provider is registered
- Study Workspace has only the Native provider
- Execution Setup UI does not appear
- Study Start follows the existing Native route
- existing production behavior remains unchanged

## Validation provider

When the flag is enabled, the Provider Catalog adds:

```text
key:
validation.study.practice.external

name:
External Practice Partner (Validation)

kind:
external

capability:
study.practice
```

This provider is deliberately non-production.

It makes no external request.

Its purpose is to validate:

- provider choice visibility
- preference persistence
- resolver precedence
- launch handoff
- Native recovery

## Execution Setup evaluation

`ExecutionSetupService` evaluates a Plan + Task.

Flow:

```text
Task
→ ExecutionCapabilityResolver
→ enabled providers for capability
→ valid PlanExecutionPreference?
→ current selected provider
→ ExecutionSetupData
```

Setup has a meaningful choice only when:

```text
enabled provider count > 1
```

For normal production Study Practice with the flag disabled:

```text
study.practice
→ canovia.study.practice only
→ no setup UI
```

With validation enabled:

```text
study.practice
→ canovia.study.practice
→ validation.study.practice.external
→ setup UI becomes available
```

Recall and Resource Study still have one provider and therefore do not show the selector.

## Onboarding precedence

Execution Setup must not interrupt existing Study preparation.

Current Study onboarding remains:

```text
1. create Plan
2. capture Study Scope
3. record first Study Evidence
```

V55.7 evaluates Execution Setup only after `WorkspaceModeOnboardingService` reports onboarding complete.

Therefore:

```text
new Study Plan
→ Scope onboarding
→ first Evidence onboarding
→ normal Study Workspace
→ Execution Setup only if provider choice exists
```

There is no global setup screen after Plan creation.

## Study Workspace UI

When multiple providers exist and no explicit preference exists:

```text
EXECUTION SETUP
この学習を、どこで実行する？
```

The user sees the available Native / External choices.

The selector is non-blocking:

```text
no selection
→ Start still works
→ Native fallback remains valid
```

After the user chooses a provider:

- `PlanExecutionPreference` persists the selection
- the prominent first-choice prompt disappears
- Workspace shows the selected execution method compactly
- `実行方法を変更` allows later changes

The controls are only shown to users with edit permission.

## Preference persistence

The existing V55.6 table is reused:

```text
plan_execution_preferences
```

V55.7 writes:

```text
plan_id
capability
provider_key
user_selected = true
```

The scope remains:

```text
Plan + Capability
```

This is intentionally important for Study Intelligence Task projection.

If Start creates a new Task for the same capability:

```text
Plan preference
→ still applies to projected Task
```

The preference is not bound to one Task ID.

## Normal Start integration

V55.7 connects provider resolution to the existing canonical Study Start:

```text
POST /plans/{plan}/study-action/execute
```

This route is already used by:

- Study Workspace Current Action
- Home Current Action
- Overview Current Action

Therefore the provider decision is not duplicated in individual views.

Flow:

```text
Study Start
→ refresh Study Adaptive Action
→ resolve/reuse/project Task
→ ExecutionResolver
→ ExecutionLaunchResolver
→ destination
```

## ExecutionLaunchResolver

V55.7 introduces the first launch resolver boundary.

For Study:

```text
Plan + Task + existing fallback route
→ ExecutionResolver
→ provider
→ launch decision
```

Native providers preserve the existing Study route.

Validation External provider maps to:

```text
execution.validation.study_practice
```

The resolver returns a launch decision object rather than a redirect response.

This preserves the V55.6 separation:

```text
provider selection
!= HTTP response
```

Future launch types can extend the same responsibility toward:

- web URL
- Universal Link
- Deep Link
- installed app handoff

without moving provider-specific logic into Current Action views.

## Validation External surface

Route:

```text
GET /execution-validation/study/{plan}/tasks/{task}
```

The surface displays:

- selected provider
- target Task
- confirmation that the handoff path worked

It explicitly does **not** perform:

- external network request
- OAuth
- external app opening
- Activity callback
- progress mutation
- Evidence creation

The surface only validates:

```text
saved preference
→ resolver
→ launch handoff
```

## Native fallback

Native remains the safe default.

Resolver precedence remains:

```text
1. valid explicit Plan preference
2. enabled Native provider
3. existing fallback
```

If the validation feature flag is later disabled while a validation preference remains stored:

- the external provider is no longer present in the catalog
- the stale preference is not considered valid
- `ExecutionResolver` falls back to Native

No migration or preference cleanup is required for safety.

## UI / product boundary

V55.7 does not add provider choice to:

- every Start click
- `/navigate`
- Plan creation
- first-run flow
- Study Scope capture
- first Evidence capture
- Development Workspace
- Career Workspace
- General execution

Provider choice remains a configuration concern, not an execution-time chooser.

## Database impact

No new migration.

V55.7 reuses:

- `plan_execution_preferences`

No existing columns change.

No backfill is required.

## Runtime / cost boundary

With the validation feature flag disabled:

- no new external provider
- no external request
- no AI request
- no visible provider UI

With the flag enabled:

- one additional static provider definition
- one Plan preference lookup when setup is evaluated
- no external network request
- no AI request

Study Intelligence and Evidence scoring are unchanged.

## Safety / architecture invariants

V55.7 preserves:

```text
Recommendation != Advertising
```

No sponsored signal enters provider selection.

It also preserves:

```text
Execution choice
!= Activity truth
```

Launching a provider does not:

- complete a Task
- change progress
- create Evidence
- change Readiness

Those actions require later Activity Integration and explicit Evidence projection.
