# V41.14 Goal Context & Guided Execution

## Purpose

Canoviaが事前に想定していない目標でも、AIの推測で長期計画を埋めるのではなく、

```text
Goal
  ↓
Goal Context
  ↓
Current State / Known / Unknown
  ↓
Provisional Plan or Measurement
  ↓
Execution
  ↓
Reflection / Evidence
  ↓
Current State update
  ↓
Plan adaptation
```

というループで伴走できる基盤を作る。

V41.14は4 Stepで進める。

---

## Step 1 — Goal Context Foundation

### Data model

`goal_contexts`

- user_id / actor_token
- plan_id nullable / unique
- desired_state
- current_state_summary
- readiness_score
- readiness_state
- status
- last_assessed_at

Plan作成前のGoal Discoveryにも使えるよう `plan_id` はnullable。
既存Planは必要になった時点でlazyにGoal Contextを生成できる。

`goal_context_facts`

Types:
- target
- current_state
- signal
- constraint
- driver
- unknown

Sources:
- user_answer
- inbox
- evidence
- native_ai
- system

States:
- confirmed
- candidate
- unknown
- superseded

Native AI由来のcandidateはconfirmed factとして扱わない。
同じkeyについて人がconfirmed factを登録した場合、candidate / unknown / old confirmedをsupersededへ送る。

### Readiness

ReadinessはAI自己評価ではなく、Canovia Policyによるdeterministic coverage。

```text
Desired State        25
Current State        25
Success Signal       20
Constraints          10
Driver / Measurement 20
------------------------
Total               100
```

State:
- LOW: 0-39
- MEDIUM: 40-69
- HIGH: 70-100

`unknown` や `candidate` はscoreへ加点しない。

### Existing Plan integration

新しいPlan作成時:
- Goal Contextを自動生成
- Plan titleをconfirmed targetとして保存
- 現行のAI Plan Builderへのredirectは維持

既存Plan:
- AI Plan Builder等で必要になった時点でlazy生成
- duplicate contextを作らない

Plan title変更:
- desired_stateが旧Plan titleのままなら同期
- ユーザーがより具体的なdesired_stateへ育てている場合は上書きしない
- goal_title factは最新confirmedへ更新

### Initial Plan AI context

Plan Builderへ以下を渡す:

- Desired State
- Current State Summary
- deterministic Readiness
- CONFIRMED FACTS
- UNCONFIRMED HINTS
- KNOWN UNKNOWNS

AI rules:
- confirmed informationを聞き直さない
- candidateを事実扱いしない
- unknownを推測で埋めない
- 質問は一度に並べず、計画への影響が最大のものを優先
- LOW / MEDIUMでもProvisional Planは生成可能
- 現在地不足が重大ならMeasurement Taskを先に置く
- deadline未設定だけを理由にPlan生成を停止しない
- 時間経過自体をProgress evidenceにしない

## Step 2 — Adaptive Goal Discovery + Live Preview

Implemented.

`/plans/create` is now the Goal Discovery entry. The legacy detailed Plan form remains at `/plans/create/manual`.

```text
Desired State only
  ↓
Goal Context without Plan
  ↓
Live Context Preview
  ↓
one high-value question
  ├ quick answer
  ├ free text / chat-like answer
  └ skip / unknown
  ↓
Context update
  ↓
Provisional Plan at any time
```

Generic question order:
1. Current State
2. Success Signal
3. Constraint
4. Measurement / Driver

Success Signal uses a two-step structure only when useful:
- first identify numeric / capability / result style
- then ask one short detail question

Input mode is never selected upfront.

`interaction_profile` records observable interaction only:
- quick_answers
- text_answers
- skips
- answered
- preferred
- last_mode

Presentation policy:
- 2+ text answers and text > quick -> conversational
- 2+ quick answers and quick dominates -> quick
- 2+ skips -> compact; Provisional Plan appears before the next question
- otherwise balanced

No personality / MBTI / psychological type is inferred.

Readiness hardening:
- numerical score remains deterministic coverage
- HIGH additionally requires Desired State + Current State + Success Signal
- candidate / unknown never increases readiness

Ownership:
- Goal Context stays user- or guest-actor-owned before Plan creation
- a logged-in user may claim only their matching guest actor context
- another actor receives 404
- stale questions cannot overwrite a newer context state

Plan attach:
- Provisional Plan can be created at any readiness
- Goal Context `desired_state` is the canonical Plan title for discovery-created Plans
- client hidden title cannot rewrite the Goal Context
- existing detailed Plan creation remains available as fallback

Inbox / Evidence-origin Goal Discovery input remains a future extension of Step 2; the current implementation supports quick, text and explicit unknown without blocking Plan creation.

## Step 3 — Guided Execution + Reflection Evidence

Implemented.

Execution hierarchy:

```text
Specialized Tool
  ↓ unavailable
Guided Execution
  ↓ unsuitable / low confidence
Timer fallback
```

### Guided Execution Policy

Guided Execution is Free and generic.

Primary examples:
- sports practice / match / training
- sales meeting / customer visit / negotiation
- interview / meeting
- presentation / live delivery
- gym / running / physical practice
- other real-world actions with observable outcomes

Focused desk work keeps Timer as Primary:
- implementation / coding / debugging
- reading / research / writing
- planning / thinking
- normal study work when no specialized Study Tool applies

When policy confidence is insufficient, Guided Execution remains available as a secondary Tool and Timer stays Primary.

Specialized recommended tools always win over Guided Execution.

### Before Action

`guided_executions` stores:
- action intent
- focus points
- observation points
- success / learning signal

Before Action is not Evidence.
It does not create a WorkSession and does not start a Timer.

The user may leave Canovia and execute in the real world.

### Reflection

After Action captures:
- outcome rating
- actual outcome
- observations
- discoveries
- next adjustment

Only confirmed Reflection creates `guided_execution_reflected` Task Evidence.

Evidence confidence:
- self report only: 0.55
- at least one structured reflection field: 0.65
- at least two structured reflection fields: 0.70

These values intentionally remain below strong externally verified Evidence.
Guided Reflection never mutates Task progress automatically.

### Identity / Idempotency

- Guided Execution belongs to the person who performed the action, not merely the Plan
- collaborators cannot complete another person's Reflection
- guest actor records can be claimed by the same actor after login
- `prepare_request_id` and `reflection_request_id` provide mutation identity
- Reflection uses a row lock and Evidence external key
- repeated Reflection does not duplicate Evidence

### UI

Guided Execution is available from:
- Home Today's Route
- Home Current Task
- Plan Primary Action
- Canovia Tools

When Guided Execution is Primary:
- Timer is not shown next to it
- recommendation minutes are not emphasized
- the UI explains that time tracking is unnecessary

The resulting Task Evidence keeps:
- what the user intended
- what actually happened
- what was observed
- what was learned
- what to change next

## Step 4 — Goal Pattern Demand / Tool Discovery

未知Goalを汎用伴走しながら、専用Tool化の需要を観測する。

Aggregate candidates:
- goal pattern
- recurring current-state signals
- recurring measurement tasks
- recurring guided-execution structures
- preferred input interaction
- points where generic support is insufficient

Adminでは需要を集計するが、AIが自動で新Toolを公開しない。

Practice Demandと同様、
利用実態 → product demand → human product decision
の順にする。
