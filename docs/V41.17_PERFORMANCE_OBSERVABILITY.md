# V41.17 — Performance Observability

## Purpose

Canoviaの画面遷移が遅い原因を、推測ではなくproduction実測で特定するための一時診断基盤。

最適化そのものはこのStepでは行わない。計測結果から最大の待ち時間を特定してから、次Stepで改善する。

## Measured routes

- `/` Home
- `/inbox`
- `/roadmap`
- `/timeline`
- `/navigate`
- `/calendar`

GET / HEADだけを対象とする。

## Log event

Render application logへ `canovia.performance` を1 requestにつき1件出力する。

記録するもの:

- request elapsed time
- DB query total time
- non-DB time
- DB share
- query count
- duplicate query count
- DB Session query count / time
- table別 query count / total ms / max ms
- duplicate query shape
- slow query shape
- Service Worker network retry / preload / prefetch flags
- session driver / DB connection name

## Privacy boundary

以下は記録しない。

- SQL本文
- query bindings
- actor token
- user id
- session id
- prompt / conversation / Inbox本文などのユーザー入力
- DB host / credential

Query shapeはSQL文字列のSHA-256先頭16文字だけを利用し、値を保持しない。
テーブル名・operation(select/update等)だけ診断用metadataとして記録する。

## Enable / Disable

productionでは診断期間中default ON。

`PERFORMANCE_LOG_ENABLED=false`

を設定するとcode deployなしで次回起動以降OFFにできる。

## Interpretation

まず `elapsed_ms` と `db_ms` を比較する。

- DB shareが高い: query回数・重複shape・特定tableを優先
- DB shareが低い: PHP/service構築、Blade、外部I/O等を優先
- 特定shapeのmax_msが大きい: index/query plan/DB性能候補
- 1 queryは短いがduplicate countが多い: N+1 / service間の再取得候補
- sessions比率が高い: DB Session自体も分離して検討

同じ操作を複数回行い、cold start直後とwarm requestを混同しない。
