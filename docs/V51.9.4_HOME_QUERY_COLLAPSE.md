# V51.9.4 Home Query Collapse

## 背景

V51.9.3でproductionへ `DB_PERSISTENT=true` を導入し、Execution / Timelineのavailability relation N+1もbatch化した。

V51.9.2実機計測時のHomeは:

- 2.55〜2.82s
- 23 queries
- session query: 0
- client cache hit: 92ms

まで下がっていたが、server側にはまだ明確な不要queryが残っていた。

V51.9.4では表示仕様を変えず、Homeのdead projectionとrelation再取得を削る。

## 1. Legacy collaborationPlans membership projection removal

Primary Homeは現在Action Home projectionを表示しており、`collaborationPlans` 変数をBlade / client runtimeのどこからも参照していない。

旧HomePageDataServiceは共同Planが1件でもあると:

- memberships
- activity_logs

をloadし、その後 `collaborationPlans` を生成して返していた。

このうちmembership count projectionは未使用だったため:

- Homeの `memberships` feature loadを削除
- `collaborationPlans` collection生成を削除
- Home return contractから `collaborationPlans` を削除

する。

Action Homeの共同作業Signalには `activity_logs` が必要なので、activity logのloadは維持する。

これにより共同Planがあるaccountでも `plan_members` SELECTを1回削減する。

## 2. WorkLog.task relation reuse

CoreContextのHome common pathでは既に `tasks` をloadしている。

旧 `loadWorkLogs()` はさらに:

```php
workLogs -> with('task')
```

を実行し、WorkLogが参照するTaskを別SELECTで再取得していた。

V51.9.4では:

- Plan.tasksが既にload済みの場合
  - WorkLogだけをload
  - task_idで既存Task modelをindex
  - `WorkLog::setRelation('task', ...)` で同一model instanceをreuse
- tasksが未loadの場合
  - 従来どおり `with('task')`

とする。

これによりHomeのWorkLog relation用Task SELECTを1回削減しつつ、CoreContextを `work_logs` 単独で使う既存callerのcontractも維持する。

## 3. Expected production effect

V51.9.2 production shapeではHome 23 queriesのうち:

- plan_members: 1
- WorkLog.task再取得用tasks: 1

を削れるため、同じaccount shapeなら約21 queriesが目安になる。

remote MySQLが約78〜85ms/queryだった計測windowでは、query roundtripだけで約150〜170ms相当を削減できる。

実際のproduction値はV51.9.4反映後にV51.8 telemetryで再確認する。

## 4. Persistent DB safety

V51.9.3の `DB_PERSISTENT=true` はV51.9.4と独立したinfra toggle。

production deploy後:

- SQLSTATE / PDO error
- stale connection error
- transaction leakage

がないことを継続監視する。

rollback:

`DB_PERSISTENT=false`

## 5. Regression contract

testsで:

- collaborative Homeでもplan_members SELECT = 0
- tasks + work_logsを同時loadしたCoreContextでTask SELECT = 1
- WorkLog.task relationはload済み
- work_logs単独requestでは従来どおりTask eager loadingが維持される
- V51.9.1 collaborative activity/career contractは維持

を固定する。

## DB migration

なし。
