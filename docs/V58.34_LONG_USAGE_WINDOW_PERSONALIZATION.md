# V58.34 Long Usage Window Personalization Trigger

## Goal

Living Profileへ「長期間の継続利用」をContext Refresh Triggerとして追加する。

目的:

> 時間が経過し、実利用も積み重なった節目で、古いPersonalization Contextを静かに再評価できるようにする。

V58.34は、利用日数から経験レベルや成長を自動判定する機能ではない。

## Source of truth

- `docs/CANOVIA_PERSONALIZATION_SPEC.md`
- `docs/V58.27_LIVING_PROFILE_FOUNDATION.md`
- `docs/V58.31_RETURN_AFTER_ABSENCE_PERSONALIZATION.md`
- current tracked Home / Workspace entry routes

No migration is added.

## Presence extension

Existing:

```text
observed_context.presence
```

V58.34 adds / maintains:

```text
first_seen_at
last_seen_at
previous_seen_at
active_day_count
last_usage_span_days
long_usage_window_reached_at
long_usage_window_span_days
long_usage_window_active_day_count
```

These are account-scoped observed facts.

## Why calendar tenure alone is insufficient

This is intentionally invalid:

```text
first seen 30 days ago
+ almost no real usage
→ "long-term user"
```

V58.34 requires both elapsed time and repeated active days.

## Initial deterministic threshold

A long-usage milestone becomes eligible when:

```text
usage span >= 30 calendar days
AND
tracked active day count >= 6
```

The trigger fires only once in V58.34.

These numbers are MVP product heuristics, not universal behavior science.

## Active day semantics

An active day is counted when an authenticated user with an existing Personalization Context makes a real tracked GET on a new calendar day.

Same-day navigation does not increment the count.

Instant Navigation prefetch does not count.

## V58.31 compatibility

V58.31 may already have:

```text
presence.last_seen_at
```

without:

- `first_seen_at`
- `active_day_count`

Compatibility rule:

```text
existing last_seen_at
+ missing first_seen_at
→ first_seen_at = existing last_seen_at

missing active_day_count
→ conservative baseline = 1
```

No historical active-day count is inferred from incomplete prior telemetry.

This intentionally avoids false long-usage milestones after rollout.

## Long absence interaction

A single real visit must not generate two Living Profile refreshes.

If the same visit qualifies for both:

```text
return_after_absence
AND
long_usage_window
```

then:

```text
return_after_absence wins for that request
```

The long-usage milestone is not marked complete on that request.

If the user continues using Canovia on a later active day, the long-usage trigger may then fire.

## Trigger

When the milestone is reached:

```text
presence updated
→ LivingProfile.refresh(
     trigger = long_usage_window
   )
```

V58.34 introduces no new inference rule.

It only re-evaluates existing deterministic Living Profile logic.

## Telemetry

Existing event:

- `context_refresh_triggered`

Metadata:

```text
trigger = long_usage_window
usage_span_bucket
active_days_bucket
```

Usage span buckets:

- `30_59`
- `60_89`
- `90_plus`

Active-day buckets:

- `6_9`
- `10_14`
- `15_plus`

Exact span days / exact active-day count are not copied into Behavior Event metadata.

## What does NOT change

V58.34 does not automatically modify:

- self-reported Context
- Guidance Level
- experience level
- Study stage
- Plan
- Task
- Entitlement
- Release Level

It does not display a questionnaire merely because the milestone was reached.

## No periodic questionnaire spam

V58.34 fires one silent long-usage milestone.

It does not implement:

- monthly surveys
- recurring 30-day questionnaires
- recurring forced re-diagnosis

Future repeated long-horizon recalibration would require a separate evidence-backed contract.

## No silent profile creation

If no Personalization Context exists:

```text
tracked visit
→ no Presence profile creation
→ no long-usage refresh
```

## UI

No new Growth Experience UI is added in V58.34.

The milestone exists as a Context Refresh Trigger only.

V58.34 also removes a duplicated stronger-evidence explanation block left in the Living Profile UI by the V58.32 sequence. That cleanup does not change Candidate semantics.

## Release boundary

Minimum:

```text
L1 Early Access Core
```

No new route / migration.

Manual review:

- `long_usage_window_personalization`

Check:

- first visit establishes first_seen + active day 1
- same-day navigation does not increment active days
- 30-day span alone is insufficient
- 30-day span + 6 active days triggers once
- exact counts stay out of Behavior Event metadata
- long absence takes precedence if both become eligible together
- long usage remains eligible on a later active day
- V58.31 presence backfills conservatively
- no Personalization Context → no silent enrollment
- mobile / desktop tracked surfaces remain stable

## Non-goals

Not implemented:

- confidence calibration
- experience-level inference
- automatic Guidance change
- automatic Plan-direction change
- recurring usage milestones
- questionnaire scheduling
- retention inference
- paid-tier gating
