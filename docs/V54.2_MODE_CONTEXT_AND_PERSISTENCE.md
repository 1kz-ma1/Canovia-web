# V54.2 Mode Context & Persistence

## Goal

V54.2 makes Workspace Mode selection stable without allowing a saved preference to make a semantically specific deep link lie about its current context.

The user can manually select a public Workspace Mode from the fixed Mode Bar. That choice persists across contextless navigation, while Plan / Task / WorkSession and strong domain routes continue to describe the actual surface being viewed.

## State model

Workspace Mode preference has two states:

```text
null
→ automatic

overview | study | development
→ manually preferred Workspace
```

`null` is intentionally the reset state. There is no separate boolean such as `workspace_mode_is_manual`.

Public values remain registry-driven through `WorkspaceModeRegistry`.

## Persistence

Authenticated users:

```text
users.workspace_mode_preference
```

- nullable string
- stores only a public Workspace Mode key
- persists across devices for the same account

Guest users:

```text
session[canovia_workspace_mode_preference]
```

- session-only fallback
- no new cookie/localStorage contract
- no user row required

`WorkspaceModePreference` owns reading, validation, persistence and reset behavior.

Invalid or unpublished modes are never returned as a valid preference.

## Resolution precedence

V54.2 resolves the visible Workspace using:

```text
explicit caller Mode
→ valid ephemeral workspace_mode query
→ strong domain route hint
→ current Plan / Task / WorkSession profile
→ persisted manual preference
→ Overview
```

This is deliberate.

A manual preference controls ambiguous or contextless surfaces such as Home. It does not overwrite the semantic truth of an unambiguous deep link.

Example:

```text
preferred Workspace = Development
open AP Study Plan
→ current visible Workspace = Study
→ source = PlanProfile
→ stored preference remains Development

return Home
→ current visible Workspace = Development
→ source = ManualPreference
```

This avoids surprising cross-domain UI such as rendering a Study Plan as Development merely because the user previously fixed Development.

## Selection actions

The V54.1 navigation-only entry remains:

```http
GET /workspace/{workspaceMode}
```

It is still useful for ephemeral navigation and does not persist preference.

V54.2 adds persistent selection:

```http
POST /workspace/{workspaceMode}/select
```

The Mode Bar uses the POST action.

After persistence, the controller reuses the same semantic destination policy as V54.1:

- Overview → Home
- Study → best accessible Study Plan → Study Scope
- Development → best accessible Development Plan → GitHub / Development surface
- no matching Plan → Home with ephemeral Mode context and guidance

Best Plan selection remains deterministic:

1. priority
2. nearest deadline
3. Plan ID

Reset:

```http
DELETE /workspace/preference
```

clears the persisted/manual preference and returns to automatic resolution.

## Mode Bar semantics

The fixed bar exposes both current context and stored preference.

Stable data:

- `data-current-workspace-mode`
- `data-workspace-mode-source`
- `data-workspace-mode-preference`

Visible context labels:

- `manual_preference` → 固定中
- `route_hint` → 画面に追従
- `plan_profile` → Planに追従
- explicit/default → 自動

A preferred Mode receives a `固定` marker in the dropdown.

When a strong current context temporarily overrides the preference, the preferred marker stays on the stored Mode while the active state follows the current surface.

## Instant Navigation

Canovia keeps the global app shell mounted during Instant Navigation.

V54.2 therefore extends synchronization so retained Mode Bar state updates:

- current Mode key
- Mode label/icon
- active option
- current marker
- Mode source
- visible context label
- dropdown open state

The persisted preference itself does not change during GET-only Instant Navigation, so it remains stable in the retained shell.

## Access and security

Mode selection does not change authorization.

- Plan lookup still uses `PlanOwnershipService`
- downstream surface authorization remains authoritative
- unpublished Workspace keys cannot be persisted
- persistence is not a privilege or billing boundary

## Migration

`database/migrations/2026_10_04_000700_add_workspace_mode_preference_to_users_table.php`

Column:

```text
users.workspace_mode_preference VARCHAR(32) NULL
```

Existing users migrate to `null` and therefore keep automatic behavior.

No data backfill is required.

## Non-goals

- implement Study Workspace Home
- implement Development Workspace Home
- redesign Overview
- change Plan category/profile classification
- change V53 Intelligence calculations
- change Task progress
- add AI traffic
- add Mode-specific billing
- introduce localStorage persistence
