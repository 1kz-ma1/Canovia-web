# V48.3 Space Station Intake Hub

## 目的

Canovia Map中央のSpace Stationを、単なるInbox / Companionへのリンクではなく、
Canoviaへ情報が入る共通の受け口として完成させる。

基本Flow:

```
Input
  -> Interpret
      -> Connect
          -> Action
```

ユーザーは「どの機能へ入れるべきか」を先に考えなくてよい。

例:

- このスクリーンショットを見て
- PRがマージされた
- 明日の予定が変わった
- このURLをPlanへ残したい
- この作業結果を記録したい
- 次に何を進めればよいか相談したい

Space Stationはまず入力を受け、既存Inbox Intelligence / Routing / Companionへ接続する。

## 既存基盤の再利用

V48.3は新しいAI routing engineを作らない。

再利用:

- InboxItem
- InboxIntelligenceService
- InboxRoutingService
- ExecutionRequestHandoffService
- Companion
- existing private file storage
- Map Spatial Dock

Space Stationはこれらの共通UI / orchestration surfaceになる。

## 1. Input

Space Stationフォームから送信した入力は `intake_mode=chat` としてInboxへ保存する。

対応入力:

- text
- URL
- screenshot / image
- PDF

Space Stationからの入力にはmetadataとして:

```
intake_mode = chat
capture_surface = space_station
```

を保存する。

L1-L3のSpatial Dockから入力した場合は、以下の構造情報だけを `map_context` として保持できる。

- level
- intent
- domain
- plan_id
- collaboration context
- reflection context

本文そのものをprojection key / telemetryへ複製しない。

## 2. Interpret

Native AI + entitlementが利用可能な場合、Space Stationから保存した直後に既存Inbox Intelligenceを実行する。

AIが出してよいもの:

- destination
- short reason
- confidence
- suggested Plan name
- suggested Task name

AIが出してはいけないもの:

- Plan ID
- Task ID
- canonical mutation
- Task completion
- progress change

Interpretationに失敗してもCapture自体は成功させる。

AI利用不可 / temporary failure時は、既存の手動接続Flowへfallbackする。

## 3. Connect

Interpretation結果は候補であり、canonical接続ではない。

ユーザーが確認する項目:

- destination
- Plan
- Task
- execution request details（必要時）

### Current Map Context

L3などでSpace Stationを開いた場合、現在表示中のPlanを
`current_map_context` candidateとしてPlan selectorの初期候補にする。

これは自動接続ではない。

- InboxItem.plan_idはcapture時点では変更しない
- Task IDは推測しない
- Confirmを押すまでcanonical dataを作らない

### Task selector

Plan未選択時はTask selectorを無効化する。

Planを選ぶと、そのPlanに属するTaskだけを選択可能にする。

これによりPlan / Task不整合をUI側でも防ぐ。

## Execution Request

V44.2ではdestinationに `execution_request` が存在する一方、
Space Station confirm formに必須fieldがなくvalidationで停止する不整合があった。

V48.3で以下を追加する。

- execution_instruction
- execution_actor_type
- execution_available_minutes

destinationが `execution_request` の時だけ表示・required化する。

Human Confirm後は既存ExecutionRequestHandoffServiceへ渡し、
Execution Orchestrationへ遷移する。

## 4. Action

人間がroutingを確定し、Space Stationへ戻るdestinationでは
flash-onlyのroute resultを表示する。

表示:

```
Space Station
  -> Plan
      -> Task
          -> Destination
```

可能な場合は次Actionを表示する。

例:

- Task Evidence -> 関連TaskをMapで見る
- Recall -> Recallを確認
- Plan Resource -> Resourceを確認
- Career Capture -> Careerを確認
- keep_inbox -> Inboxを確認

route resultは表示用flash stateであり、新しいcanonical entityではない。

## Companion

Space Stationは必ずroutingする場所ではない。

「まだ整理したくない」「判断を相談したい」場合はCompanionへ入れる。

つまり:

```
Input -> Interpret -> Confirm
          |
          +-> Companion
```

を許す。

## UI

Space Station Surface内に4段階indicatorを表示する。

1. 受信
2. 解釈
3. 接続
4. Action

Desktopではラベル付き。
Mobileではstep number / completionを中心にcompact表示する。

## JavaScript

専用module:

`resources/js/space-station-intake.mjs`

責務:

- execution_request field visibility / required
- selected PlanとTask optionの整合
- Instant Navigation後のremount

canonical mutationやAI実行はJSへ置かない。

## Human agency boundary

自動化可能:

- 入力保存
- Interpretation
- destination候補
- name hint
- current Map Contextの候補表示

Human Confirm必須:

- destination確定
- Plan ID確定
- Task ID確定
- Evidence / Resource / Career Capture作成
- Execution Request確定

Task完了・progress変更はInbox routingの責務にしない。

## Projection / privacy

SpaceStationContextServiceのstate_keyにはuser contentを含めない。

反映してよいもの:

- pending count
- latest Inbox Item ID/status
- candidate destination / confidence
- current context Plan ID
- confirmed destination / target IDs

本文・URL内容・AI reason全文はprojection keyへ直接入れない。

## Non-goals

- autonomous Plan/Task mutation
- AIによるID選択
- Task completion inference
- progress自動加算
