# V58.8 Recall Batch Ingest

Status: implemented / validated  
Branch: `feature/v58-8-recall-batch-ingest`

## 1. Goal

Allow multiple Recall material pages to be selected in one action and extracted
with one Native AI run.

```text
2-5 images / PDFs
→ one submission
→ one private StudyRecallSource per file
→ one Native AI run
→ source_index on each Candidate
→ normal Human Review
→ Recall Deck
```

V58.8 reduces repeated upload and provider-execution friction without weakening
the existing Source / Candidate / Deck authority boundaries.

## 2. Data model

No batch table and no migration were added.

The existing invariant remains:

```text
1 StudyRecallSource = 1 saved material file
```

A batch is an operation over multiple Source rows, not a persistent domain
entity.

This preserves:

- per-Source private file authorization;
- V58.7 per-Source retry;
- existing account/file cleanup;
- Candidate -> one primary evidence Source relation.

## 3. Intake limits

Batch intake accepts:

- 2 to 5 files;
- PDF / JPEG / PNG / WEBP;
- maximum 10 MB per file;
- maximum 20 MB total material.

Single-file upload and pasted-text extraction remain unchanged.

## 4. One Native AI run

`StudyRecallBatchCandidateExtractionService` sends all batch files through one
`NativeAiGateway::generateStructured()` call.

Input content is ordered as:

```text
SOURCE_INDEX 0 marker
file 0
SOURCE_INDEX 1 marker
file 1
...
final extraction prompt
```

The marker contains the zero-based index and original filename.

The structured schema requires every Candidate to return its primary
`source_index`.

This allows a single model run to read multiple pages while still assigning each
Candidate to a concrete saved Source.

## 5. Candidate persistence

Batch Candidates keep the V41.12 fields:

- prompt
- answer
- note
- tags
- source_excerpt
- confidence

and add the extraction-only field:

- source_index

`source_index` is resolved to the matching `StudyRecallSource` before
persistence.

The existing uniqueness boundary remains authoritative:

```text
task_id + fingerprint(prompt|answer)
```

If the same concept appears on multiple pages, only one Candidate is persisted.

No Candidate enters the Recall Deck without the existing Human Review / promote
step.

## 6. Source result state

On successful extraction:

- every Source becomes `ready`;
- every Source shares the same successful `native_ai_run_id`;
- each Source stores only the number of newly created Candidates attributed to
  that Source.

On Native AI failure:

- every Source becomes `failed`;
- every Source retains the same failed Native AI run ID;
- saved private material remains available;
- V58.7 can retry each Source independently.

## 7. Native AI failure trace fix

V58.8 also closes a pre-existing traceability gap in `NativeAiGateway`.

Provider HTTP errors could create a failed `NativeAiRun` but rethrow a
`NativeAiExecutionException` without that run ID.

The gateway now rethrows provider-originated failures with the current run ID
when the original exception did not already contain one.

This lets both batch and single-Source extraction retain the failed run
reference.

## 8. Request fingerprint privacy

`NativeAiGateway::inputPartFingerprints()` now fingerprints marker
`input_text` in addition to image/file payloads.

Only SHA-256 values are persisted in the request hash context.

Raw marker text and Base64 material bytes are not stored in
`NativeAiRun.request_hash`.

## 9. UI

Automatic AI users now see:

`複数ページをまとめて取り込む`

inside the Recall material section.

The batch form:

- uses a multi-file picker;
- explains the 2-5 file limit;
- explains the 10 MB per-file / 20 MB total limits;
- states that the files are processed in one Native AI run.

The existing single-file / pasted-text form remains the default simple path.

Free/manual Recall users do not see the batch extraction UI.

## 10. Failure cleanup

If any failure occurs while saving the batch before provider execution:

- already stored batch files are deleted;
- already created batch Source rows are deleted;
- Native AI is not called.

After provider execution has begun, Source rows/files are intentionally retained
so V58.7 retry can recover them.

## 11. Security / boundaries

V58.8 does not:

- fetch arbitrary URLs;
- fetch Plan Resource URLs;
- create public material URLs;
- change Recall scheduling;
- change V58.6 Task progression;
- change V58.7 retry rules;
- auto-promote Candidates;
- add background jobs;
- add a migration;
- change entitlement or billing behavior.

## 13. Result

The material intake path now supports real multi-page study input without
multiplying provider runs:

```text
page 1 + page 2 + page 3
→ one upload action
→ three private Sources
→ one Native AI run
→ deduplicated pending Candidates
→ Human Review
→ Recall learning
→ V58.6 progression
```

This completes the V41.12 "multiple pages / multiple images batch source"
follow-up while retaining V58.7 recovery per saved Source.
