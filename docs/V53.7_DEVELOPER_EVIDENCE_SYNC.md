# V53.7 Developer Evidence Sync

## Goal

V53.7 connects real GitHub activity to Canovia Intelligence without converting activity directly into progress or completion.

```text
GitHub webhook
→ minimal routing facts
→ authoritative GitHub App REST re-fetch
→ explicitly linked Artifact / Task
→ TaskEvidence
→ normalized EvidenceObservation
→ V53.8 Development State / Release Readiness
```

V53.7 stops at the Evidence boundary. It does not calculate release readiness and does not choose a Development Action.

## Core authority rule

A signed webhook is a routing signal, not the authoritative Development fact.

Canovia never imports the raw webhook payload directly into Intelligence. After routing, it re-reads the current object through the installed GitHub App and records only bounded facts with known decision meaning.

```text
Webhook says something changed
        ↓
Canovia identifies the linked object
        ↓
GitHub App REST confirms current state
        ↓
controlled Evidence
```

This preserves the V46.10 safety boundary while extending it beyond Pull Requests.

## Supported Development Evidence

V53.7 normalizes the following GitHub facts:

- Pull Request current state
- Pull Request review
- Pull Request CI
- Pull Request merge
- Issue state
- Branch head
- Commit existence / identity
- Deployment state

TaskEvidence types:

- `pull_request_observed`
- `pull_request_review_submitted`
- `pull_request_ci_observed`
- `pull_request_merged`
- `github_issue_observed`
- `github_branch_observed`
- `github_commit_observed`
- `github_deployment_observed`

These observations are facts. None of them means `Task = done` by itself.

## Webhook routing

`GitHubWebhookService` now accepts:

- `pull_request`
- `pull_request_review`
- `workflow_run`
- `check_run`
- `check_suite`
- `issues`
- `push`
- `create` for Branch creation
- `deployment`
- `deployment_status`

`github_webhook_deliveries.routing_targets` stores only minimal bounded locators such as:

```text
pull_request → number
issue        → number
push         → branch + commit SHA
branch       → branch name
deployment   → deployment id
```

The existing `pull_request_numbers` field remains for backward compatibility with V46.10.

Raw webhook body, commit message, Issue body, Deployment payload, and other unbounded provider text are not persisted in the delivery record.

## Explicit-link boundary

GitHub Repository activity is not broadcast across every Task in a Plan.

V53.7 only records non-PR Evidence when:

1. the Repository is explicitly registered and connected to the same GitHub App installation
2. a matching GitHub Artifact is explicitly linked to a Task
3. the actor owning the Plan has `developer_github_evidence` capability
4. GitHub authoritative state still matches the routed object

An Artifact without a linked Task is rejected before a GitHub API read.

This prevents generic repository activity from becoming false Evidence for unrelated work.

## Entitlement boundary

Existing `FeatureAccessService` and `FeatureKey::DeveloperGithubEvidence` remain the authorization boundary.

The new non-PR sync checks entitlement before GitHub REST re-fetch. A Plan without the capability does not receive background GitHub reads through V53.7.

No second Premium check or Developer-specific billing rule is introduced.

## Pull Request Evidence

V46 already returned Review / CI / Merge facts. V53.7 adds `pull_request_observed` so Development Intelligence can distinguish:

- PR exists and is open
- Draft PR
- closed PR
- merged PR
- head/base refs and head SHA

Repeated identical PR state is idempotent. A meaningful PR state change can create a new observation.

Review, CI, and Merge Evidence remain separate because they represent different quality gates.

## Issue Evidence

`inspectIssue()` re-fetches the Issue and exposes only:

- Issue number
- state
- state reason
- locked flag
- assignee count
- update / close timestamps

V53.7 does not import Issue title, body, comments, or arbitrary labels into Intelligence.

An Issue closing is evidence of GitHub workflow state, not proof that the feature is production-ready.

## Branch and Commit Evidence

A Branch event or push may produce:

- `github_branch_observed`: branch name + authoritative head SHA + protection flag
- `github_commit_observed`: commit SHA + branch + parent count + signature verification flag

Commit message, changed-file list, patch/diff, and source code are excluded from Intelligence Evidence.

A push confirms implementation activity occurred. It does not assign progress percent.

## Deployment Evidence

`inspectDeployment()` re-fetches the GitHub Deployment and its latest status.

Normalized facts:

- Deployment ID
- SHA
- ref
- environment
- latest status
- production-environment flag
- transient-environment flag

Deployment payload and status description are excluded.

Deployment Evidence is only attached to linked PR / Branch / Commit Artifacts whose authoritative SHA/ref matches the deployment. It is not attached to every Task in the Repository.

A successful deployment is a strong release signal but still does not automatically mean the product requirement is complete; V53.8 will combine it with other quality gates.

## GitHub App permissions

V53.7 reuses existing permissions where possible and introduces no new secret/token storage model.

Required GitHub App permissions by signal:

- Pull Requests / Reviews: `pull_requests` read or write
- Branch / Commit / push: `contents` read or write
- Issue: `issues` read or write
- Deployment: `deployments` read or write
- CI: existing optional `actions`, `checks`, and `statuses` read signals

To receive the new automatic signals, the GitHub App configuration must subscribe to the corresponding webhook events and installations must have the matching permissions. Canovia application code does not silently alter GitHub App permissions.

Existing installations may require GitHub-side permission approval after the App configuration is expanded.

## Task mutation policy

V53.7 never changes:

- Task progress
- Task status
- remaining minutes
- Canovia workflow lane

GitHub activity only creates or updates idempotent Evidence records.

```text
Commit observed ≠ 50% complete
PR merged       ≠ 100% complete
Deploy success  ≠ requirement verified
```

V53.8 owns the interpretation layer.

## Intelligence normalization

`TaskEvidenceAdapter` allowlists Development facts before they cross into `EvidenceObservation`.

Allowed facts include identifiers and decision-relevant states such as:

- repo / Artifact reference
- PR number/state/draft/merged/head SHA
- review state
- CI state
- Issue number/state
- Branch/head SHA
- Commit SHA
- Deployment environment/status/SHA

Excluded:

- raw webhook payload
- Issue body/title
- PR body
- commit message
- changed files / patch
- source code
- Deployment payload/description
- arbitrary provider metadata

## DevelopmentEvidenceCollector

`App\Intelligence\Development\DevelopmentEvidenceCollector` is the V53.8 input boundary.

It collects only whitelisted GitHub TaskEvidence for a Plan, orders it chronologically, and converts each item through the generic `TaskEvidenceAdapter`.

V53.8 therefore does not need to understand webhook routing, GitHub REST clients, or TaskEvidence provider payloads.

```text
GitHub integrations
→ TaskEvidence
→ DevelopmentEvidenceCollector
→ EvidenceObservation[]
→ Development State Builder (V53.8)
```

## Existing V46 compatibility

V53.7 preserves the existing V46 return layer rather than replacing it.

- PR manual return sync still works
- PR webhook return sync still works
- GitHubEvidenceDecisionService still receives existing Evidence
- GitHub Workflow Hub remains a user-facing workflow surface

A latent model/table mismatch was also corrected: `GitHubWebhookDelivery` now explicitly binds to the migrated `github_webhook_deliveries` table.

## What V53.7 does not do

V53.7 does not:

- infer percentage progress from commits
- mark a Task complete after merge
- mark a release ready after CI
- mark a requirement complete after deployment
- build Development Readiness
- generate a Development Next Action
- ingest repository source code into Intelligence
- fan repository events out to unlinked Tasks

Those interpretation decisions belong to V53.8.

## Next: V53.8 Developer Readiness

V53.8 should interpret the normalized Development Evidence into goal-relative release state.

Candidate dimensions include:

- implementation evidence
- review state
- CI / automated test state
- merge state
- deployment state
- explicit verification
- specification / acceptance-criteria synchronization

The intended loop is:

```text
Development Evidence
→ Development State
→ Release Readiness
→ largest missing quality gate
→ Decision
→ Current Action
```

A merged PR is therefore one strong input, not the final answer.


## V53.8 completion boundary

V53.8 now consumes `DevelopmentEvidenceCollector` output and evaluates release readiness per Task.

The final V1 release gates are:

- implementation
- CI / test
- review
- merge
- production deploy
- verification
- specification synchronization

GitHub facts remain Evidence and are not converted directly into Task progress.

Verification and Spec Sync are explicit Human Confirmation Evidence bound to concrete release identity. New code or a new Production Deployment can therefore invalidate stale confirmations instead of leaving an old Ready state active.

Details are authoritative in `docs/V53.8_DEVELOPER_READINESS.md`.
