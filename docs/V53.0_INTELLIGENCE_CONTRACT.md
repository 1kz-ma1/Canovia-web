# V53.0 Intelligence Contract

## Goal

V53 changes Canovia from a Task-centered planner into an Intelligence-driven execution system.

The Core loop is:

```text
Goal
  ↓
Current State
  ↓
Gap / Readiness
  ↓
Decision
  ↓
Next Action
  ↓
Evidence
  ↓
Outcome
  ↓
State update / Replan
```

Task remains important for transparency and execution, but Task is no longer the source of truth for deciding what should happen next.

## Core rule

```text
Task != Intelligence state
Task != Decision source of truth

Task = one possible projection of an Action
```

This means Canovia may:

- keep a long-lived manual Task
- generate a temporary Action without creating a durable Task
- replace an Action when new Evidence changes the State
- complete or retire a projected Task when the Action is no longer useful
- explain why an Action was proposed without requiring the user to inspect a Task tree

Existing Plan and Task flows remain valid and are not removed by V53.0.

## Vocabulary

### State

A normalized description of the current reality for one scope.

Examples:

- Study: mastery, coverage, retention, time remaining
- Development: implementation, CI, review, deploy, verification

State is derived from Evidence and deterministic context. It is not a copy of Task progress.

Contract: `App\Intelligence\Data\StateSnapshot`.

### Evidence

An observation about reality.

Examples:

- study practice result
- recall review
- GitHub PR merge
- CI result
- file or image capture
- execution reflection

V53.0 does not create a competing Evidence database. Existing `TaskEvidence` and later domain Evidence sources can be normalized into `EvidenceObservation`.

Contract: `App\Intelligence\Data\EvidenceObservation`.

### Readiness

An assessment of how prepared the scope is to reach the relevant outcome.

Readiness may have:

- score
- level
- components
- gaps
- confidence

Examples:

- exam readiness
- release readiness

Readiness is not Task completion percentage.

Contract: `App\Intelligence\Data\ReadinessAssessment`.

### Decision

The selected interpretation of State and Readiness about what should happen next.

A Decision must be explainable and traceable to its input State through `inputFingerprint`.

Contract: `App\Intelligence\Data\Decision`.

### Action

An executable proposal produced from a Decision.

An Action may later be projected into:

- Task
- Next Action card
- guided execution
- external-AI handoff
- native execution

Core does not require a Task ID.

Contract: `App\Intelligence\Data\ActionProposal`.

### Outcome

What happened after an Action was attempted.

Outcome is based on subsequent Evidence and becomes input to the next State.

Contract: `App\Intelligence\Data\OutcomeObservation`.

### Confidence

A normalized 0.0–1.0 confidence value used for Evidence, Readiness, Decision, Action and Outcome.

A deterministic fact may use confidence 1.0. Estimated or inferred values should use lower values when appropriate.

Contract: `App\Intelligence\Data\Confidence`.

## Domain boundary

V53.0 introduces:

- `general`
- `study`
- `development`

through `IntelligenceDomain`.

The Core must not contain Study-specific or Development-specific rules. Those arrive in later V53 phases through domain implementations of the common contracts.

## Processing contracts

```text
StateBuilder
   ↓
ReadinessEvaluator
   ↓
DecisionEngine
   ↓
ActionGenerator
   ↓
OutcomeInterpreter
   └──────→ next Evidence / State
```

### StateBuilder

Consumes domain context and normalized Evidence and returns a StateSnapshot.

### ReadinessEvaluator

Evaluates State and returns readiness, gaps and confidence.

### DecisionEngine

Selects the next decision from State + Readiness.

This boundary may later be backed by:

- deterministic rules
- domain rules
- OpenAI reasoning
- future Canovia-owned models

V53.0 intentionally does not choose a reasoning provider.

### ActionGenerator

Turns a Decision into one or more executable Action proposals.

It does not directly mutate Task state.

### OutcomeInterpreter

Converts Evidence collected after an Action into an Outcome observation.

The next phase can use that Outcome to rebuild State.

## Existing Canovia assets

V53.0 reuses rather than replaces existing foundations.

### TaskEvidence

Existing TaskEvidence remains valid durable Evidence for Task-linked activity.

Later adapters may convert TaskEvidence rows to EvidenceObservation.

### GuidedExecution

GuidedExecution can become one execution surface for ActionProposal.

It is not the Intelligence source of truth.

### GitHubEvidenceDecisionService

This existing deterministic service proves that Evidence can drive a user-reviewable state candidate.

Later V53 Developer work should migrate this concept behind the generic Intelligence contracts rather than delete working GitHub behavior prematurely.

### UserStateSnapshot

The existing UserStateSnapshot models user-behavior signals such as decision load and focus continuity.

It is not equivalent to V53 domain StateSnapshot. Both may coexist.

### NativeAiRun

NativeAiRun remains provider/cost/operation observability for AI execution.

It is not a Decision record and must not become the Intelligence source of truth.

## Data collection direction

The long-term training/evaluation asset is the relationship:

```text
State before
→ Decision
→ Action
→ Outcome
→ State after
```

V53.0 defines the runtime contract only.

Durable Intelligence trace storage is intentionally deferred until the contract has been exercised by Study V1. This avoids prematurely freezing a database schema around unvalidated fields.

When persistence is introduced it must preserve:

- domain
- state fingerprint / normalized features
- decision type and reason
- confidence
- action taken or rejected
- resulting outcome
- state delta

Raw private documents, full prompts, secrets, session data and provider payloads must not be treated as default training data.

## Trust and transparency

Canovia must be able to answer:

- What is the current State?
- What is missing?
- Why is this Action recommended?
- How confident is the recommendation?
- Which Evidence changed the recommendation?

Task lists remain useful as an inspectable execution view, but users should not need to maintain them manually for Canovia to understand reality.

## V53.0 non-goals

V53.0 does not implement:

- Study-specific readiness
- Developer-specific release readiness
- OpenAI routing
- prompt generation
- model training
- Intelligence database migrations
- automatic Task mutation
- automatic GitHub progress mutation
- new user-facing UI
- pricing / entitlement changes

## Compatibility rule

Existing Task / Plan / Evidence / Execution behavior must continue to work.

V53 is introduced alongside current flows and only becomes authoritative after domain-specific validation proves the new loop.
