# V46.5 GitHub App Connection UX

## Goal

V46.4で実装したGitHub App Write Layerを、一般ユーザーがApp ID / Private Key / PATを意識せず接続できるUXへする。

ユーザーの操作は次の形に限定する。

```text
Canovia
  「GitHubを接続」
        ↓
GitHub
  Account / Organizationを選択
  Repositoryを選択
  Permissionを確認
        ↓
Canovia
  接続状態をserver-sideで検証
        ↓
  接続済み / 承認待ち / 権限承認待ち
```

Canovia運営側とRepository利用者の責務を分離する。

## Operator setup

Canovia運営側が1回だけ行う。

GitHub App側:

- Public GitHub Appとして運用可能な設定
- Metadata: read
- Contents: read & write
- Pull requests: read & write
- Setup URL:
  `{CANOVIA_APP_URL}/github-workflow/github-app/setup`
- V46.5では Redirect on update を前提にしない
- install URL:
  `https://github.com/apps/{app-slug}/installations/new`

Canovia server-side:

- `GITHUB_APP_ID`
- `GITHUB_APP_PRIVATE_KEY` または `GITHUB_APP_PRIVATE_KEY_BASE64`
- `GITHUB_APP_INSTALL_URL`

Private Key / installation token / PATは一般ユーザーへ入力させない。

## User setup

Repositoryを利用するユーザーはRepository Overviewの:

`GitHubを接続`

だけを起点にする。

Canoviaは64桁のrandom stateを生成し、15分だけsessionへ:

- artifact_id
- plan_id
- Canovia user_id
- repo_full_name
- expires_at

を保持する。

GitHub install URLへstateを付与してredirectする。

state自体をDBへ永続化しない。

## Setup callback security

GitHubのSetup URLへ戻るquery parameter:

- `state`
- `installation_id`
- `setup_action`

を直接権限根拠にしない。

特に `installation_id` はbrowser queryをそのまま信用しない。

callbackでは:

1. stateがCanovia sessionに存在する
2. 15分以内
3. stateを開始したCanovia userと一致
4. 対象Artifact / Planへのedit権限が現在もある
5. DeveloperGithubWrite entitlementが現在もある
6. stateに保存したrepo_full_nameとArtifact URLが一致
7. Canovia serverがGitHub App JWTで対象Repositoryの現在Installationを再取得
8. GitHubから取得したInstallation IDとcallback installation_idが一致

を確認して初めてconnectedとする。

stateはcallbackでpullし、one-timeにする。

この設計ではSetup URLのqueryだけでGitHub write権限を発生させない。

## Connection state

Repository Artifact metadata:

`metadata.github_app_connection`

へ安全なprojectionだけを保持する。

status:

- `connecting`
  - CanoviaからGitHub install flowを開始した
- `pending`
  - GitHub側でまだ対象RepositoryへのInstallationを確認できない
- `connected`
  - 対象RepositoryへのInstallationと必要write permissionを確認済み
- `permission_update_required`
  - Installationは存在するがContents / Pull Requestsのwriteが不足
- `revoked`
  - 過去connectedだったが現在Installationを確認できない
- `verification_failed`
  - callback informationとserver-side GitHub verificationが一致しない

保存可能:

- installation_id
- account_login
- account_type
- target_type
- repository_selection
- permissions
- GitHub management URL
- requested_by_user_id
- requested_at
- connected_at
- last_checked_at
- setup_action

保存禁止:

- GitHub App Private Key
- App JWT
- installation access token
- PAT
- user password
- OAuth access token

## Organization / enterprise policy

企業Organizationでは、Repository AdminがGitHub Appを直接installできないpolicyがあり得る。

その場合GitHub側でOrganization Ownerへのrequestとなり、Canoviaはwrite可能とみなさない。

Canovia UIでは:

```text
接続待ち
OrganizationではOwner承認が必要な場合があります
承認後 → 接続状態を確認
```

と表示する。

Owner承認後、callbackが再度発生しなくても:

`接続状態を確認`

からGitHub App JWTで対象RepositoryのInstallationをserver-side確認し、connectedへ更新できる。

企業側がApp installation request自体を禁止している場合、Canoviaが回避しない。
そのOrganizationではGitHub Write機能は利用不可のままとする。

## Permission updates

GitHub Appが対象Repositoryへinstallされていても:

- Contents != write
- Pull Requests != write

なら `permission_update_required`。

Canovia write formは表示しない。

GitHub側でpermission更新が承認された後に「接続状態を確認」で再評価する。

## Repository management

GitHub APIから安全なinstallation management URLが得られた場合:

`GitHubで管理`

を表示できる。

GitHub側で:

- Repository access変更
- App uninstall
- permission approval

等を行う。

CanoviaはGitHub Organization policyを変更しない。

## Write surface gating

V46.5 UIでは次をすべて満たすときだけ「変更をレビューに出す」formを表示する。

- Plan edit permission
- DeveloperGithubWrite entitlement
- server-side GitHub App configured
- Repository Artifact
- `github_app_connection.status = connected`

ただしHTTP write endpoint自体はconnection metadataだけを信頼しない。
V46.4 `GitHubRepositoryWriter` が実行時にGitHubからInstallation / token / permissionを再確認する。

つまりmetadataはUX projection、GitHub APIがwrite時のauthority sourceである。

## Existing installation discovery

GitHub Appが先にRepositoryへinstallされていた場合でも、
「接続状態を確認」で現在Installationを発見できる。

Setup callbackを必須の唯一経路にしない。

## Corporate use

会社RepositoryでCanoviaを利用できるかは、その会社の:

- GitHub Organization policy
- GitHub App installation policy
- third-party integration review
- security / compliance policy
- source code handling rule

に依存する。

Canoviaはpolicyを迂回しない。

導入不可の場合でも、Repository URL / manual Workflow / External AI handoffなど、
write permissionを要求しない経路は分離して維持できる。

## Non-goals

- Organization Owner approvalの自動化
- GitHub Organization policy変更
- SSO / SCIM bypass
- GitHub Enterprise Server対応
- OAuth user access token
- user identityをGitHub commit authorへ偽装
- PAT storage
- App auto-install
- Repository access auto-expansion
- webhook
- background installation polling
- automatic merge
